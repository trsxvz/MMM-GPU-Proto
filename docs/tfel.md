# TFEL and MFront: technical details

This document describes what the prototype changes in TFEL and MFront, and
why. It is meant for readers who want to understand or review these
changes. The use of the interfaces, with their complete examples, is
documented in the TFEL tree (see [the last section](#documentation-in-the-tfel-tree)).

## Organisation of the changes

The changes form four families.

| Family | Content | Effect on the CPU results |
|---|---|---|
| GPU code in TFEL | mathematical and material headers usable in GPU code | none |
| GPU-compatible generated code | classes generated by MFront, drivers of the `generic` interface shared with the new interface | none |
| `generic-parallel` interfaces | new interface of behaviours and models, extension of the one of material properties, tests | not applicable (new libraries) |
| Fixes | defects found along the way in the existing code | fixed, one commit each |

## Generic-parallel interface of behaviours and models

MFront had a `generic` interface that integrates a behaviour at one point.
The `generic-parallel` interface generates, for the same behaviour,
functions that process a whole batch of points. It is inspired by the
`generic-parallel` interface of material properties, already present in
TFEL.

### Generated functions and symbols

For each behaviour and each modelling hypothesis, the library exports the
functions of the `generic` interface followed by `_generic_parallel`:

- the integration function of a batch,
  `<behaviour>_<Hypothesis>_generic_parallel`;
- one function per initialize function,
  `<behaviour>_<Hypothesis>_InitializeFunction_<name>_generic_parallel`;
- one function per post-processing,
  `<behaviour>_<Hypothesis>_PostProcessing_<name>_generic_parallel`;
- for an orthotropic behaviour, the rotations of the gradients, of the
  thermodynamic forces and of the blocks of the tangent operator (suffixed
  by the stress measure or the finite strain tangent operator);
- `<behaviour>_generic_parallel_report`, which analyses the statistics of
  asynchronous computations.

This is the naming of the material properties (`S_generic_parallel`,
`S_generic_parallel_report`). MFront refuses a behaviour or a model whose
name contains `_generic_parallel`.

It also exports description symbols, read at loading time:

| Symbol | Value | Role |
|---|---|---|
| `<behaviour>_mfront_interface` | `GenericParallel`, or `Generic` with the `generic_functions` option | tell if the functions of a point are available |
| `<behaviour>_generic_parallel_backend` | `cuda`, `hip`, `stlpar`, `kokkos`, `raja`, `sycl`, `openmp`, `openacc` or `arcane` | know where and how the behaviour computes |
| `<behaviour>_generic_parallel_api_version` | `MFRONT_GPB_API_VERSION` (3) | tell if the functions of batches are available, reject an incompatible contract |
| `<behaviour>_generic_parallel_memory_space` | `host`, `device` or `any` | know where to place the data (see [Memory space](#memory-space)) |

These symbols let the caller check everything at loading time, without
compiling against TFEL. This is what MGIS does.

### Data contract

The contract is in C, in `MFront/GenericParallelBehaviour/BatchData.h`. A
batch is described by a structure (`mfront_gpb_BatchData`) rather than by a
long list of arguments. A behaviour has a dozen groups of variables, and a
structure can evolve without changing the prototype of the functions. Its
version is exported by the libraries.

Each group of variables is a **field**: a pointer and two strides.

```c
typedef struct mfront_gpb_ConstField {
  const mfront_gb_real* values;          // first value of the first point
  mfront_gb_size_type point_stride;      // between two points, 0: uniform
  mfront_gb_size_type component_stride;  // between two components
} mfront_gpb_ConstField;
```

Two strides cover the two useful layouts:

- point by point, the layout of MGIS: `point_stride` is the size of the
  group, `component_stride` is 1;
- component by component, which gives coalesced memory accesses on GPU:
  `point_stride` is 1, `component_stride` is the number of points.

Material properties and external state variables can also be given
**variable by variable**. Each one is then uniform or given per point,
independently of the others. This is the natural form of the data of
MGIS. The elements of an array of variables (`a[2]`) are distinct
variables, as in the symbols exported by MFront.

The batch structure also contains the number of points, the time
increment, the computation options (the first three values of `K` of the
`generic` interface, same meaning), the initial time step factor, the
optional outputs (tangent operators, time step factors and statuses per
point, speed of sound), the states at the beginning and at the end of the
time step, the statistics and the execution policy (see
[Execution policies](#execution-policies)).

### Execution at one point

The work at one point is written once, in
`MFront/GenericParallelBehaviour/Integrate.hxx`, as templates usable on the
host and on the GPU:

1. the values of the point are copied into local arrays, whose sizes are
   known when the code is generated;
2. the `generic` view of the point is built on these copies, and the
   integration strategy of the behaviour is called;
3. the outputs are copied back into the fields, and the status of the point
   is recorded.

A direct access to the fields, without local copy, was measured: no gain at
run time, and 25 to 40 % more compilation time with nvcc. It was removed.

The data of a point are described by a generated type (`PointTraits`). It
gives the maximum sizes of the data of a point and the integration strategy
of the behaviour. A type rather than a value, because nvcc cannot generate
the host launcher of a kernel when one of its template parameters is a
class.

The generated behaviour class is the same for both interfaces. The
`generic-parallel` interface derives from the `generic` interface and
reuses the members that the latter adds to the class. The generator writes
only once the identical blocks produced by several interfaces: the same
behaviour can therefore be generated for both interfaces at once. The
interface only adds a constructor that receives the parameters.

The `generic-parallel` interface has no integration code of its own. The
drivers of the `generic` interface (small strain, finite strain,
Green-Lagrange and Hencky strategies, initialize functions,
post-processings) were split in two:

- a core usable on host and GPU, which takes the computation options
  explicitly;
- the historical host functions, with an unchanged signature, which decode
  the options and call the core.

Both interfaces therefore share the same cores. The integration strategies
(`StandardIntegrator`, `FiniteStrainIntegrator`,
`GreenLagrangeStrainIntegrator`, `LogarithmicStrainIntegrator`,
`ModelIntegrator`) are types chosen by the generated code.

Initialize functions and post-processings are called through generated
function objects, never through pointers to members: `nvc++` ignores these
pointers without any message in GPU code.

### Backends

Each backend provides a single primitive: apply a function object to the
points of the batch and reduce the statistics (number of failures, of
unreliable results, smallest time step factor, first failed point and
first unreliable point). Each
one uses the idiomatic primitive of its programming model.

| Backend | Primitive | Execution queue | Asynchronous | Options |
|---|---|---|---|---|
| `cuda`, `hip` | one thread per point, warp vote, atomic operations only when an event occurs | stream (`cudaStream_t`, `hipStream_t`) | yes | `number_of_threads_per_block` (128 by default) |
| `stlpar` | `std::transform_reduce` on a counting iterator | none | no | `execution_policy`, `device_stack_size` |
| `kokkos` | `Kokkos::parallel_for`, atomic operations only when an event occurs | instance of the execution space | yes | `execution_space` |
| `raja` | `RAJA::forall`, atomic operations only when an event occurs | resource of camp of the execution policy | yes | `execution_policy` |
| `sycl` | `parallel_for` and atomic updates | `sycl::queue`, mandatory | yes, if no value is copied and if the queue is in order | `data_transfer_policy`, `device_stack_size` |
| `openmp` | `target teams distribute parallel for` or `parallel for` | none | no | `offload`, `device_stack_size` |
| `openacc` | `parallel loop` with reductions | none | no | `device_stack_size` |
| `arcane` | command of Arccore (`RUNCOMMAND_LOOP1`), native atomic operations only when an event occurs | queue of Arccore (`RunQueue`), mandatory | yes | none |

A few choices deserve an explanation:

- SYCL does not use reductions: their barriers make AdaptiveCpp fail on
  large kernels run on CPU.
- The kernel must run after the computations already submitted to the
  queue, which may produce its inputs. An in-order SYCL queue guarantees
  it. With an out-of-order queue, a synchronous computation first waits
  for the end of the queue. An asynchronous computation is refused there
  (invalid arguments): nothing would guarantee the order. The rule is the
  same for behaviours and material properties.
- The number of threads per block of CUDA and HIP is rounded to the
  multiple of the warp size, read on the GPU at run time. The warp vote
  assumes complete warps. The same rule holds for behaviours and material
  properties.
- Kokkos must be a **shared** library, compiled **without relocatable
  device code** with CUDA. The generated libraries are loaded by `dlopen`:
  the caller and they must share the same instance of Kokkos. The
  generated function checks that Kokkos is initialised, it never
  initialises it. mfem-mgis built with the `enable-kokkos` option
  initialises it on demand (option `--kokkos` or variable
  `MFEM_MGIS_KOKKOS`, see `results/kokkos-polycrystal-2026-10-11`). The
  statistics of a synchronous computation are in
  `Kokkos::SharedSpace`, as for material properties. The `OpenACC` and
  `OpenMPTarget` backends of Kokkos do not have this space: a static
  assertion reports it.
- RAJA needs no initialisation. The execution policy is a type of RAJA
  (`RAJA::cuda_exec_async<128>` by default in code compiled for CUDA, the
  OpenMP loop on the host). A null queue denotes the default stream of the
  current GPU, as for `cuda` and `hip`: the default resource of camp is a
  stream created by camp on the GPU 0, wrong with one GPU per MPI process.
  The statistics of a synchronous computation are in managed memory
  allocated by the resource of camp, and the shared data are copied once
  per GPU. The policies of OpenMP target and SYCL are refused at
  compilation: camp cannot allocate managed memory for them, and the `raja`
  configuration only compiles for CUDA and the host. RAJA must be a shared
  library, as Kokkos. RAJA is built with
  CUDA and OpenMP in its own spack environment (`deps/spack/mmm-raja`): its
  camp needs OpenMP, while the camp of `mmm-gpu` (used by Umpire) does not
  have it. With CUDA, nvcc compiles all the sources of the library,
  including those shared with the `generic` interface, as `nvcc_wrapper`
  does for Kokkos.
- Arcane is used through its core component, Arccore, built alone with
  CUDA by `scripts/build-arccore.sh` (accelerator mode CUDA, clang 20 and
  CUDA 12.9, as `cuda-clang`). The queue chooses the device at run time:
  a library compiled for CUDA computes on the GPU with a CUDA queue, on the
  threads of the host with a `Thread` queue, sequentially with a
  `Sequential` queue. A CUDA queue with a library compiled without CUDA,
  and a null queue, are refused (`-5`). The memory space is therefore
  `device`, as for OpenACC with a compiler other than `nvc++`. The atomic
  operations are those of CUDA on the GPU and `std::atomic_ref` on the
  host: those of Arccore have no unsigned 64-bit integers, and its
  reducers synchronise the queue. The commands are launched asynchronously
  (`RunQueue::ScopedAsync`, the state of the queue is restored), then
  `barrier()` for a synchronous computation. The statistics and the shared
  data are in the unified memory of Arccore. The loops and the kernels of
  Arccore use 32-bit indices: a batch is split in commands of at most 2^30
  points, so that the index of a thread never overflows.
  The generated source is a `.cu` file compiled by clang as a CUDA
  compiler. The code of the behaviours is also emitted for the host, where
  an unqualified `max` (the generated code has `using namespace std`)
  would select the device function of CUDA: the device functions are
  excluded from the overloads of the host compilation
  (`-Xarch_host -fgpu-exclude-wrong-side-overloads`). The configuration
  file of Arccore is not used (`find_package` would enable the CUDA
  language in TFEL): the headers and libraries are searched in
  `Arccore_ROOT`, the accelerator mode read in `arccore_config.h`.
- OpenACC targets the device chosen by the compiler: the GPU with
  `nvc++ -acc=gpu`, the cores of the host with `nvc++ -acc=multicore`. The
  memory space follows from the compilation macros
  (`__NVCOMPILER_OPENACC_GPU`, `__NVCOMPILER_OPENACC_MULTICORE`), and
  `TFEL_DEVICE_CODE` is defined with `-acc=gpu`, as with `-mp=gpu`. The
  OpenACC runtime of `nvc++` uses the CUDA driver without the CUDA runtime:
  the stack size is set through the driver on the context of OpenACC
  (`MFront/GenericParallel/OpenACCStackSize.hxx`). The shared data are
  copied by `acc_malloc` once per device. The minimum reductions of OpenACC
  on `long long` and `unsigned long long` return 1 on the GPU with nvc++
  25.11 (`reproducers/nvhpc-openacc-min-reduction`): the indices are
  reduced as `size_t` or `unsigned long`. With the separate and managed
  memory modes, nvc++ 25.11 fails to compile the headers of TFEL for
  OpenACC (undefined global variable for an empty function object in the
  device code, `reproducers/nvhpc-openacc-managed-global`): the
  `openacc-nvhpc-gpu` configuration uses `-gpu=mem:unified` (HMM).
- The `stlpar` backend also serves the GPU with `nvc++ -stdpar=gpu`. The
  libraries linked to TBB (gcc, clang, icpx) stay loaded until the end of
  the process (`-Wl,-z,nodelete`): the TBB threads were still running when
  the libraries were unloaded at exit.

### Execution policies

The data of a batch end with two members, shared by behaviours, models and
material properties: `statistics` (optional, see
[Synchronous and asynchronous](#synchronous-and-asynchronous)) and
`execution_policy`, a pointer to an execution policy of the backend. A null
pointer selects the default policy of the backend (default stream, default
instance or resource); the `sycl` backend has none.

The policies are C++ classes of `mfront::generic_parallel`, one per backend,
in `MFront/GenericParallel/`. They derive from
`AbstractBackendExecutionPolicy`, defined by the `MFrontGenericParallelRuntime`
library, whose virtual method `getIdentifier` gives their identifier. The
generated function compares it with the identifier of its backend, then
converts the policy by `static_cast`. A policy of another backend is refused
(`-5`). Each library exports the identifier it expects
(`<name>_generic_parallel_execution_policy`), next to its backend and its
memory space. The identifiers are constant expressions, so that this symbol
is initialized statically as the two others, except with Kokkos (the name of
an execution space is not always a constant expression): it is then
initialized when the library is loaded.

| Backend | Policy | Identifier | Member |
|---|---|---|---|
| `cuda`, `hip` | `CUDABackendExecutionPolicy`, `HIPBackendExecutionPolicy` | `cuda`, `hip` | `stream` |
| `sycl` | `SyclBackendExecutionPolicy` | `sycl:oneapi`, `sycl:acpp` | `queue` (required) |
| `kokkos` | `KokkosBackendExecutionPolicy<ExecutionSpace>` | `kokkos:` and the name of the execution space | `execution_space` |
| `raja` | `RAJABackendExecutionPolicy<Resource>` | `raja:host`, `raja:cuda`, `raja:hip` | `resource` (camp) |
| `arcane` | `ArcaneBackendExecutionPolicy` | `arcane:cuda`, `arcane:hip`, `arcane:host` (accelerator mode of Arccore) | `queue` (required) |
| `stlpar`, `openmp`, `openacc` | `ParallelSTLBackendExecutionPolicy`, ... | `stlpar`, `openmp`, `openacc` | none |

All the policies have the common options `preserve_stack_size` (the stack
size of the GPU threads is never modified, an error is reported if it is
too small) and `asynchronous`, and are created by `make...` functions taking
an aggregate:

```cpp
const auto p = mfront::generic_parallel::makeCUDABackendExecutionPolicy(
    {.common_options = {.asynchronous = true}, .stream = stream});
```

`getIdentifier` is declared before the destructor: its place in the table of
virtual functions is the same with the ABIs of Visual Studio and of gcc,
clang and MinGW (checked by `reproducers/execution-policies`). The generated
libraries do not need `MFrontGenericParallelRuntime`; the codes creating
policies link it. The generated function copies what it needs: the policy
does not have to outlive the call.

An empty batch is accepted without any check: nothing is read, written or
submitted, the fields and the policy may be null. The rule is the same for
material properties.

### Memory space

Each library declares where its computations read the data. The value is
fixed at compile time, from the backend, the compiler and the memory mode
(`MFront/GenericParallel/MemorySpace.hxx`).

| Backend and compilation | Memory space |
|---|---|
| `cuda`, `hip` | `device` |
| `stlpar`, `openmp` on the host | `host` |
| `nvc++ -stdpar=gpu`, `nvc++ -mp=gpu`, `nvc++ -acc=gpu` | `device`, or `any` with unified memory |
| `openacc` with `nvc++ -acc=multicore` | `host` |
| `openacc` with other compilers | `device` |
| `kokkos` | `host` if the execution space accesses host memory, `device` otherwise |
| `raja` | `device` for the policies of CUDA and HIP, `host` otherwise |
| `sycl` | `any` with automatic transfers, `device` otherwise |
| `arcane` | `device` (device of the queue, known at run time) |

`device` means that the computations cannot read the ordinary memory of the
host. The data must be on the GPU or in shared memory. `any` means that any
data is suitable. The caller does not need to know the list of backends:
this symbol is enough.

### Errors and statuses

The function of a batch returns a status, also written in the output
structure (`mfront_gpb_OutputStatus`):

| Status | Meaning |
|---|---|
| `1` | success at all points |
| `0` | success, but the time step factor is lower than 0.99 at some points |
| `-1` | failure of the computation at some points |
| `-5` | invalid arguments, nothing is computed |
| `-6` | invalid parameters (parameters file which can't be read), nothing is computed |
| `-7` | backend error (allocation, launch of a kernel, exception on the host) |

These errors of the batch are the ones of the material properties. In
case of failure, the structure gives the number of failed points and
**the index of the first one**, and also the number of unreliable points
(time step factor lower than 0.99) and the index of the first one. The
statistics hold opaque keys (index of the point on 48 bits), decoded by
the report function of the library. This index does not depend on the order of
the computations (atomic minimum or reduction). An optional array gives the
status of each point.

The detailed error message of a point is not transmitted: GPU code has
neither exceptions nor a message buffer per thread. To obtain it, the point
is replayed with the `generic` library of the same behaviour.

**With atomic operations, error reporting costs nothing in case of
success.** The kernels write into the statistics only if an event occurs
at a point. On CUDA and HIP, a warp vote avoids any atomic operation in the
warps without an event. In synchronous mode, the `cuda`, `hip`, `sycl`,
`kokkos`, `raja` and `arcane` backends keep the statistics in memory blocks
accessible
by the host and the GPU, allocated at the first call and then reused
(`MFront/GenericParallel/StatusBlockPool.hxx`). The `stlpar`, `openmp` and
`openacc` backends merge the statuses of the points by a reduction: its
result, a few integers, is copied to the host at each call. The host
initialises a block and reads it after the synchronisation: without an
event, no data goes between the host and the GPU. Measurement, on an elastic
behaviour and 1000 points: the synchronous CUDA call goes from 135 to 29 µs.

### Synchronous and asynchronous

The two notions are independent.

- **Statistics**: if the caller gives none, the status describes the result.
  If it gives some, they are accumulated in this structure, which must be
  accessible by the GPU (and by the host for `stlpar`, `openmp` and
  `openacc`, which accumulate on the host), and the status only reports the
  errors of the batch. `<behaviour>_generic_parallel_report`, exported by the
  library, then fills the output status as a synchronous computation does,
  message included, as for the material properties.
- **Asynchronous** (`asynchronous` option of the policy): the `cuda`, `hip`,
  `kokkos`, `raja`, `arcane` and `sycl` (without copy, in-order queue)
  backends return
  as soon as the computation is submitted, and the caller synchronises the
  queue before the report. An asynchronous computation requires statistics
  (`-5` otherwise). The other backends compute synchronously. Without this
  option, the function returns once the computation is finished, even with
  statistics.

Several batches and the assembly can thus be submitted before a single
synchronisation.

### Stack of the GPU threads

Some behaviours require a larger stack than the default value of NVIDIA
GPUs (1 KB). The `cuda` and `hip` backends compute the required size from
the attributes of the kernel
(`MFront/GenericParallel/GPUStackSize.hxx`). Kokkos, RAJA and Arcane use a
probe kernel that is never launched
(`MFront/GenericParallel/KokkosStackSize.hxx`,
`MFront/GenericParallel/RAJAExecutionPolicy.hxx`,
`MFront/GenericParallel/ArcaneUtilities.hxx`). These headers serve
behaviours and material properties. `nvc++` and
AdaptiveCpp give no access to this size: the `device_stack_size` option
sets it through the CUDA runtime loaded in the process
(`MFront/GenericParallel/DeviceStackSize.hxx`). The stack size is common to
all the computations of the process: `preserve_stack_size` makes it
possible to forbid changing it.

The kernel is a template parameter of the function that reads its
attributes. The CUDA runtime is linked statically by default: each library
has its own instance, which only knows its own kernels. A shared function
that took the kernel as an argument would be resolved by the dynamic
linker to the instance of a single library, and the kernel of another
library would be unknown there (`invalid resource handle`). The CUDA test
of material properties, which loads three libraries, showed it.

### Coverage

The interface covers everything the `generic` interface can do:

- small strain behaviours and general behaviours (thermal, cohesive
  zones);
- finite strain, including the Green-Lagrange and Hencky strategies and the
  conversions of the tangent operator;
- initialize functions and post-processings;
- rotations of orthotropic behaviours: gradients, thermodynamic forces and
  all the blocks of the tangent operator, through a module shared with the
  `generic` interface (`MFront/BehaviourRotationFunctions.hxx`);
- single crystals (slip systems and interaction matrices built at compile
  time);
- behaviour variables and their parameters, the
  `StandardElastoViscoPlasticity` brick, the TDLS linear solver in implicit
  behaviours;
- data shared by all points (`@SharedData`, see
  [GPU code](#gpu-code-in-tfel-and-mfront));
- standalone models: they are treated as behaviours without gradients, as
  by the `generic` interface. A library of models exports the same
  functions and symbols as a library of behaviours.

## Generic-parallel interface of material properties

This interface existed in TFEL. It evaluates a material property on a set
of points. The prototype extends it so that it offers the same
possibilities as the one of behaviours, and gives it the interface planned
for TFEL 5.2 (version 3 of the functions, `MFRONT_GPMP_API_VERSION`).

### What changed

- **Backends**: `kokkos`, `raja`, `openmp`, `openacc` and `arcane` added to
  the existing backends (`cuda`, `hip`, `stlpar`, `sycl`).
- **Properties defined by data or calling other material laws**: usable on
  CUDA and HIP.
- **One function per material property `S`**:
  `int S_generic_parallel(mfront_gpmp_OutputStatus*, const mfront_gpmp_BatchData*)`.
  The data of the batch give the number of points, the output and the
  arguments (pointer and stride), the out-of-bounds policy, the optional
  statuses of the points, the statistics and the execution policy. The function with
  contiguous arrays (suffix `2`) is removed. The names end with
  `_generic_parallel`, and the name of a material property can't contain
  this suffix. Without the `generic_functions` option (see
  [Interfaces built on the generic interfaces](#interfaces-built-on-the-generic-interfaces)),
  such a library has no function `S` of the `generic` interface. Its
  functions of batches are always recognized by the symbol
  `S_generic_parallel_api_version`. The SYCL queue, an argument specific to
  this backend inserted in the middle of the others, goes through the
  execution policy: the signature is the same everywhere.
- **Same evaluation as `generic` at each point**: same checks, same status
  at each point (`0`, `1`, `-1`, `-4`, written in the optional array of the
  statuses), same retained check (first failure, otherwise last warning).
  The output is `NaN` where the evaluation fails, the computed value where
  it is not finite.
- **Output status and statistics modelled on behaviours.** The output
  status (`mfront_gpmp_OutputStatus`) gives the numbers of failed points
  and of points out of their bounds with the `Warning` policy, and the
  first point of each kind. Its status is the error of the batch, otherwise
  the status of the first failed point, otherwise the status of the first
  unreliable point. The statistics (`mfront_gpmp_Statistics`) hold two
  opaque keys (index of the point and retained check), decoded only by the
  report function of the library. Each kernel merges the status of its
  point only when an event occurs: atomic operations for CUDA, HIP, SYCL,
  Kokkos, RAJA and Arcane, reduction for the parallel algorithms, OpenMP
  and OpenACC, as for behaviours.
- **Errors of the batch** shared by the three types of objects: `-5`
  (invalid arguments), `-6` (invalid parameters), `-7` (runtime error of
  the backend, including an exception of its runtime on the host). An
  empty batch is accepted without check. `errno` is restored at each
  return.
- **Statistics given**: on all the backends, the output status only
  reports the errors of the batch, and the report function
  `S_generic_parallel_report` gives the result once the computations are
  finished. The backends with a queue may return as soon as the
  computation is submitted. The synchronous evaluation calls the same
  function: the analysis is written only once.
- **Stack of the threads**: CUDA, HIP, Kokkos, RAJA and Arcane adapt it to the
  kernel, with the headers of behaviours. `preserve_stack_size` therefore
  has the same effect everywhere.
- **SYCL transfers**: the copy class of behaviours
  (`MFront/GenericParallel/SYCLDeviceCopies.hxx`) also serves material
  properties. The statuses of the points and the statistics are copied if
  needed. The output is copied in both directions: the values between two
  values of a strided output are kept. A USM allocation of any type is
  accessible, as for behaviours. The errors of the kernel are propagated
  (`wait_and_throw`).
- **Number of points**: type `size_t` in the CUDA, HIP and Kokkos kernels
  and with AdaptiveCpp, at most 2^48 - 1 points (the index is stored in the
  keys of the statistics).
- **Symbols**: backend, version of the functions, memory space, as for
  behaviours.
- **Reused blocks**: the statistics of a synchronous evaluation come from a
  pool of blocks, without allocation per call; waiting on the stream
  instead of the whole GPU (CUDA, HIP); waiting on the instance used
  instead of the whole of Kokkos.

Deliberate differences with the `generic` interface: no status `-2` or
`-3` at a point (no exception, no `errno` in device code), a null rank of
the variable for `-4`, a message without the values, no MTest file.

### Tests

The tests of the semantics are written once
(`test-suite/material-properties/generic-parallel/tests.hxx`) and shared by
the backends whose arrays are accessible by the host; each backend adds its
own tests (queues, asynchronous evaluation, stack, memory of the device). A
comparator (`compare.cxx`) evaluates each test material property with the
`generic` interface at each point and with the batch, for the three
policies, contiguous, strided and uniform values, synchronous and
asynchronous evaluations: values, statuses of the points and summary. The
values are compared exactly with `g++`, `clang++` and `nvc++` on the host,
up to 1e-13 with `icpx` and on GPUs.
A test property with bounds and physical bounds on two arguments and on
its output (`BoundsOrderTest`) checks the retained check: first failure,
otherwise last warning, rank of the output after the arguments. The
property generated with the runtime checks disabled is run on the four
backends of TFEL master (`stlpar`, `cuda`, `hip`, `sycl`) and on `openmp`
and `openacc`. The error reported for an invalid file of parameters
(`-6`), the limit of the grid of the CUDA and HIP kernels (`-5` beyond
2^31 - 1 blocks) and the refusal of a name containing `_generic_parallel`
are also checked.

One difference with the `generic` interface remains open. A material
property calling another one (`@MaterialLaw`) uses, in device code, the
implementation of the called property of the `mfront::device` namespace.
This implementation returns `NaN` outside the physical bounds of the called
property, whereas the `generic` interface does not check them: on a device,
the evaluation then fails with the status `-4`. The comparison of this test
property keeps the temperatures in the physical bounds. A check on the
side of the caller for the material laws is proposed for TFEL 6.0.

## Comparison between behaviours and material properties

| | Behaviours and models | Material properties |
|---|---|---|
| Call | batch structure | batch structure |
| Execution options | queue, statistics, stack | same members |
| Synchronous or asynchronous | `asynchronous` option of the execution policy | identical |
| Execution policy | `execution_policy` member, one class per backend | identical |
| Asynchronous report | `<name>_generic_parallel_report` (symbol, it decodes the keys) | `<name>_generic_parallel_report` (symbol, it decodes the keys and names the variable) |
| Empty batch | accepted without check | accepted without check |
| Errors of the batch | `-5` (arguments), `-6` (parameters), `-7` (backend) | identical |
| Automatic SYCL transfers | `SYCLDeviceCopies.hxx` | same class |
| Merge of the statuses of the points | atomic (CUDA, HIP, SYCL, Kokkos, RAJA, Arcane), reduction (parallel algorithms, OpenMP, OpenACC) | identical |
| Number of failed points, first failed point | yes, and first unreliable point | identical |
| Stack of the threads | adapted to the kernel, `preserve_stack_size` | identical |
| Memory space, backend, version | exported symbols | exported symbols |
| Optional array of the statuses per point | yes | yes |

The statistics of the behaviours carry the time step factor after the
members shared with the material properties; the output status of the
material properties carries the check retained at the reported point.

## Interfaces built on the generic interfaces

The three `generic-parallel` interfaces are built on their `generic`
interface, so that the code at one point is written once:

- material properties: the code evaluating a material property at a
  point (order of the checks, out of bounds policies, macro disabling the
  bounds checks, body) is written by
  `GenericMaterialPropertyInterfaceBase::writePointEvaluation`, used by the
  `generic`, `cyrano` and `generic-parallel` interfaces. Each one reports
  the checks in its own way: messages with the values for `generic` and
  `cyrano`, identifiers of the checks in the kernels. The statuses, the
  messages and the values of `generic` and `cyrano` are unchanged. A
  differential test compares the libraries generated before and after the
  change: about 740 000 calls on 60 material properties, with the three
  policies, values below, on and above each bound, `NaN`, a wrong number
  of arguments and an invalid file of parameters. It finds no
  difference;
- models: `GenericParallelModelInterface` derives from
  `GenericModelInterface`, whose model class is generated for the device;
- behaviours: as before, `GenericParallelBehaviourInterface` derives from
  `GenericBehaviourInterface`; the functions of the `generic` interface
  are written by `writeGenericFunctions`, whose options select the files,
  the symbols and the linkage of the out of bounds policy. The sources
  generated by the `generic` interface for the behaviours and the models
  are unchanged (compared byte for byte on about 1450 files, apart from
  the paths of TDLS, which differ between the two builds compared).

With the `generic_functions` option of the interface (configuration
file: `interfaces_options: {generic-parallel: {generic_functions: true}}`),
a library also contains the functions of the `generic` interface and
exports `Generic` as interface. It can be used as a library of the
`generic` interface (MTest, MGIS). Its functions of batches are detected
by `<name>_generic_parallel_api_version`. It has one set of parameters
shared by all its functions and, for a behaviour, one out of bounds
policy (for a material property, the policy is an argument of each call).
They have a hidden visibility, so that libraries of several backends
loaded in the same process stay independent. The functions of a point of
the material properties and of the behaviours are written in a separate
source. This source is compiled by the C++ compiler of the configuration:
the compiler of the backend for the backends based on C++ programming
models, the C++ compiler for CUDA and HIP. The functions of a point of
the models are written in the source of the batch functions. The
behaviour class then has the constructors of both interfaces
(`AbstractBehaviourInterface::getInterfacesOfAdditionalBehaviourConstructors`).
Limits: with the compilers translating host and device code in a single
pass (nvc++ for the GPU, generic compiler of AdaptiveCpp), the functions
of a point follow the rules of device code; `errno` is set by the
mathematical functions with `icpx` only with `-fp-model=precise` (given by
its configuration files) and with `nvc++` only with `-Mnobuiltin` (not
given).

## GPU code in TFEL and MFront

Code run on GPU has no exceptions, no virtual functions called on objects
created by the host, and no access to the global variables of the host. The
following changes make TFEL and the generated code compatible, without
changing the results on CPU.

- **Annotations.** The mathematical and material headers are annotated
  (`TFEL_HOST_DEVICE`). Each header is compiled with clang CUDA, which
  refuses any call to a host function from GPU code
  (`scripts/clang-cuda-header-scan.sh`).
- **GPU code and single-pass compilers.** `TFEL_DEVICE_CODE` is defined
  when GPU code is compiled. Single-pass compilers (`nvc++`, AdaptiveCpp)
  define it in the whole compilation unit: only the `generic-parallel`
  libraries they compile then follow the rules of GPU code on the host.
- **Behaviours without virtual functions.** `MechanicalBehaviour` no longer
  declares the interface of behaviours as pure virtual functions. The
  virtual table requires run-time type information, absent from GPU code.
  The generated code did not use it.
- **Trivially copyable types.** The tangent operator of finite strain
  behaviours uses `TrivialGenTypeBase` instead of `std::variant`, whose
  visitation is not supported by `nvc++` in GPU code.
- **Constant data.** The data built at compile time (slip systems) go
  through `tfel::utilities::getConstantObject`. nvcc fills the static
  variables of functions with zeros in GPU code.
- **Eigenvalues** without recursion or assertion in GPU code (Jacobi
  algorithm for multiple eigenvalues).
- **Cubic splines**: iterators advanced without `std::advance`, `std::next`
  and `std::prev`, which nvcc compiles into empty functions in GPU code.
- **Portable errors.** `tfel::fail<Exception>(message)` throws the
  exception on the host and returns `false` on the GPU. `abortResolution`
  (implicit DSLs) and `abortIntegration` (Runge-Kutta) stop the integration
  of a point. The 36 test behaviours whose user code was not usable on GPU
  were made portable with these tools, without changing their results.
- **Shared data** (`@SharedData`). Data common to all points, for example
  the orientations of a polycrystal read from a file, are computed on the
  host then copied once per GPU and per context.
- **Parameters of behaviour variables.** The values of the parameters are
  read on the host and passed by value to the kernels
  (`mfront_parameters_values`).
- **Material laws called by behaviours**: an implementation in the
  namespace `mfront::device`, generated in the header of the `mfront`
  interface of material properties.
- **Same behaviour class on the host and the GPU**, and comparison with the
  numerical jacobian done only on the host.
- **Static variables.** MFront writes a static variable
  (`@StaticVariable`, `@IntegerConstant`, numbers of slip systems)
  `TFEL_STATIC_VARIABLE(v)`, in the code blocks and in the inputs of
  material properties. This macro of `TFELConfig.hxx` gives the variable
  itself in host code, which therefore does not change, and a copy
  initialised by a constant expression, `(decltype(v){v})`, in GPU code
  (`TFEL_DEVICE_CODE`). GPU code cannot refer to a constexpr static
  variable of the host, which is what an operator that takes its arguments
  by reference does in an expression evaluated at run time, for example
  `T + dT - Tref` with quantities (`@UseQt true`, nvcc: "identifier is
  undefined in device code"). The Runge-Kutta algorithms also write this
  way the stiffness recomputed at the intermediate stages and the
  constants of rkCastem. Reproducer: `reproducers/mfront-static-quantity-cuda`;
  test behaviour `StrainHardeningCreep3`.

## Incompatibilities

The support of GPU code changes a few programming interfaces. The list is
in the release notes of TFEL (`tfel/docs/web/release-notes/release-notes-5.2.md`, section
"Known incompatibilities"): `MechanicalBehaviour` without virtual
functions, functions of `BoundsCheck`, `LogarithmicStrainHandler` defined
in its header, slip systems built at compile time. The functions of
`generic-parallel` material properties, new in TFEL 5.2, differ from those
of the master (version 3, see
[above](#generic-parallel-interface-of-material-properties)). Those of the
behaviours and of the models, absent from the master, changed in the
prototype on 21/10 (version 3 of `BatchData.h`). Their names are followed
by `_generic_parallel`. The statistics hold opaque keys:
`mfront_gpb_BatchStatistics` becomes `mfront_gpb_Statistics`, and
`mfront_gpb_initializeBatchStatistics` becomes
`mfront_gpb_initializeStatistics`. `mfront_gpb_getStatus` is removed. The `statuses` come
after `s1` in the data of a batch. The report function is exported by the
library instead of `mfront_gpb_report`. The errors of the batch are `-5`,
`-6` and `-7` instead of `-2` and `-3`. The configuration files of `icpx`
request `-fp-model=precise`.

## Single precision

The behaviours, models and material properties of the `generic` and
`generic-parallel` interfaces can be generated in `float` with the DSL
option `real_type` (`double` by default), which writes the macros
`MFRONT_GB_REAL_TYPE` and `MFRONT_GMP_REAL_TYPE` at the top of the
sources. Each function exports the symbol `<f>_real_size`, and the API
versions are shifted by 1000 for a type other than `double`: an older
caller refuses the library instead of misreading it. The other interfaces
and the models of the `Model` DSL refuse `float`. `IsAssignableTo` accepts
the assignment of a floating-point type to a narrower one. MTest refuses a
behaviour that is not in `double`. In `float`, the convergence criteria
are bounded at generation time, with a warning, and MFront warns when the
criterion of a behaviour is looser than 1e-5. In double, the generated
code only changes by the size symbol. The choices (decisions D1 to D9) and
the measurements are in [plan-precision.md](plan-precision.md); patches
0109 to 0117.
