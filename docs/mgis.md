# MGIS: technical details

This document describes what the prototype changes in MGIS, and why. MGIS
loads the libraries generated by MFront and manages the material data
(`MaterialDataManager`). The prototype teaches it to use the libraries of
the `generic-parallel` interface: behaviours, models and material
properties computed by batches, on CPU or on GPU.

- Base: MGIS master `a30dbf5` (20/10/2026; branch of the prototype rebased on this version, previously on `e8ef4b4` of 13/10/2026, started from `818f0f9` of 02/10/2026).
- Modified sources: repository `mgis/`, branch `gpu-proto`. Patch series:
  `patches/mgis/` (`git am`).
- The documentation of the API, in English, is in the MGIS tree (see
  [the last section](#documentation-in-the-mgis-tree)).

## What changes, in short

- MGIS recognises a `generic-parallel` library at loading time and checks
  its compatibility.
- The existing functions (`integrate`, `executeInitializeFunction`,
  `executePostProcessing`, rotations) switch by themselves to batch
  computation. The calling code does not change.
- Each batch function also exists with an execution policy, which chooses
  the queue (CUDA stream, SYCL queue, etc.). The computation is synchronous
  by default, asynchronous with an asynchronous policy.
- The data are never copied: the batch is described directly on the arrays
  of the `MaterialDataManager`.
- The arrays can be laid out component by component, or belong to the
  caller and be described by views with arbitrary strides, on GPU
  included. The end of the time step is then done on the GPU (see
  [Views and layouts](#views-and-layouts)).
- The caller declares where its arrays are. MGIS checks that they are
  accessible by the computations of the library.
- MGIS does not depend on any GPU library. The arrays come from the caller,
  or from a memory resource it provides.
- Profiling: `setProfilingSynchronization` gives a function called at the
  beginning and at the end of each active timed section, before reading
  the time. The computations launched asynchronously, for example on a
  GPU, are then counted in the section that launches them. No default
  function.

## Loading

When a behaviour is loaded (`mgis::behaviour::load`), MGIS reads the
description symbols of the library and makes two independent tests, as
for the material properties. The functions of batches exist if the library
exports `<name>_generic_parallel_api_version`: version 3 of the data
contract is checked, the backend and the memory space are read (member
`batch_api_version`). The functions of a point exist if the library
exports `Generic` as interface. They are stored in the description of the
behaviour (`interface`, `backend`, `memory_space`, `batch_api_version`).
`isGenericParallelBehaviour` tells whether a behaviour has the functions
of batches. A library of the `generic-parallel` interface built with the
`generic_functions` option has both: both are loaded, the functions of a
point being used by the functions acting on one point and the functions of
batches by the functions acting on a material data manager. A library with
none of them is refused.

MGIS keeps its own copy of the C structures of TFEL
(`MGIS/Behaviour/BatchDataView.hxx`), as for the `generic` interface: it
does not depend on TFEL at compile time. A test checks that the offset of
each member of these copies is the one of TFEL. The report function of the
library (`<name>_generic_parallel_report`, member `batch_report`) analyses
the statistics of asynchronous computations: MGIS no longer decodes them.

Before this work, a `generic-parallel` library was loaded without error.
Its batch functions were then called with the arguments of one point:
undefined behaviour. Now, each access of the `LibrariesManager` refuses the
other kind of library with a clear message.

## Integration of a batch

```cpp
auto r = integrate(policy, m, opts, dt);        // all points
auto r = integrate(policy, m, opts, dt, b, e);  // points [b, e)
```

The version without a policy (`integrate(m, opts, dt)`) uses the policy of
the manager (`m.batch_execution_policy`). The versions with a `ThreadPool`
make a single batch call: the parallelism is the one of the backend.

Mapping of the data:

- the gradients, the thermodynamic forces, the internal state variables and
  the energies are fields laid out point by point;
- the material properties and the external state variables are given
  variable by variable: each one is uniform or given per point, as in the
  `MaterialStateManager`;
- the mass density is passed only if the speed of sound is requested: it is
  the only one to use it.

Difference with the point by point computation: all points are integrated,
even if some fail. The result gives the absolute index of the first failed
point (`n`) and the number of failures in the message.

## Initialize functions, post-processings, rotations

They follow the same model as the integration:

```cpp
executeInitializeFunction(policy, m, name[, inputs][, b, e]);
executePostProcessing(outputs, policy, m, name[, b, e]);
rotateGradients(policy, dest, behaviour, src, r[, location]);  // and the other rotations
```

The versions without a policy switch by themselves. For rotations, the
matrices can be given per point or uniform. The `RotationMatrix2D` and
`RotationMatrix3D` forms build the matrices on the host at each call: for
repeated rotations on GPU, it is better to build them once with
`buildRotationMatrices`, in a shared memory given by a resource, and to
give them as an array. A rotation is done in place if the source and the
destination are the same array.

The inputs of the initialize functions and the outputs of the
post-processings must be placed like the arrays of the manager.
`allocatePostProcessingVariables` allocates them on the host (and refuses a
behaviour that does not read host memory), or with a given resource. The
rotations, with or without a policy, take the location of their arrays as
last argument (`HOST` by default), like `evaluate`. A null resource
designates everywhere the default resource of the standard library.

## Models

The `generic-parallel` interface of models exports the same symbols as the
one of behaviours. `mgis::model::load` goes through the loading of
behaviours: a `generic-parallel` model is therefore used exactly like a
behaviour, with the same batch functions and the same parameters
(`setParameter`).

## Material properties

```cpp
const auto mp = mgis::material_property::load(library, "YoungModulus");
const auto inputs = std::array{std::span<const real>(temperatures)};
auto r = evaluate(values, mp, inputs);                    // default queue
auto r = evaluate(policy, values, mp, inputs, location);  // chosen queue
```

At loading time, MGIS makes two independent tests. If the library exports
the version of the functions of batches of points
(`<name>_generic_parallel_api_version`, version 3), MGIS checks it, reads
the backend and the memory space, and loads the function for a batch of
points (`batch_fct`) and the report function of the statistics
(`batch_report_fct`). If the property comes from the `generic` interface,
MGIS loads the function for one point (`fct`). A library with none of
these functions is refused. The structures of the functions of batches
(`mgis_mp_BatchData`, `mgis_mp_BatchOutputStatus`, etc.) are copies of
those of TFEL, checked member by member by a test.

`evaluate` evaluates a property on a batch of points. Each input is uniform
(one value) or given per point. Like `integrate`, `evaluate` makes a single
call for a `generic-parallel` property and computes point by point on the
host otherwise.

The result (`MaterialPropertyEvaluationResult`) is the same for both
interfaces, like `BehaviourIntegrationResult` for behaviours: status and
rank of the out-of-bounds variable (meaning of the `generic` interface),
index of the first failed point, message. For a `generic-parallel`
property, the message also gives the reported point and the numbers of
failed points and of unreliable results. Such a property only returns the
statuses `1`, `0`, `-1` and `-4`. The errors of the batch (`-5` invalid
arguments, `-6` invalid parameters, `-7` backend error) throw an
exception, at submission time for an asynchronous evaluation. The point by
point computation stops at the first failure, the batch computes all
points (`NaN` where a bound makes the evaluation fail): the reported index,
status and rank are the same, except that the rank is null for a result
which is not finite (`-4`). Without failure, they describe the first point
where the result is unreliable.

## Memory

### Location of the arrays and memory space

The caller declares the location of its arrays (`mgis::MemoryLocation`):

- `HOST`: ordinary memory of the host;
- `DEVICE`: memory of a GPU, which the host cannot read;
- `SHARED`: memory readable by both (CUDA or HIP managed memory, SYCL
  shared memory, `Kokkos::SharedSpace`).

For a `MaterialDataManager`, the location is given by its initializer
(`MaterialDataManagerInitializer::location`). The values given by a
`std::span` (external storage) and the arrays passed to the batch
functions of the manager must have the same location. For a material
property and for a rotation, the location is an argument.

MGIS compares this location with the memory space of the library, exported
by TFEL (`isMemoryLocationAccessible`):

| Memory space of the library | `HOST` | `DEVICE` | `SHARED` |
|---|---|---|---|
| `host` (and `generic` libraries) | yes | no | yes |
| `device` | no | yes | yes |
| `any` | yes | yes | yes |

MGIS therefore knows no list of backends. A new backend of TFEL needs no
change in MGIS.

### Functions that read the arrays on the host

Some functions of MGIS read the arrays on the host: `update`, `revert` and
`updateValues` without copy operations (`FieldOperations`, see
[Views and layouts](#views-and-layouts)), the extraction of internal state
variables, `save`, `restore`, the finite strain conversions and the point
by point computation. They refuse arrays placed on a GPU instead of
crashing.

Likewise, the values kept by MGIS itself (uniform value, local storage
`LOCAL_STORAGE`) are in host memory. They are refused when the
computations cannot read this memory. They must then be given by a
`std::span` on an accessible memory, as external storage. A uniform value
can be given by a `std::span` of a single value.

### Memory resources

A `MaterialDataManager` itself allocates the arrays that its initializer
does not give. By default, it allocates them on the host. The initializer
can now give a standard memory resource (`std::pmr::memory_resource*`):
MGIS then allocates with it. MGIS initialises these arrays on the host: the
resource must therefore allocate memory readable by the host, that is,
shared memory. If the arrays are on a GPU only, the caller gives all of
them.

MGIS provides five resources, as headers that the calling code compiles
with its own GPU tool (`MGIS/MemoryResources/`):

| Header | Memory |
|---|---|
| `CUDAManagedMemoryResource.hxx` | CUDA managed memory |
| `HIPManagedMemoryResource.hxx` | HIP managed memory |
| `SYCLSharedMemoryResource.hxx` | SYCL shared memory, of a given queue |
| `KokkosSharedSpaceMemoryResource.hxx` | `Kokkos::SharedSpace` |
| `RAJAManagedMemoryResource.hxx` | managed memory of a resource of camp (RAJA) |
| `ArcaneUnifiedMemoryResource.hxx` | unified memory of Arccore (Arcane), accessible by all the queues |

Cost: one pointer per array and one virtual call per allocation. Nothing
per computation.

## Execution policy

`mgis::BatchExecutionPolicy` is common to behaviours, models and material
properties:

- `backend_policy`: pointer to an execution policy of the backend of the
  library, defined by TFEL (`MFront/GenericParallel/`, for instance
  `CUDABackendExecutionPolicy` holding a stream, see the TFEL part). It
  carries the queue and the common options `preserve_stack_size` and
  `asynchronous`. Null designates the default policy of the backend. The
  description of a library gives the identifier of the policy it expects
  (`execution_policy`, read by
  `LibrariesManager::getGenericParallelExecutionPolicy`).

MGIS only forwards the pointer: a declaration of the class is enough
(`MGIS/BackendExecutionPolicy.h`) and MGIS still builds without TFEL. The
codes creating policies include the headers of TFEL and link
`MFrontGenericParallelRuntime`.

With this policy, the computation is synchronous: the function returns
once the computation is finished. This is the default. A backend policy
requesting an asynchronous computation is refused by the library, since
the statistics are only allocated by the asynchronous functions.

The functions without a policy use the one of the manager
(`batch_execution_policy`), or a default policy for rotations and material
properties. The backend policy it points to must stay valid as long as the
manager refers to it. SYCL has no default policy: a policy holding a queue
must then be passed, or given to the manager.

## Asynchronous computation

Each batch function also exists with an asynchronous policy
(`mgis::AsynchronousBatchExecutionPolicy`): integration, initialize
functions, post-processings, rotations, evaluation of material properties.
Nothing changes for the code that does not use it.

```cpp
const auto cuda = mfront::generic_parallel::makeCUDABackendExecutionPolicy(
    {.common_options = {.asynchronous = true}, .stream = stream});
auto p = AsynchronousBatchExecutionPolicy{};
p.backend_policy = &cuda;
p.resource = &resource;  // managed memory
p.location = MemoryLocation::SHARED;
const auto pending = integrate(p, m, opts, dt);
// ... other computations submitted to the stream, for example other materials
cudaStreamSynchronize(stream);
const auto r = pending.getResult();
```

- The function returns as soon as the computation is submitted if the
  backend policy requests it (`asynchronous` option), once it is finished
  otherwise (default policy, or backends computing synchronously). In both
  cases it returns a pending computation: `PendingBatchComputation` for
  behaviours and models, `PendingBatchEvaluation` for material properties.
- Once the queue is synchronised by the caller, `getResult` returns the
  result of the synchronous function, index of the first failed point
  included, given by the report function of the library (an asynchronous
  computation on a non empty batch requires it). MGIS cannot synchronise the queue itself: it does not depend on
  any GPU library.
- The pending computation keeps the memory written or read by the GPU: the
  status of the computation (statistics of behaviours, statuses of material
  properties) and, for rotations, the matrices built from the material
  axes. It must not be destroyed before the end of the computation. It can
  be moved (for example into a `std::optional` or a container), but not
  assigned: assignment would copy the status if the memory resources
  differed, while the GPU writes it.
- This status is initialised and read by the host, written by the GPU. The
  policy gives the memory resource that allocates it and its location.
  MGIS checks that it is accessible by both: host memory for computations
  on the host, shared memory otherwise.

The two modes share all the code, except how the status is obtained: in
synchronous mode, the generated function returns it; in asynchronous mode,
it is read from the statistics after the synchronisation. The result is
therefore the same.

The rotations from the material axes (`RotationMatrix2D`,
`RotationMatrix3D`) build the matrices in the memory allocated by the
resource of the policy. In asynchronous mode, they therefore also work for
a library that computes on the GPU, which the synchronous version refuses
(matrices built in host memory).

Each asynchronous call allocates its status with the resource of the
policy. With a managed memory resource, this means one `cudaMallocManaged`
and one `cudaFree` per call. The remedy is standard: a
`std::pmr::synchronized_pool_resource` on top of the managed resource,
which the documentation of MGIS recommends and which the tests use. The
resources of MGIS accept any alignment for this purpose (see
[Fixes of existing defects](#fixes-of-existing-defects)). With a pool,
destroying a pending computation before the end of the computation
corrupts the next call instead of only being slow.

## Views and layouts

A `MaterialDataManager` lays out its arrays point by point by default.
MFEM and GPU codes often own their arrays, laid out component by component
for coalescing. The prototype adds to MGIS an API on views, which
describes these arrays without copying them. TFEL did not have to change:
its contract already describes each field by two strides.

- **`FieldView`**: view on the values of a group of variables, with a
  stride between two points and a stride between two components. A zero
  point stride describes uniform values. Factories: `makeFieldView`,
  `makePointByPointFieldView`, `makeComponentByComponentFieldView`,
  `makeUniformFieldView`, `getComponents`. An output must have distinct
  values: MGIS checks it.
- **Layout of a manager**: `MaterialDataManagerInitializer::layout`
  (`POINT_BY_POINT` by default, or `COMPONENT_BY_COMPONENT`). Everything
  that is given per point to the manager follows this layout: states,
  blocks of the tangent operator, speed of sound, external state variables
  with several components, inputs of the initialize functions, outputs of
  the post-processings, of the extraction and of the finite strain
  conversions. `save` and `restore` always write point by point.
- **`MaterialDataView`**: the data of a material in the arrays of the
  caller. All the functions of the manager exist on a view. Those of the
  manager call those of the view: a single code path. Without a policy,
  they take a workspace (`BehaviourIntegrationWorkSpace`), one per thread.
  No `ThreadPool` on a view: CPU parallelism goes through the `openmp`,
  `openacc` and `stlpar` backends.
- **Rotations and material properties**: overloads on views. The overloads
  on arrays go through them.
- **End of time step on GPU**: `update`, `revert` and `updateValues` take
  copy operations (`FieldOperations`), just as allocations go through a
  `std::pmr::memory_resource`. MGIS knows which arrays to copy, the caller
  provides the copy. Headers for CUDA, HIP, SYCL, Kokkos, RAJA, OpenMP,
  OpenACC, Arccore (`ArcaneFieldOperations`, on a queue of Arccore) and the
  parallel algorithms of C++ (`ParallelSTLFieldOperations`,
  on the host or on an NVIDIA GPU with `nvc++ -stdpar=gpu`), compiled by the
  caller with its toolchain.
- **Unchecked view and update of the inputs only**: `make_unchecked_view`
  returns the view of a manager like `make_view`, without checking that
  the values kept on the host (uniform values, local storage, mass
  density) are accessible by the computations. The caller then replaces
  the views of the arrays by those of their copies on the GPU, and copies
  these values into an accessible memory. `updateInputValues` updates the
  material properties, the external state variables and the mass density
  of a state from another one, with the same procedure and the same
  policies as `updateValues`, without copying the arrays of the state
  (gradients, thermodynamic forces, internal state variables, energies):
  the caller copies them itself, for example on their copies on the GPU.
  `updateValues` now copies the arrays, then calls `updateInputValues`.
  mfem-mgis uses both for the data of the materials it keeps on the GPU.
- **`MaterialFunctionManager`**: constructor with an initializer. Laid out
  component by component, it returns *strided coalesced* views of
  `mgis::function`.
- **Bindings**: the layout is exposed in C, Fortran and Python (numpy
  arrays with the strides of the layout).
- **Cost**: the TFEL kernels are unchanged, only the computation of the
  addresses changes. Once the arrays are allocated, the synchronous
  functions that compute on points (integration, initialisation,
  post-processing, rotations, `evaluate`), `update` and `revert` no longer
  allocate anything on the heap in the calling thread, on a manager as on a
  view. A test checks it by counting the calls to `operator new`. The
  threads of the `stlpar` backend (TBB) allocate their own.
- **Failed points**: the blocks of the tangent operator at a point where
  the integration fails are unspecified, whatever the path.
- **Mass density**: required for the speed of sound of a `generic-parallel`
  behaviour (TFEL requires it), zero if absent point by point, as MGIS has
  always done.

The layout by element blocks (`byNODES` of the MFEM interpolators) is not
covered: it would require a third stride and an extended TFEL contract.
The MFEM kernels read the `byVDIM` layout, which the views cover.

The design, its variants set aside and the reviews are in
[history/design-views-mgis-2026-10-08.md](history/design-views-mgis-2026-10-08.md).

## Errors

MGIS distinguishes two cases, like TFEL:

- **a failure of the computation at a point** (non-convergence, physical
  bound) is a result: status `-1` in the result, with the index of the
  first failed point;
- **an invalid argument or a backend error** throws an exception. It is
  never taken for a failure of the computation.

The functions for one point (`integrate` on a view of one point,
`integrate_debug`, initialize functions and post-processings of one point,
rotations of one point, C bindings) refuse a library without the functions
of a point (a `generic-parallel` library built without the
`generic_functions` option) with a message. They used to call a null
pointer. The detailed diagnosis of a point is done with the `generic`
library of the same behaviour, or with the same library if it was built
with the `generic_functions` option.

## Fixes of existing defects

These defects were found along the way and fixed in separate commits:

- the axes of the rotation matrices were refused when their number of
  values was correct (inverted test), and the number of points was
  compared with a remainder instead of a quotient: no `RotationMatrix2D`
  nor `RotationMatrix3D` could be built;
- a material property could not be given by a `std::span` of a single
  value, although the evaluation already treated it as uniform;
- the failure of an initialize function or of a post-processing point by
  point did not set the status to `-1`;
- a uniform value of a material property in local storage is stored as a
  scalar, as for external state variables;
- the mass density can be given by a `std::span` of a single value;
- the HDF5 restoration of an external state variable with several
  components in local storage wrote outside its array (size of one point
  per component instead of all of them);
- the CUDA, HIP and Kokkos memory resources refused an alignment stricter
  than the one of their memory. A pool of the standard library requests
  blocks aligned on their size: it failed above 256 bytes. The alignment
  is now obtained by over-allocation;
- the initializer `MaterialDataManagerInitializer` had no constructor in
  Python;
- the error message of the rotations of the blocks of the tangent operator
  talked about thermodynamic forces.

- `MaterialAxisStorage` was not exported: copying a `RotationMatrix2D` or a
  `RotationMatrix3D` outside of MGIS did not link. Moreover, the copy of a
  locally stored axis pointed to the storage of the original;
- the Fortran bindings of the tangent operator returned an array of wrong
  shape as soon as the operator was not square (and, for a manager, with a
  first extent never set). They return the transpose of the operator, of
  shape `[gs, ths]` at each point, and refuse an operator that is not a
  single block;
- the Python binding read a strided numpy array (`a[::2]`) as if it were
  contiguous: it is now refused;
- `update` and `revert` of a manager allocated an execution context at
  each call.

## Current limitations

- **Layout by element blocks** not covered (see
  [Views and layouts](#views-and-layouts)).
- **No variant with `Context`**: the batch functions throw exceptions, like
  the other functions on a manager. mfem-mgis wraps them in `try`/`catch`
  blocks.
- **`MaterialFunctionManager`** builds its manager on the host. It is not
  used by mfem-mgis.
- **Continuous integration**: the `generic-parallel` tests of MGIS are
  built only if the TFEL found provides the interface. The official CI of
  MGIS uses TFEL master: they will only run there once the interface is
  integrated into TFEL. The tests on the host use the `stlpar` backend.
  The GPU tests are disabled by default: `cuda` backend
  (`enable-generic-parallel-cuda-tests`), `stlpar` backend compiled by
  `nvc++ -stdpar=gpu` (`enable-generic-parallel-stlpar-nvhpc-gpu-tests`,
  same tests, libraries and tests compiled by nvc++ whatever the compiler
  of MGIS). The other backends are tested in TFEL: MGIS only passes
  pointers, a queue and a memory space.
- **No status per point**: the optional array of TFEL is not exposed.
- **Bindings**: the C bindings refuse the libraries without the functions
  of a point; the Python and Fortran bindings do not know the batch
  functions. All three expose the layout of the managers, not the views.

## Example

A behaviour compiled for CUDA, data in managed memory allocated by MGIS, a
CUDA stream chosen by the caller:

```cpp
#include "MGIS/Behaviour/Behaviour.hxx"
#include "MGIS/Behaviour/MaterialDataManager.hxx"
#include "MGIS/Behaviour/Integrate.hxx"
#include "MGIS/MemoryResources/CUDAManagedMemoryResource.hxx"

using namespace mgis::behaviour;
auto resource = mgis::memory_resources::CUDAManagedMemoryResource{};
const auto b = load("libBehaviour-cuda.so", "Norton",
                    Hypothesis::TRIDIMENSIONAL);
auto i = MaterialDataManagerInitializer{};
i.location = MemoryLocation::SHARED;
i.resource = &resource;
auto m = MaterialDataManager(b, n, i);
// uniform temperature, in a memory readable by the GPU
setExternalStateVariable(m.s0, "Temperature", temperature,
                         MaterialStateManager::EXTERNAL_STORAGE);
setExternalStateVariable(m.s1, "Temperature", temperature,
                         MaterialStateManager::EXTERNAL_STORAGE);
const auto cuda =
    mfront::generic_parallel::makeCUDABackendExecutionPolicy({.stream = stream});
const auto policy = BatchExecutionPolicy{.backend_policy = &cuda};
const auto r = integrate(policy, m, BehaviourIntegrationOptions{}, dt);
```

## Single precision

MGIS is configured in `float` with the option `MGIS_REAL_TYPE` (`double`
by default), which generates the header `MGIS/RealType.h`. The numeric type
of each entry point is checked at loading time (symbol `<f>_real_size` of
TFEL). The tests pass in `float` (49/49) and with CUDA (51/51, in double as
in float), and with the tests of the `stlpar` backend on the host and
compiled by `nvc++ -stdpar=gpu` (54/54 in double as in float, 20/10).
Limits found in `float`: the Norton behaviour of the tests can no longer be
integrated around 3e9 Pa, and the cycle shared by the tests of the field
operations (`FieldOperationsTest.hxx`) makes three steps instead of four.
Compiled by `nvc++`, the Norton behaviour differs from the reference by
3.1e-5 on the stresses and 1.5e-3 on the tangent operator at the onset of
the flow, on the GPU as on the host and without contraction: the float
tolerances of `GenericParallelCUDATest` depend on the compiler. Details in
[plan-precision.md](plan-precision.md); patches 0062 to 0068.
