# A `generic-parallel` interface for MFront behaviours

Prototype. Goal: compile any MFront behaviour for a batch of integration
points on GPUs (CUDA, HIP) and CPUs (C++ standard parallel algorithms), in the
spirit of the `generic-parallel` interface for material properties (TFEL
master, #966), and usable by MGIS and mfem-mgis.

## Principles

1. **Same semantics as the `generic` interface.** A batch call is equivalent
   to calling the `generic` entry point on each point: same inputs, same
   outputs, same meaning of `K[0]`, `K[1]`, `K[2]` and `rdt`. The CPU results
   of the `generic` interface are the reference of the tests.
2. **Reuse the generated behaviour class.** The class generated by MFront is
   already mostly device-compatible. The new interface only adds a constructor
   and a small amount of glue code. No duplicated physics.
3. **Logic in headers, thin generated code.** The per-point work (gathering
   strided data, building the behaviour, integrating, exporting) is written
   once in `MFront/GenericParallelBehaviour/*.hxx` as `TFEL_HOST_DEVICE`
   templates. Backends only write kernels or parallel loops that call it.
4. **No change of the CPU behaviour of existing interfaces.** Device-specific
   branches use the `TFEL_DEVICE_CODE` macro, defined only when compiling
   device code.
5. **Same infrastructure as material properties**: backend factory and
   options, configuration files, library names suffixed by the backend,
   exported metadata, tests in the installation directory.

## Data layout

Each group of variables (gradients, thermodynamic forces, material
properties, internal state variables, external state variables, energies,
tangent operator, `rdt`) is described by a field (`mfront_gpb_ConstField`
for inputs, `mfront_gpb_Field` for outputs):

```c
typedef struct {
  const mfront_gb_real* values;         // first value of the first point
  mfront_gb_size_type point_stride;     // between two points, 0: uniform
  mfront_gb_size_type component_stride; // between two components
} mfront_gpb_ConstField;
```

Two strides serve both layouts:

- point by point (MGIS today): `point_stride` = size of the group,
  `component_stride` = 1;
- component by component (coalesced, GPU): `point_stride` = 1,
  `component_stride` = number of points.

A batch is described by `mfront_gpb_BatchData`: number of points, time
increment, computation options (the three first values of `K` in the
`generic` interface), initial `rdt`, optional per point `rdt` and
statuses, the fields of the states at the beginning and at the end of the
time step, and the queue (CUDA or HIP stream). A C structure is used rather
than a long argument list: behaviours have a dozen groups of variables and
the structure can evolve without breaking the prototype of the generated
functions. The summary is returned in `mfront_gpb_OutputStatus` (status,
number of failures and of unreliable results, minimum `rdt`, message).

## Per point execution

For each point, the kernel (`MFront/GenericParallelBehaviour/Integrate.hxx`):

1. builds a `mfront_gb_BehaviourData` view of the point. When all fields are
   stored point by point, the view points directly to global memory.
   Otherwise the values are gathered into local arrays, whose (maximal)
   sizes are known at code generation;
2. calls the integration strategy of the behaviour (see below) with the
   computation options of the batch and the parameters of the behaviour,
   passed by value to the kernel;
3. scatters the outputs if needed, and records the status.

The data of a point are described by a generated type (`PointTraits`) whose
static member `value` gives the maximal sizes of the data of a point and
whose `Integrator` member type gives the integration strategy: nvcc can't
generate the host stub of a kernel whose template parameter is a class type.

### One per point implementation for `generic` and `generic-parallel`

The drivers of the `generic` interface (`MFront/GenericBehaviour/*.hxx`:
small strain and general behaviours, standard finite strain behaviours,
finite strain strategies based on the Green-Lagrange and Hencky strains,
initialize functions, post-processings) are split into:

- a core, `TFEL_HOST_DEVICE`, which takes the computation options
  explicitly (`ComputationOptions`, decoded from the first values of `K` by
  the `generic` interface, given by the batch data in `generic-parallel`)
  and forwards additional arguments to the constructor of the behaviour
  (`Behaviour b(d, args...)`: none for `generic`, the parameters for
  `generic-parallel`). Exceptions are only caught on the host;
- the historical host functions, with unchanged signatures, which decode
  the options and call the core.

The `generic-parallel` interface has no integration code of its own: the
per point kernel only adapts the batch data. Integration strategies are
types (`mfront::gb::StandardIntegrator`, `finite_strain::Integrator`, ...)
selected by the generated code.

### Point view, functions applied at each point

`PointView<PointTraits, direct>` builds the `generic` behaviour data of a
point: pointers to the fields if all of them are stored point by point,
local copies otherwise. All the inputs are copied by the constructor
(including, on request, the state at the end of the time step, read by
post-processings and only partially written by some initialize functions),
and the outputs are read back through the pointers of the behaviour data.

The functions applied at each point are trivially copyable function objects
returning the statistics of the point: `PointIntegrator`,
`InitializeFunctionExecutor`, `PostProcessingExecutor`, `RotationExecutor`.
Each backend provides a single primitive, `apply(status, n, queue, rdt0, f,
...)`. The entry points (`integrateBatch`, `executeInitializeFunctionOnBatch`,
`executePostProcessingOnBatch`, `rotateBatch` in `Integrate.hxx`) check the
data, choose the function object (`dispatch*`) and call the primitive of
the backend, given as a callable object; the functions of a backend only
bind its primitive to its options. The SYCL backend keeps its own entry
points, since it copies the fields to the device before the dispatch.

Initialize functions and post-processings are called through named function
objects generated by MFront (`<Behaviour>InitializeFunction_<name>`),
never through pointers to members, which `nvc++` silently ignores in device
code. The pointer to member API of the `generic` interface is kept on the
host (`mfront::gb::MethodCaller`).

### Rotations of orthotropic behaviours

`MFront/BehaviourRotationFunctions.hxx` describes the rotation functions of
an orthotropic behaviour (rotated objects with their types and offsets,
size of a point, direction of the rotation) and writes the rotation of the
values of a point with `tfel::math::change_basis` on views. It is shared by
the `generic` interface (functions for one point and for arrays) and the
`generic-parallel` interface (function objects applied by
`RotationExecutor` on `mfront_gpb_RotationData`, with a rotation matrix per
point or a uniform one). Scalars, vectors, symmetric tensors, tensors and
the associated tangent operator blocks are supported.

### Constant data in device code

Data built at compile time (slip systems of single crystals) are accessed
through `tfel::utilities::getConstantObject<T>()`: a `__device__ constexpr`
variable template in CUDA and HIP device code (function scope statics are
zero-filled by nvcc), an `inline constexpr` variable template otherwise, and
a copy with `nvc++ -stdpar=gpu` (no access to global data from GPU code).

The finite strain tangent operator uses `TrivialGenTypeBase` (tagged union
of trivially copyable types) instead of `std::variant`, whose visitation is
not supported in device code by `nvc++`. The fixed size mathematical
objects of TFEL are trivially copyable.

### Standalone models

Models (`@DSL Model`) are treated as behaviours without gradients, as by the
`generic` interface: outputs are internal state variables, inputs are
external state variables. The integration strategy of the point traits,
`mfront::gpb::ModelIntegrator`, builds the model from the behaviour data of
the point and from a structure holding the parameters (filled on the host,
passed by value), then calls its `execute` method. The backends are not
changed. The model class is written by the same function as for the
`generic` interface (`writeGenericModelClass`), whose device mode adds the
host and device annotations, reports bounds failures by returned values and
uses the device implementation of the material laws.

### Behaviour variables

Behaviour variables are default constructed members (or factory products)
of the behaviour. Their default constructors, those of their data classes
and the factories are host and device functions. Their parameters, read
from parameters initializers on the host, take their default values in
device code.

## Generated class

The `generic-parallel` interface derives from the `generic` interface and
reuses the members it adds to the behaviour class (data constructors,
`exportStateData`). The code generator writes identical blocks produced by
several interfaces only once, so both interfaces can be used together. The
interface adds a template constructor taking the parameters.

## Device code

`TFEL_DEVICE_CODE` is defined when device code is compiled. Host code is
unchanged; device code returns failures instead of throwing exceptions.
Material properties called by behaviours have an implementation in the
`mfront::device` namespace, generated by the `mfront` material property
interface in its header. The CUDA backend increases the stack size of the
threads if a kernel requires it.

## Errors

The entry point reports, through an output status, the number of points
where the integration failed and whether some results are unreliable
(`rdt` < 0.99). An optional per point status array gives the location of the
failures.

## Backends

All backends apply a function object (`PointIntegrator`, trivially copyable,
no extended lambdas required) at each point and reduce the statistics of
the batch (`BatchStatistics`: numbers of failures and unreliable results,
minimal time step scaling factor), each with the idiomatic primitive of its
programming model:

1. CUDA and HIP (`GPU.hxx`): one thread per point, reduction per warp and
   atomic operations only when a point failed or decreased the time step
   scaling factor; the stack size is computed from the kernel attributes;
2. C++ standard parallel algorithms (`ParallelSTL.hxx`):
   `std::transform_reduce` over a counting iterator (gcc/TBB, clang, nvc++
   `-stdpar=gpu`);
3. Kokkos (`Kokkos.hxx`): `Kokkos::parallel_reduce` with a reduction functor
   (`init`, `join`), any execution space;
4. SYCL (`SYCL.hxx`): `parallel_for` with atomic updates of the statistics
   (no reductions: their barriers make AdaptiveCpp fail on large kernels on
   CPUs), optional automatic transfers of the fields not accessible by the
   device;
5. OpenMP (`OpenMP.hxx`): `target teams distribute parallel for` (offload)
   or `parallel for` (host threads), with reductions member by member of
   the statistics.

The CUDA runtime used by nvc++ and AdaptiveCpp gives no access to the stack
size: `MFront/GenericParallel/DeviceStackSize.hxx` sets it through the CUDA
runtime loaded by the process (`device_stack_size` option).

## Kokkos backend

The libraries generated by MFront are loaded at runtime by the calling code
(MGIS uses `dlopen`). The calling code and the generated libraries must
then share the same instance of Kokkos (initialization, execution spaces,
memory pools): Kokkos must be a **shared** library, built **without
relocatable device code** with CUDA. The generated function checks that
Kokkos is initialized; it never initializes it. The batch summary is
reduced by `Kokkos::parallel_reduce` with a reduction functor. The execution
space instance may be given through the `queue` member of the batch data.

## Roles of TFEL/MFront, MGIS and mfem-mgis

The three libraries share the work as follows. Each one only knows the
interface of the previous one.

| | TFEL/MFront | MGIS | mfem-mgis |
|---|---|---|---|
| Role | code of a material point, processing of a batch | material data, loading, dispatch | finite elements, solvers, orchestration |
| GPU code | kernels of the batch functions (one backend per library) | none in the core | assembly and solvers on the device (MFEM, hypre, Ginkgo) |
| Memory | never allocates (except the SYCL copies of inaccessible fields) | allocates the material data in the requested memory space | owns the finite element data, decides where they live |
| Interface | `mfront_gpb_BatchData` (C), metadata symbols | `MaterialDataManager`, batch integration functions | `PartialQuadratureSpace`, nonlinear forms |

Principles:

- TFEL/MFront exposes a C data contract: fields (pointer and strides) for
  each group or each variable, a queue, statuses. The kernels receive
  everything by value. TFEL does not choose the device nor the memory
  space: the caller gives pointers accessible by the device.
- MGIS maps its data (`MaterialDataManager`, uniform or per point values)
  to this contract without copies when possible (per variable fields for
  the material properties and the external state variables). MGIS selects
  the `generic` or the `generic-parallel` function and falls back to the
  `generic` interface if needed. MGIS has no dependency on a GPU toolkit:
  memory spaces are provided by the caller or by optional components.
- mfem-mgis decides which parts run on the device: integration only,
  integration and assembly, or everything. It moves the finite element
  data with the memory manager of MFEM and calls MGIS on the points of
  each partial quadrature space. It never calls TFEL directly.
- A backend of TFEL is a property of a generated library. Several
  libraries (for instance `cuda` and `stlpar`) can be loaded together, so
  that the choice between the host and the device is made at run time by
  MGIS or mfem-mgis.

## Milestones

1. Generated code compilable for GPUs: `TFEL_HOST_DEVICE` annotations, device
   compatible checks of the tangent operator flag, parameters taken from an
   argument in the interface constructor.
2. The interface, the batch data structure, the device integration driver,
   the CUDA and C++ standard backends, for small strain behaviours.
3. Tests against the `generic` interface: elasticity, J2 plasticity (default
   DSL), Norton and Chaboche (implicit DSL), in the installation directory.
4. Implicit DSL and TDLS for the local Newton solvers.
5. Finite strain behaviours, initialize functions, post-processings,
   rotations, single crystals (done in the prototype).
6. MGIS: load a `generic-parallel` library, integrate a batch described by
   views. Then mfem-mgis.
