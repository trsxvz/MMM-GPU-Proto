==================
Installation guide
==================

.. contents::
    :depth: 2
    :local:

Quick start
-----------

``mfem-mgis`` is packaged in `Spack <https://spack.io/>`_, which also
installs all its dependencies. These commands set up Spack:

.. code:: sh

   git clone --depth=2 --branch=v1.2.2 https://github.com/spack/spack.git
   source spack/share/spack/setup-env.sh
   spack repo update builtin --branch develop

The last command selects the ``develop`` branch of the Spack packages,
because their releases do not provide ``mfem-mgis`` yet.

The ``@master`` version of ``mfem-mgis``, its development version, is
currently recommended, as it includes many fixes:

.. code:: sh

   spack install mfem-mgis@master

The last release (1.0.4) is installed by:

.. code:: sh

   spack install mfem-mgis

.. note::

   The Spack package installs the upstream versions of ``mfem-mgis``,
   which do not include the features of this prototype (computations by
   batches and by kernels, execution settings, computations on a GPU).
   The prototype is built from its sources, see
   :ref:`mfem_mgis_installation_prototype`.

Spack needs a few system tools, such as ``git``, ``python3`` and C, C++
and Fortran compilers. They are listed in the `Spack documentation
<https://spack.readthedocs.io/en/latest/installing_prerequisites.html>`_.
The first installation builds about 90 packages from their sources. It
takes about 15 minutes on a computer with 8 cores.

.. note::

   Install Spack outside the sources of ``mfem-mgis``, to avoid issues
   with CMake.

Installing with Spack
---------------------

Versions
^^^^^^^^

This documentation is generated from the ``gpu-proto`` branch, a
prototype based on the ``@master`` version. The computations by batches
and by kernels, the execution settings (option ``--execution``), the
computations and the solvers on a GPU (see
:ref:`mfem_mgis_batch_computations`) and the ``float`` numerical type
(see below) are not available in the ``@master`` version nor in the
releases. Some of the other features it describes are
not available in the last release (1.0.4). They are marked as such.

Variants
^^^^^^^^

The package has three variants:

- ``mpi`` enables MPI parallelism. It is enabled by default. Only the
  ``@master`` version can be built without MPI, with ``~mpi``.
- ``mumps`` adds the ``MUMPS`` solver to ``MFEM``. It is enabled by
  default when MPI is.
- ``int64`` uses 64 bit integers in ``hypre`` and ``metis``. It is
  enabled by default.

For example, this command installs the ``@master`` version without MPI:

.. code:: sh

   spack install mfem-mgis@master~mpi

Compilers
^^^^^^^^^

``mfem-mgis`` requires GCC 11 or newer. Spack detects the compilers of
the system the first time it runs. A compiler made available later, for
example by ``module load``, must be added with:

.. code:: sh

   spack compiler find

Using the installed package
^^^^^^^^^^^^^^^^^^^^^^^^^^^

.. code:: sh

   spack load mfem-mgis

This command makes ``mfront`` and ``mpirun`` available. It also sets the
``MFEMMGIS_DIR`` variable, which CMake projects use to find
``mfem-mgis``. When several versions are installed, the version must be
given, for example ``spack load mfem-mgis@master``.

Building from the sources
-------------------------

To work on the sources of ``mfem-mgis``, Spack only installs its
dependencies, in an environment:

.. code:: sh

   git clone https://github.com/thelfer/mfem-mgis.git
   spack env create mfem-mgis-deps
   spack -e mfem-mgis-deps add mfem-mgis@master
   spack -e mfem-mgis-deps install --only dependencies
   spack env activate mfem-mgis-deps

Once activated, the environment gives CMake access to the dependencies.
CMake builds the sources, and the ``check`` target runs the tests:

.. code:: sh

   cmake -S mfem-mgis -B build -DCMAKE_INSTALL_PREFIX=install
   cmake --build build -j 8
   cmake --build build --target check
   cmake --build build --target install

A ``MFEM`` built outside the environment, for instance with ``CUDA`` or
``HIP``, is given by ``-DMFEM_DIR=<prefix of MFEM>`` (or the environment
variable ``MFEM_DIR``), which takes precedence over
``CMAKE_PREFIX_PATH``.

Building the prototype
^^^^^^^^^^^^^^^^^^^^^^

The ``gpu-proto`` branch requires versions of ``MGIS`` and ``TFEL`` which
are not the ``master`` versions installed by Spack:

- ``MGIS`` must provide the field operations (header
  ``MGIS/FieldOperations.hxx``), the location and the layout of the arrays
  of the material data managers. This is checked when CMake configures
  ``mfem-mgis``, which stops with an error otherwise. The ``master``
  branch of ``MGIS`` does not provide them: the prototype branch of
  ``MGIS`` does.
- The behaviours for the GPU are generated by the ``generic-parallel``
  interface of ``MFront``, with the configuration files of ``TFEL``
  (``config-cuda-nvcc.json``, ``config-hip-hipcc.json``). The
  configuration files ``config-kokkos.json``, ``config-kokkos-host.json``
  and ``config-openmp-*.json`` are only provided by the prototype branch
  of ``TFEL``.
- The computations on a GPU require ``MFEM`` compiled with ``CUDA`` or
  ``HIP`` (see below): the Spack package of ``mfem-mgis`` has no variant
  for them.

These versions are built from their sources and given to CMake:
``-DMFrontGenericInterface_DIR=<prefix of MGIS>/share/mgis/cmake`` (or
``CMAKE_PREFIX_PATH``) for ``MGIS``, ``-DMFEM_DIR=<prefix of MFEM>`` for
``MFEM``, ``mfront`` of this ``TFEL`` being found in the ``PATH`` (or
given by the variable ``MFRONT``).

CMake options
^^^^^^^^^^^^^

- ``enable-gpu-tests`` (``ON``): adds the tests which require a GPU, when
  ``MFEM`` is compiled with ``CUDA`` or ``HIP``;
- ``enable-amgx`` (``OFF``): solvers of the ``AmgX`` library (requires
  ``MFEM`` compiled with ``CUDA``, ``AmgX`` being given by ``AMGX_DIR``,
  see :ref:`mfem_mgis_batch_computations_amgx`);
- ``enable-kokkos`` (``OFF``): initialization of ``Kokkos`` (see below);
- ``enable-trilinos`` (``OFF``): solvers and preconditioners of
  ``Trilinos`` (requires ``enable-kokkos``, see below);
- ``enable-portable-build`` (``OFF``): binaries shared between machines
  of the same architecture;
- ``BENCHMARKS`` (``OFF``): compiles the benchmarks;
- ``enable-doxygen-doc`` (``OFF``): generation of the ``Doxygen``
  documentation;
- ``enable-tfel-tests`` (``OFF``): tests based on the test framework of
  ``TFEL`` (found with the hint ``TFEL_DIR``), already enabled when the
  ``TFEL`` used by ``MGIS`` provides this framework.

The direct solver ``CuDSSSolver`` is available when ``MFEM`` is built
with ``cuDSS`` (see :doc:`../user_guide/glossary`).

MFEM compiled with CUDA or HIP
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

When ``MFEM`` is compiled with ``CUDA`` or ``HIP``, the sources
containing kernels of ``MFEM`` (``mfem::forall``) must be compiled as
``CUDA`` code (by ``nvcc``) or as ``HIP`` code (by the ``clang`` of ROCm
used by the ``hipcc`` of ``MFEM``). The CMake
module ``MFEMMGISDeviceCode.cmake``, installed with ``mfem-mgis`` and
loaded by ``find_package(MFEMMGIS)``, provides:

- ``mfem_mgis_enable_device_language()``, to be called at file scope
  (not in a function), which enables the ``CUDA`` or ``HIP`` language
  with the compilers used to build ``MFEM``: ``nvcc`` and its host
  compiler (unless ``CMAKE_CUDA_COMPILER`` and ``CMAKE_CUDA_HOST_COMPILER``,
  or the environment variables ``CUDACXX`` and ``CUDAHOSTCXX``, are
  given), or the ``clang`` of ROCm used by the ``hipcc`` of ``MFEM``
  (unless ``CMAKE_HIP_COMPILER`` or the environment variable ``HIPCXX`` is
  given: ``CMake`` does not accept ``hipcc`` as ``HIP`` compiler), on the
  AMD platform (unless ``CMAKE_HIP_PLATFORM`` is given);
- ``mfem_mgis_compile_as_device_code(target sources...)``, which compiles
  the given sources of the target as ``CUDA`` or ``HIP`` code, for the GPU
  architectures of ``MFEM``.

Both do nothing when ``MFEM`` is compiled neither with ``CUDA`` nor with
``HIP``. CMake 3.18 (``CUDA``) or 3.21 (``HIP``) or later is then
required. The tests which require a GPU are disabled by
``-Denable-gpu-tests=OFF``. With ``HIP``, the tests on the host, on the
``debug`` device of ``MFEM`` and the tests of the option ``--execution``
are registered, but not the other tests on the GPU, which select the
``cuda`` device of ``MFEM`` (``--device cuda``) or use behaviours
generated by the ``cuda`` backend of ``MFront``. ``mfem-mgis`` has been
run with a ``MFEM`` compiled with ``HIP`` on an integrated AMD GPU
(``gfx1036``, ROCm 10.1, HIP 7.16). With this runtime, a kernel waiting
in a stream is lost when the first kernel of a shared library not yet
loaded is launched (for instance a behaviour generated by ``MFront``);
the environment variables ``AMD_SERIALIZE_KERNEL=3`` and
``AMD_SERIALIZE_COPY=3`` avoid it, at the expense of the overlap of the
computations.

The use of a GPU is described in :ref:`mfem_mgis_batch_computations_gpu`.

Kokkos
^^^^^^

The behaviours generated by the ``kokkos`` backend of the
``generic-parallel`` interface of ``MFront`` require an initialized
``Kokkos``, which they do not initialize. With the option
``-Denable-kokkos=ON`` (``Kokkos`` being found by ``find_package``, for
instance through ``CMAKE_PREFIX_PATH``), ``mfem_mgis::initialize``
initializes ``Kokkos`` on demand, after the device of ``MFEM``, with the
option ``--kokkos`` or the environment variable ``MFEM_MGIS_KOKKOS`` (any
non empty value other than ``0``), and ``mfem_mgis::finalize`` finalizes it
before ``MPI``. Without this option, ``--kokkos`` is an error and
``MFEM_MGIS_KOKKOS`` is ignored with a warning.

- ``Kokkos`` uses the GPU of the device of ``MFEM`` configured by
  ``--device``, by ``MFEM_MGIS_DEVICE`` or by the program before
  ``mfem_mgis::initialize``; otherwise, ``Kokkos`` chooses its GPU.
- ``Kokkos`` must be built as shared libraries, which the behaviours use
  too (the ``Kokkos`` used by ``MFront`` with the configuration file
  ``config-kokkos.json``): otherwise, they still report that ``Kokkos`` is
  not initialized. With a ``Kokkos`` built for a GPU, the device of
  ``MFEM`` is a GPU (for instance ``--device cuda``); the configuration
  file ``config-kokkos-host.json`` generates behaviours for the host.
- The only source of ``mfem-mgis`` including ``Kokkos`` is compiled by the
  compiler of ``Kokkos``, through the launcher of ``Kokkos`` set on this
  target only (without ``CMAKE_CXX_COMPILER_LAUNCHER``, such as
  ``ccache``), in the shared library ``MFEMMGISKokkos``, installed next to
  ``MFEMMGIS`` and privately linked to ``Kokkos``: the projects using
  ``mfem-mgis`` neither find ``Kokkos`` nor inherit its flags. Their
  installed programs need a run path to the directory of this library (for
  instance ``CMAKE_INSTALL_RPATH_USE_LINK_PATH``).
- ``find_package(Kokkos)`` sets ``CMAKE_CXX_EXTENSIONS`` to ``OFF``:
  ``mfem-mgis`` is then compiled without the extensions of the compilers
  (``-std=c++20`` instead of ``-std=gnu++20``).

Trilinos
^^^^^^^^

With the option ``-Denable-trilinos=ON``, the Krylov solvers of ``Belos``,
the direct solvers of ``Amesos2``, the preconditioners of ``Ifpack2``, the
algebraic multigrid of ``MueLu`` and the two level Schwarz preconditioner
of ``FROSch`` are available in parallel (see
:ref:`trilinos_linear_solvers`). ``Trilinos`` is found by
``find_package(Trilinos)`` with the components ``Tpetra``, ``Belos``,
``Ifpack2``, ``MueLu``, ``Amesos2`` and ``ShyLU_DDFROSch`` (for instance
through
``CMAKE_PREFIX_PATH``). It requires ``MFEM`` compiled with ``MPI``, the
``double`` type and the option ``enable-kokkos``, the ``Kokkos`` of
``Trilinos`` being the one which ``mfem-mgis`` initializes (the ``Kokkos``
found by ``mfem-mgis`` must be the one ``Trilinos`` is built with): ``Kokkos`` is
initialized when the first solver of ``Trilinos`` is built, if needed,
and finalized by ``mfem_mgis::finalize``.

- The sources including ``Trilinos`` are compiled by the compiler of
  ``Kokkos`` in the shared library ``MFEMMGISTrilinos``, installed next to
  ``MFEMMGIS`` and privately linked to ``Trilinos``, whose interface only
  uses standard types: the projects using ``mfem-mgis`` neither find
  ``Trilinos`` nor inherit its flags.
- ``Tpetra`` computes on the GPU when ``Trilinos`` (and its ``Kokkos``) is
  built with ``CUDA`` or ``HIP``, on the host otherwise.
- With Spack, ``trilinos@17.2`` requires ``kokkos@5.2.1`` and
  ``kokkos-kernels@5.2.1``, for instance ``trilinos@17.2.1 +mpi +wrapper
  +kokkos +openmp +tpetra +belos +ifpack2 +muelu +amesos2 +shylu
  cxxstd=20`` (``+shylu`` for ``FROSch``; the sparse direct solver
  ``Tacho`` of ``Amesos2`` requires the CMake options
  ``Trilinos_ENABLE_ShyLU_NodeTacho`` and ``Amesos2_ENABLE_ShyLU_NodeTacho``,
  which the package of Spack does not set),
  completed by ``+cuda cuda_arch=...`` for a GPU of NVIDIA.

Numerical type
^^^^^^^^^^^^^^

``mfem-mgis`` uses the numerical type of ``MFEM`` (``mfem::real_t``),
``mfem_mgis::real``: ``double``, or ``float`` when ``MFEM`` is compiled
in single precision (``MFEM_USE_SINGLE``, variant ``precision=single`` of
the Spack package, which requires ``hypre`` in single precision and
``MUMPS`` with ``+float``). ``hypre`` must then use its internal ``LAPACK``
(variant ``~lapack`` of the Spack package): with an external ``LAPACK``,
``hypre`` 3.2.0 in single precision calls the ``LAPACK`` routines of the
``double`` type on ``float`` arrays, which breaks ``ParaSails``, the
Gaussian elimination of types 98, 99, 198 and 199 of ``BoomerAMG`` and
other solvers of ``hypre``. The configuration of ``mfem-mgis`` warns about such
a ``hypre``. Then:

- ``MGIS`` must be configured with the same type
  (``-DMGIS_REAL_TYPE=float``), which the configuration checks;
- ``AmgX`` (``enable-amgx``) and ``Trilinos`` (``enable-trilinos``) are
  refused, and ``SuiteSparse``, which
  ``MFEM`` does not support in single precision, is not required;
- the type is exported by the installed CMake configuration
  (``MFEMMGIS_REAL_TYPE`` variable and ``MFEM_MGIS_REAL_TYPE`` global
  property), and ``mfem_mgis_add_behaviours_library`` generates the
  behaviours with it (``real_type`` option of ``mfront``): ``MGIS``
  refuses a behaviour of another type when it is loaded;
- the parameters of ``mfem-mgis`` (``Parameters``) keep their values in
  ``double`` and convert them when they are read, so that
  ``{"Tolerance", 1e-10}`` compiles with both types;
- the relative tolerances given to the solvers (``RelativeTolerance``
  and ``Tolerance`` parameters) are bounded below by 100 times the machine
  epsilon (``1.2e-5``), since the relative residuals stagnate at about ten
  machine epsilons. A null tolerance and the absolute tolerances are kept.

With ``float``, the residuals of the nonlinear problems stagnate at about
``1e-5`` of the scale of the internal forces: a tolerance relative to the
initial residual of a time step, small at the end of a loading or of the
iterations of a coupling, may be out of reach, and an absolute tolerance
of about ten times this floor is then needed, unless the Newton solver
accepts the stagnation of the residual at this floor (option
``StagnationRelativeTolerance``, see :doc:`../user_guide/nonlinear_algorithms`).
For finite strain
behaviours, the deformation gradient, close to the identity, is rounded
to about ``1e-7``, so that the stresses are only known to about
``1e-7`` times the elastic moduli. The convergence criteria of the
behaviours are raised by ``MFront`` (see the ``real_type`` option of
``TFEL`` 5.2).

Creating a simple example based on ``mfem-mgis``
------------------------------------------------

The installation of ``mfem-mgis`` includes two simple examples, ``ex1`` and
``ex3``, in the directory ``share/mfem-mgis/examples`` of the
installation. The ones of the prototype require the prototype: they build
their behaviour libraries for the CPU and, if ``MFEM`` uses a GPU, for the
GPU, with the CMake function ``mfem_mgis_add_behaviours_library`` (see
:ref:`mfem_mgis_batch_computations_execution`), so ``mfront`` is needed
when CMake configures them (variable ``MFRONT``, or ``mfront`` found in
the ``PATH``). They can be copied to another location and built with
CMake. With ``mfem-mgis`` installed by Spack (upstream version):

.. code:: sh

   spack load mfem-mgis
   cp -r `spack location -i mfem-mgis`/share/mfem-mgis/examples/ex1 .
   cd ex1
   cmake -B build
   cmake --build build
   ctest --test-dir build

Without spack, for instance with the prototype installed from its sources
in ``<prefix>``, ``share/mfem-mgis/examples/env.sh`` sets the required
environment variables (``MFEMMGIS_DIR``, ``MFEM_DIR``, the ``PATH`` to
``mfront``...):

.. code:: sh

   source <prefix>/share/mfem-mgis/examples/env.sh
   cp -r <prefix>/share/mfem-mgis/examples/ex1 .
   cd ex1
   cmake -B build
   cmake --build build
   ctest --test-dir build

The examples of the prototype accept the options of ``mfem-mgis``, such
as ``--execution``:

.. code:: sh

   ./build/UniaxialTensileTest --execution cpu

Their sources can be modified to develop your own study cases.

Installing mfem-mgis and mfem-mgis-examples on Topaze (CCRT)
------------------------------------------------------------

This guide provides step-by-step instructions for setting up your
environment on ``Topaze/CCRT`` and installing the necessary software. Follow
these steps to get started.

.. note::

   This guide installs the ``@master`` version of ``mfem-mgis`` with
   Spack, without the features of the prototype. The examples of the
   prototype (which call ``mfem_mgis::getBehavioursLibrary`` and the CMake
   function ``mfem_mgis_add_behaviours_library``) do not build against
   it: they require the prototype, built from its sources (see
   :ref:`mfem_mgis_installation_prototype`).

Create a new directory and useful paths
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

.. code-block:: bash

   mkdir topaze-dir && cd topaze-dir
   export MY_DIR=$PWD
   export MY_LOG=YOURLOGIN
   export MY_DEST=/ccc/scratch/cont002/den/${MY_LOG}/mini-test

Download Spack, mfem-mgis, and mfem-mgis-examples (not required)
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Before proceeding, remove your user configuration of Spack
(``~/.spack``). Download Spack and the git directories of ``mfem-mgis``
and ``mfem-mgis-examples``:

.. code-block:: bash

   cd $MY_DIR
   git clone --depth=2 --branch=v1.2.2 https://github.com/spack/spack.git
   rm -rf ~/.spack
   export SPACK_ROOT=$PWD/spack
   source ${SPACK_ROOT}/share/spack/setup-env.sh
   cd ${SPACK_ROOT}
   git clone --branch=develop https://github.com/spack/spack-packages.git
   spack repo set --destination "${PWD}/spack-packages" builtin
   cd ..
   git clone https://github.com/thelfer/mfem-mgis.git
   git clone https://github.com/latug0/mfem-mgis-examples.git

Create a Spack Mirror on Your Machine (Local)
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The ``develop`` branch of the Spack packages provides ``mfem-mgis``. The
examples require the ``@master`` version of ``mfem-mgis``. Create a
``spack`` mirror and a bootstrap directory.

.. code-block:: bash

   spack bootstrap mirror --binary-packages my_bootstrap
   spack mirror create -d re2c_mirror re2c@3.0
   cp -r re2c_mirror/_source-cache/archive/b3/ my_bootstrap/bootstrap_cache/_source-cache/archive
   spack mirror create -d mirror-mfem-mgis -D mfem-mgis@master

It’s possible that you will need some packages in your mirror, you can
specify them with the following command:

.. code-block:: bash

   spack mirror create -d mirror-mfem-mgis -D mfem-mgis@master zlib ca-certificates-mozilla zlib-ng util-macros pkgconf findutils libpciaccess libedit libxcrypt bison libevent numactl

**Copy Data to Topaze**

You’ll need to copy the following files to Topaze: 

- spack
- mfem-mgis
- mfem-mgis-examples
- mirror-mfem-mgis
- my_bootstrap

Create an archive for these files:

.. code-block:: bash

   cd $MY_DIR
   tar czvf archive.tar.gz mfem-mgis/ mfem-mgis-examples/ mirror-mfem-mgis/ spack/ my_bootstrap/
   scp archive.tar.gz $MY_LOG@topaze.ccc.cea.fr:$MY_DEST/

**Load Topaze modules**

Log on ``Topaze``:

.. code-block:: bash

   ssh -Y $MY_LOG@topaze.ccc.cea.fr

Load the required modules on Topaze:

.. code-block:: bash

   module load gnu/13.2.0
   module load mpi/openmpi/4.0.5
   module load cmake/3.29.6

Install mfem-mgis on Topaze
^^^^^^^^^^^^^^^^^^^^^^^^^^^

Note that the installation is performed in your scratch directory, and
files are automatically removed after 3 months.

**Setup spack**

If you had a previous installation of ``spack`` on Topaze, remove its
user configuration (``rm -rf ~/.spack``) to avoid any conflicts.

Now extract the files and set-up the bootstrapping

.. code-block:: bash

   cd $MY_DEST
   tar xzvf archive.tar.gz
   source $PWD/spack/share/spack/setup-env.sh
   spack repo set --destination "${PWD}/spack/spack-packages" builtin
   spack bootstrap reset -y
   spack bootstrap add --scope=site --trust local-binaries $PWD/my_bootstrap/metadata/binaries/
   spack bootstrap add --scope=site --trust local-sources $PWD/my_bootstrap/metadata/sources/
   spack buildcache update-index $PWD/my_bootstrap/bootstrap_cache
   spack bootstrap disable --scope=site github-actions-v2
   spack bootstrap disable --scope=site github-actions-v0.6
   spack bootstrap disable --scope=site spack-install
   spack bootstrap root $PWD/spack/bootstrap

Now you can look for the compilers

.. code-block:: bash

   spack compiler find

and remove the unnecessary ones ``spack`` might have found by editing the configuration file, e.g., 

.. code-block:: bash

   vim $HOME/.spack/packages.yaml

Now everything is set to bootstrap

.. code-block:: bash

   spack bootstrap now
   spack bootstrap status

If everything goes well, you will obtain something like

.. code-block:: bash

   [PASS] Core Functionalities

   [PASS] Binary packages

**Export SPACK Variables**

To use ``MFront``, you need to export some ``SPACK`` variables. Please execute
the following commands:

.. code-block:: bash

   export CC='gcc'
   export CXX='g++'
   export FC='mpifort'
   export OMPI_CC='gcc'
   export OMPI_CXX='g++'
   export OMPI_FC='gfortran'

**Install MFEM-MGIS**

.. code-block:: bash

   spack mirror add MMM $PWD/mirror-mfem-mgis/

**Run installation**

.. code-block:: bash

   module load gnu/13.2.0 mpi/openmpi/4.0.5 hwloc cmake/3.29.6
   spack compiler find
   spack external find hwloc
   spack external find cmake
   spack external find openssh
   spack external find openmpi
   
   spack install mfem-mgis@master%gcc@13.2.0

Install MFEM-MGIS-examples on Topaze
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Follow these steps to install mfem-mgis-examples on Topaze:

.. code-block:: bash

   cd mfem-mgis-examples
   mkdir build && cd build
   spack load mfem-mgis
   cmake ..
   make -j 10
   ctest

**How to run an example (ex7)**

There are two ways to run an example, such as ex7, from its build
directory ``build/ex7``:

Using ccc_mprun
^^^^^^^^^^^^^^^

To run an example using ccc_mprun with 1024 processes and 1 core per process (-m access to other filesystem, -T time), execute the following command:

.. code-block:: bash

   ccc_mprun -n 1024 -c 1 -m work,store,scratch -T 84000 -pmilan ./mox2 -m mesh/inclusion.msh -o 1 -r 2 --no-post-processing

Using ccc_msub
^^^^^^^^^^^^^^


Here's an example of a `run.batch` job submission file to run an RVE simulation on 4096 MPI processes on the partition named milan for 86400 seconds.

.. code-block:: bash

  #!/bin/bash
  #MSUB -r ver
  #MSUB -n 4096
  #MSUB -c 1
  #MSUB -T 86400
  #MSUB -o ver_4096_%I.o
  #MSUB -e ver_4096_%I.e
  #MSUB -q milan
  #MSUB -m scratch,work

  module load gnu/13.2.0 mpi/openmpi/4.0.5 cmake/3.29.6
  export OMP_NUM_THREADS=1
  set -x
  ccc_mprun ./mox2 -m mesh/inclusion.msh -o 1 -r 2 --no-post-processing

Then, to submit the job:

.. code-block:: bash
  
  ccc_msub run.batch


Troubleshooting
^^^^^^^^^^^^^^^

If you encounter ``Spack`` errors due to missing packages, consider the following two possibilities:

- Check if the package is already installed on Topaze by running:

.. code-block:: bash

  spack external find your-package

If the package is found, you can use it directly.

- If the package is not installed on ``Topaze``, you can add its sources to your mirror directory. If you are using an SSHFS mount, you can complete your mirror by executing the following command on your host machine:

.. code-block:: bash

  spack mirror create -d your-mirror/ -D your-package

For more questions about ``spack``, see the ``spack`` documentation.
