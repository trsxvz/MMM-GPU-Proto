=========================================
Computations by batches and by kernels
=========================================

.. contents::
    :depth: 3
    :local:

Overview
========

By default, the gradients are computed and the behaviours are integrated
element by element, and the inner forces and the tangent operator are
assembled by the element loops of :code:`MFEM`. :code:`mfem-mgis` also
provides another path, in which:

- the behaviours are integrated by batches: the behaviour of a material is
  integrated at all its integration points by a single call to
  :code:`MGIS`;
- the gradients, the inner forces and the stiffness matrices of the
  elements are computed by kernels of :code:`MFEM` (:code:`mfem::forall`),
  for all the elements of a material at once;
- the tangent operator is assembled by kernels, or applied without being
  assembled.

Each step is selected separately. The kernels run on the device of
:code:`MFEM` if one is enabled, for instance a GPU (see
:ref:`mfem_mgis_batch_computations_gpu`), and on the host otherwise.

Selecting the computations
==========================

Parameters and environment variables
------------------------------------

The computations are selected by five parameters of the nonlinear
evolution problem, given to its constructor with the parameters of the
finite element discretization (see :ref:`mfem_mgis_batch_computations_example`).
The default value of each parameter can be changed by an environment
variable, for instance to run an existing executable, or a whole test
suite, with the batch path:

.. list-table::
   :header-rows: 1
   :widths: 28 30 20 32

   * - Parameter
     - Values
     - Default value
     - Environment variable
   * - :code:`BehaviourIntegration`
     - :code:`PointByPoint`, :code:`Batch`
     - :code:`PointByPoint`
     - :code:`MFEM_MGIS_BEHAVIOUR_INTEGRATION`
   * - :code:`GradientsComputation`
     - :code:`ElementByElement`, :code:`Kernels`
     - :code:`ElementByElement`
     - :code:`MFEM_MGIS_GRADIENTS_COMPUTATION`
   * - :code:`InnerForcesComputation`
     - :code:`ElementByElement`, :code:`Kernels`
     - :code:`ElementByElement`
     - :code:`MFEM_MGIS_INNER_FORCES_COMPUTATION`
   * - :code:`TangentOperatorComputation`
     - :code:`ElementByElement`, :code:`Kernels`, :code:`MatrixFree`
     - :code:`ElementByElement`
     - :code:`MFEM_MGIS_TANGENT_OPERATOR_COMPUTATION`
   * - :code:`TangentOperatorAssembly`
     - :code:`Atomic`, :code:`Ordered`
     - :code:`Atomic`
     - :code:`MFEM_MGIS_TANGENT_OPERATOR_ASSEMBLY`

A parameter given to the problem takes precedence over the environment
variable, which only replaces the default value. The environment variables
are read when the problem is built. An invalid value is reported with the
name of the parameter, or of the environment variable, which gave it.

Integration by batches
----------------------

With :code:`BehaviourIntegration` set to :code:`Batch`, the gradients are
first computed on all the elements, then the behaviour of each material is
integrated at all its integration points by one call to :code:`MGIS`:

- a behaviour generated by the :code:`generic` interface of :code:`MFront`
  is integrated point by point by :code:`MGIS`, which stops at the first
  failure;
- a behaviour generated by the :code:`generic-parallel` interface is
  integrated as a batch, all the points being integrated even if the
  integration fails at some of them.

For an orthotropic behaviour, the gradients are rotated in the material
frame before the integration (except for a prediction), and the tangent
operator blocks are rotated back to the global frame after it, at all the
points at once. For a behaviour which does not provide the rotation of the
values of one point (behaviours generated by the :code:`generic-parallel`
interface), the thermodynamic forces in the global frame are also computed
at all the points after the integration. The behaviour integrators of
:code:`mfem-mgis` support the integration by batches.

Consistency checks
------------------

The following combinations are refused, with an error message, at the
beginning of each resolution (method :code:`solve` of the problem):

- gradients computed by kernels with the integration point by point: the
  computation of the gradients by kernels requires
  :code:`BehaviourIntegration` set to :code:`Batch`;
- a behaviour generated by the :code:`generic-parallel` interface
  integrated point by point: such a behaviour can only be integrated by
  batches;
- a behaviour integrator, a mesh or a finite element space which does not
  support the computations by kernels (see
  :ref:`mfem_mgis_batch_computations_supported`) with any of
  :code:`GradientsComputation`, :code:`InnerForcesComputation` or
  :code:`TangentOperatorComputation` set to another value than
  :code:`ElementByElement`;
- the integration by batches, or the inner forces or the tangent operator
  computed by kernels, when the solvers of :code:`PETSc` are used.

Integration rules
=================

Each behaviour integrator chooses the integration rule of the elements of
its material. The optional parameter :code:`IntegrationRuleOrder` of the
finite element discretization, a non negative integer, replaces this rule
by the rule of :code:`MFEM` of the given order for the geometry of the
element. A rule having a weight which is not positive (some rules of
:code:`MFEM` for the simplices) is refused.

A lower order reduces the number of integration points, hence the number
of behaviour integrations and the work of the kernels. For instance, the
standard mechanical behaviour integrators use 27 points on the hexahedra
of order 1 by default, and 8 points with :code:`IntegrationRuleOrder` set to 3. On
a mesh of affine hexahedra, both rules integrate the elastic stiffness
exactly. The parameter is also used by the integration point by point.
Like the other parameters of the finite element discretization, it can be
given to the constructor of the nonlinear evolution problem (see
:ref:`mfem_mgis_batch_computations_example`).

What can be computed by kernels
===============================

Behaviours
----------

The kernels compute the gradients of the behaviours from the values and
the derivatives of the unknowns at the integration points, then the inner
forces and the stiffness matrices of the elements from the thermodynamic
forces and the tangent operator blocks. The following behaviours are
supported, in :math:`3D`, in plane strain and in plane stress:

- standard small strain mechanical behaviours (linearised strain);
- standard finite strain mechanical behaviours (deformation gradient);
- stationary nonlinear heat transfer behaviours (temperature gradient),
  the temperature at the integration points, computed from the unknowns,
  being an external state variable of the behaviour;
- the transient term of the heat equation (behaviour integrator
  :code:`TransientHeatTransfer`), whose gradient is the temperature at the
  integration point;
- micromorphic damage behaviours (micromorphic damage and its gradient).

Regularizations
---------------

The FBar formulation and the regularization of Faltus et al. (see
:doc:`behaviour_integrators`) are supported in :math:`3D` and in
plane strain. The regularization of Faltus et al. is not computed by
kernels in plane stress, where the axial component of the deformation
gradient is not given by the unknowns.

- With the FBar formulation, the stiffness matrices depend on the current
  estimate of the unknowns: the tangent operator can only be computed by
  kernels if the gradients are computed by kernels.
- With the regularization of Faltus et al., the inner forces depend on the
  current estimate of the unknowns: they can only be computed by kernels
  if the gradients are computed by kernels.

Meshes and finite element spaces
--------------------------------

The computations by kernels require:

- a mesh made of a single geometry (no mixing of hexahedra and
  tetrahedra, for instance), which is not a NURBS mesh, and whose elements
  have the dimension of the space (no surface mesh in :math:`3D`, for
  instance);
- a finite element space of uniform order whose shape functions are
  mapped by value (:code:`H1`);
- a behaviour integrator on each material of the mesh, all the elements
  of a material using the same integration rule.

The inverses and the determinants of the jacobians of the element
transformations are computed once for each integration rule: they are not
updated if the mesh is modified (refinement, displacement of the nodes or
of the vertices).

.. _mfem_mgis_batch_computations_other_integrators:

Boundary conditions and other integrators
-----------------------------------------

With the inner forces computed by kernels, the boundary conditions which
do not depend on the unknowns (:code:`UniformImposedPressure` and
:code:`UniformHeatSource`) are not integrators of the nonlinear form:
their contributions are added to the inner forces (see
:ref:`mfem_mgis_boundary_conditions`).

The other integrators of the nonlinear form (for instance the ones of a
boundary condition depending on the unknowns, such as a Robin boundary
condition given as a boundary face integrator) are handled as follows:

- the contributions of the domain, boundary and boundary face integrators
  are evaluated on the host by the loops of :code:`MFEM` restricted to
  them (markers of the attributes included), and added to the inner forces
  computed by kernels and, with :code:`TangentOperatorComputation` set to
  :code:`Kernels`, to the local matrix assembled by kernels. On a GPU, the
  inner forces and the values of the local matrix are copied to the host
  at each evaluation;
- if the nonlinear form contains interior face integrators, or uses an
  extension of :code:`MFEM`, the residual is assembled by :code:`MFEM`,
  the inner forces computed by kernels being added to it, and the
  stiffness matrices computed by kernels are assembled with the
  contributions of the other integrators by the element loop of
  :code:`MFEM`;
- with :code:`TangentOperatorComputation` set to :code:`MatrixFree`, the
  resolution fails: the tangent operator applied without assembly requires
  that the nonlinear form only contains the integrator of
  :code:`mfem-mgis`.

Assembly and application of the tangent operator
================================================

Assembly by kernels
-------------------

With :code:`TangentOperatorComputation` set to :code:`Kernels`, and a
nonlinear form without interior face integrators nor extension of
:code:`MFEM`, the tangent operator is assembled as follows:

- the local matrix of the tangent operator, on the local vector of the
  finite element space, is created at the first assembly. Its pattern
  contains the couplings between the degrees of freedom of each element.
  In each row, the diagonal entry comes first, then the other columns,
  sorted, which is the ordering of :code:`hypre`;
- at each assembly, the stiffness matrices of the elements are added to
  this matrix by kernels, without being stored. With a device of
  :code:`MFEM`, the additions are atomic, the elements sharing degrees of
  freedom; without device, the elements are processed one after the other
  on the host. Unless the device of :code:`MFEM` is a :code:`CUDA`,
  :code:`HIP` or :code:`debug` device, the positions of the entries of the
  stiffness matrices in the rows of the matrix are computed at the first
  assembly, and read by the following ones instead of searching for the
  entries in their rows. They are computed again (three times at most) if
  the columns of the rows are reordered, for instance by a direct solver.
  They take two bytes per entry of the stiffness matrices of the
  elements;
- with :code:`TangentOperatorAssembly` set to :code:`Ordered`, the
  stiffness matrices of all the elements are first stored element by
  element (:math:`n^{2}` values per element, :math:`n` being the number of
  degrees of freedom of an element), then added to the matrix by one
  thread per row, which adds the contributions to its row in a fixed
  order: by element, then by row and column of the stiffness matrices of
  the elements. The values of the matrix are then the same at each
  assembly, also on a GPU, where the order of the atomic additions changes
  from one run to the next, and with it the last digits of the results.
  In the sequential computations of the tests of :code:`mfem-mgis` on a
  GPU, the results are then the same at each run; other operations, such
  as the products of :code:`hypre` on several processes, may still change
  their last digits. This also applies to the elastic operator of the
  fixed point solver. The stiffness matrices of all the elements must fit
  in an array of :code:`MFEM` (fewer than :math:`2^{31}` values). The
  parameter has no effect when the stiffness matrices are computed element
  by element;
- the contributions of the other integrators of the nonlinear form, if
  any, are added to this matrix on the host (see
  :ref:`mfem_mgis_batch_computations_other_integrators`);
- in a sequential computation, the matrix is replaced by
  :math:`P^{T}\,A\,P` on a non conforming mesh, :math:`P` being the
  prolongation of the finite element space, then the essential degrees of
  freedom are eliminated, their
  diagonal being set to one;
- in parallel, the global matrix is built from the local matrices of the
  processes, as by :code:`mfem::ParNonlinearForm::GetGradient`, and the
  essential degrees of freedom are eliminated, their diagonal being set to
  one.

In parallel, when :code:`hypre` does not compute on a GPU and each row of
the prolongation of the finite element space has a single entry, equal to
one (conforming mesh), the pattern of the global matrix and the exchanges
between the processes are computed at the first assembly and kept: the
following assemblies only copy, exchange and add the values. This setup is
performed again if the pattern of the local matrix changes or if the finite
element space is updated. Otherwise, the global matrix is computed by the
triple product of :code:`hypre` at each assembly.

.. _mfem_mgis_batch_computations_matrix_free:

Application without assembly
----------------------------

With :code:`TangentOperatorComputation` set to :code:`MatrixFree`, the
tangent operator is applied by kernels on the true degrees of freedom,
from the tangent operator blocks of the last integration of the
behaviours, without being assembled:

.. math::

   y = P^{T}\,\left(\sum_{e} B^{T}\,K\,B\,w\,\det J\right)\,P\,x

where :math:`P` is the prolongation of the finite element space. The
essential degrees of freedom are constrained as by
:code:`mfem::ConstrainedOperator`. The diagonal of the operator is also
computed by kernels; on a non conforming mesh, it is approximated as by
:code:`mfem::BilinearForm::AssembleDiagonal`.

The linear systems are then solved by an iterative solver of
:code:`MFEM` (for instance :code:`CGSolver`), with a preconditioner which
does not require the assembled operator (see :doc:`glossary`):

- :code:`OperatorJacobiSmoother` and :code:`OperatorChebyshevSmoother`,
  which only use products by the operator and its diagonal;
- :code:`AssembledOperator`, which sets up another preconditioner, for
  instance :code:`HypreBoomerAMG`, on the tangent operator assembled by
  kernels. The setup is performed every :code:`UpdatePeriod` calls (one by
  default), and again when the tangent operator has been assembled again
  in between. The other calls keep the setup, which then preconditions a
  nearby operator.

The following snippet, for a parallel computation, preconditions the
conjugate gradient of :code:`MFEM` by :code:`HypreBoomerAMG` set up on the
assembled tangent operator every two calls:

.. code:: c++

   problem.setLinearSolver(
       ctx, "CGSolver",
       {{"RelativeTolerance", 1e-10},
        {"MaximumNumberOfIterations", 1000},
        {"Preconditioner",
         mfem_mgis::Parameters{
             {"Name", "AssembledOperator"},
             {"Options",
              mfem_mgis::Parameters{
                  {"UpdatePeriod", 2},
                  {"Preconditioner",
                   mfem_mgis::Parameters{{"Name", "HypreBoomerAMG"}}}}}}}}) |
       or_die;

The tangent operator of the stationary heat transfer behaviours is
negative definite
(:math:`\vec{j}=-k\,\vec{\nabla} T`), while the diagonal of the essential
degrees of freedom is set to one: the conjugate gradient is not suited,
and :code:`GMRESSolver` can be used instead.

Prediction
----------

With the integration by batches, the inner forces computed by kernels and
:code:`TangentOperatorComputation` set to :code:`Kernels` or
:code:`MatrixFree`, the operator and the inner forces of the prediction
(see :ref:`mfem_mgis_nonlinear_algorithms`) are also computed by kernels,
the operator being assembled, if no boundary condition contributes to the
operator of the prediction and, in a sequential computation, if the mesh
is conforming.

.. _mfem_mgis_batch_computations_post_processings:

Post-processings
----------------

The computations on functions defined at the integration points used by
the post-processings are also made by kernels, on the device if a device
is enabled, when the environment variable
:code:`MFEM_MGIS_POST_PROCESSINGS_COMPUTATION` is :code:`Kernels`
(:code:`ElementByElement` by default; the variable is read at each
computation, and an invalid value is reported by
:code:`mfem_mgis::initialize`):

- :code:`computeMeasure` and :code:`computeIntegral`: reduction over the
  elements, for the behaviour integrators which support kernels (the
  weight of an integration point is then :code:`w det J`);
- :code:`computeL2Projection` and
  :code:`computeImplicitGradientRegularization`: right-hand sides by a
  kernel; for the L2 projection, mass matrices computed by a kernel and
  assembled by :code:`MFEM` (:code:`AssemblyLevel::FULL`), on the device
  if a device is enabled; the operator of the implicit gradient
  regularization is assembled element by element;
- :code:`updateGridFunction`, used by the exports of the results at the
  nodes (:code:`ParaviewExportIntegrationPointResultsAtNodes`): local
  projections by a kernel, then arithmetic mean at the nodes through the
  element restriction and, in parallel, the prolongation.

The other cases are computed element by element: functions defined on
boundaries or on a part of the mesh, integration rules differing between
the elements of a material, elements of different geometries, finite
element spaces other than the Lagrange elements (Bernstein basis
included), devices of :code:`libCEED` for the L2 projections, and, for the
values at the nodes, non conforming meshes and elements with more than 32
degrees of freedom (hexahedra of order 3, for instance). In parallel, the
choice is made by all the processes. The mesh is not modified (no nodes
are given to a mesh without nodes). The values at the nodes and the
projections computed on the device are valid on the device, and copied on
the host when read there.
:code:`getNumberOfPostProcessingsComputationsByKernels`
(:code:`MFEMMGIS/PostProcessingsComputation.hxx`) counts the computations
made by kernels. The results only differ from the ones computed element
by element by rounding errors. The values of the functions are gathered
on the host, where the functions of the user are stored, then used on the
device. The kernels are declared in
:code:`MFEMMGIS/Batch/IntegrationPointsFunctions.hxx`.

.. _mfem_mgis_batch_computations_gpu:

Computations on a GPU
=====================

Requirements
------------

The kernels run on a GPU when :code:`MFEM` is compiled with :code:`CUDA`:
the sources of :code:`mfem-mgis` containing kernels are then compiled as
:code:`CUDA` code (see :doc:`../installation_guide/installation_guide`).
When :code:`MFEM` is compiled with :code:`HIP`, these sources are not
compiled, and the computations by kernels are refused.

Selection of the device
-----------------------

The device of :code:`MFEM` is created by :code:`mfem_mgis::initialize`,
from:

- the option :code:`--device` (or :code:`-dev`), declared by
  :code:`mfem_mgis::declareDefaultOptions`, whose value is a configuration
  of the device of :code:`MFEM` (for instance :code:`cuda`, or
  :code:`debug`);
- otherwise, the environment variable :code:`MFEM_MGIS_DEVICE`, if no
  device of :code:`MFEM` is already configured.

No device is created by default. The processes of a node are assigned the
GPUs of the node in a round-robin manner (several processes may share a
GPU). On a GPU, each profiling section waits for the end of the kernels
launched on the GPU before it is closed.

The memory of the host is the standard one, and the memory of the device
the default one of :code:`MFEM` (:code:`Umpire` if :code:`MFEM` is
compiled with it), unless the environment variable :code:`MFEM_MEMORY` of
:code:`MFEM` gives them. :code:`MFEM` compiled with :code:`Umpire`
otherwise also allocates the memory of the host with :code:`Umpire`, which
records each allocation, including the temporaries of the loops over the
elements made on the host: on the bubble of :code:`mm-opera-hpc` on a GPU,
the post-processings (export of the stresses at the nodes, L2 projection)
took 60.8 s instead of 10.5 s. :code:`MFEM_MEMORY=umpire` restores this
behaviour, :code:`MFEM_MEMORY=host` uses the standard memory of the host
and the memory of the device allocated by the runtime of the GPU, without
pool. An application which creates its own :code:`mfem::Device` keeps the
choice of :code:`MFEM`, unless it calls
:code:`mfem::Device::SetMemoryTypes` before.

The :code:`debug` device of :code:`MFEM` keeps the copies of the arrays
"on the device" in a separate memory of the host, and detects the accesses
to invalid copies, which allows checking the memory accesses of the
kernels without a GPU.

Integration of the behaviours on the device
-------------------------------------------

A behaviour is integrated on the device when the device of :code:`MFEM`
is a :code:`CUDA`, :code:`HIP` or :code:`debug` device, the behaviour is
integrated by batches, it is generated by the
:code:`generic-parallel` interface of :code:`MFront`, and its computations
can access the memory of the device. For a GPU, the behaviour is compiled
for this GPU, for instance with the configuration file
:code:`config-cuda-nvcc.json` distributed with :code:`TFEL` (in
:code:`share/tfel/mfront/configuration-files`):

.. code:: sh

   mfront --obuild --interface=generic-parallel \
          --configuration-file=config-cuda-nvcc.json Behaviour.mfront

The library is named after the :code:`@Library` keyword of the
:code:`MFront` file, or else after its :code:`@Material` keyword, followed
by the backend given by the configuration file. Without these keywords, the
command above produces :code:`src/libGenericParallelBehaviour-cuda.so`.

The behaviours generated with the configuration files :code:`config-cuda-nvcc.json`,
:code:`config-cuda-clang.json`, :code:`config-hip-hipcc.json` and
:code:`config-hip-clang-nvidia-platform.json` run on a NVIDIA GPU in
:code:`mfem-mgis`. The ones generated with :code:`config-kokkos.json`
require :code:`Kokkos` to be initialized: :code:`mfem-mgis` built with the
option :code:`enable-kokkos` initializes it with the option
:code:`--kokkos` (see :doc:`../installation_guide/installation_guide`).
The ones generated with the :code:`SYCL` configurations require a
:code:`SYCL` queue given by the program, and the ones generated by the
compilers of :code:`NVIDIA HPC SDK` (:code:`stlpar` and :code:`openmp`
backends with offloading) use a runtime of :code:`OpenMP` which conflicts
with the one of :code:`GCC`, loaded by :code:`MFEM` and :code:`mfem-mgis`
built by :code:`GCC`.

The behaviour is then integrated by :code:`MGIS` on the copies of the
arrays of the material on the device. The material properties and the
external state variables are copied to the device at each integration;
for an orthotropic behaviour, the rotations are performed on the device.
The update and the revert of the state of the material are performed on
the device, then the arrays are synchronized on the host.

A point-wise model (:code:`PointWiseModel`) generated by the
:code:`generic-parallel` interface for the device is integrated in the same
way, by batches on the device, whatever the parameter
:code:`BehaviourIntegration`; its update and its revert are performed on
the host. After its integration, the copies of its arrays on the host are
made valid for reading: the other models may read its states on the host,
for instance as external state variables given with the
:code:`EXTERNAL_STORAGE` mode.

The other behaviours (generated by the :code:`generic` interface, or by
the :code:`generic-parallel` interface for the host, with the
:code:`openmp` or :code:`stlpar` backends) are integrated on the host:
their arrays are copied between the host and the device when the kernels
need them. With the :code:`debug` device, the behaviours generated by the
:code:`generic-parallel` interface for the host are integrated on the
copies of the arrays on the device, which are in the memory of the host.

The arrays of the materials stay on the device during a resolution when
all the behaviours are integrated on the device and the gradients, the
inner forces and the tangent operator are computed by kernels:

- :code:`BehaviourIntegration` set to :code:`Batch`;
- :code:`GradientsComputation` and :code:`InnerForcesComputation` set to
  :code:`Kernels`;
- :code:`TangentOperatorComputation` set to :code:`Kernels` or
  :code:`MatrixFree`.

Otherwise, the arrays of the materials are copied between the host and
the device at each integration of the behaviours.

hypre on the GPU
----------------

:code:`hypre` computes on the GPU when it is built with the support of
GPUs and its memory is located on the device (see
:code:`mfem::HypreUsingGPU`). In this case:

- the strategy :code:`Elasticity` of :code:`HypreBoomerAMG` is replaced by
  the strategy :code:`System`, with a warning;
- the level of fill of :code:`HypreILU` is zero by default, and a greater
  level is refused (see :doc:`glossary`);
- :code:`HypreParaSails`, which only computes on the host, is refused;
- the global tangent operator assembled by kernels is computed by the
  triple product of :code:`hypre` at each assembly.

The size of the pool of memory allocated at once by :code:`hypre` on the
GPU, through :code:`Umpire`, is given in GiB by the option
:code:`--hypre-device-pool-size` (or :code:`-hdps`), declared by
:code:`mfem_mgis::declareDefaultOptions`, or by the environment variable
:code:`MFEM_MGIS_HYPRE_DEVICE_POOL_SIZE`. Each process has its own pool,
whose size is 4 GiB by default in :code:`hypre` 3.2. The size is set
before the first allocation of :code:`hypre` on the GPU. If :code:`hypre`
does not use a pool of :code:`Umpire` on the GPU, the option is refused,
and the environment variable is ignored with a warning.

For small linear systems, whose resolutions on a GPU are dominated by the
launches of kernels, :code:`hypre` may compute on the host while the
behaviours and the computations of :code:`MFEM` and of :code:`mfem-mgis`
stay on the GPU: option :code:`--hypre-on-host` (or :code:`-hoh`, and
:code:`--no-hypre-on-host` or :code:`-no-hoh` to cancel it), declared by
:code:`mfem_mgis::declareDefaultOptions`, or environment variable
:code:`MFEM_MGIS_HYPRE_ON_HOST` (any non empty value other than
:code:`0`). :code:`MFEM` then copies the matrices and the vectors given to
:code:`hypre` on the host, and :code:`mfem::HypreUsingGPU` is false: the
restrictions listed above do not apply. The option
:code:`--hypre-device-pool-size` is then refused. The option requires
:code:`hypre` 2.31.0 or later when :code:`hypre` is built with GPU
support. :code:`PETSc` may make :code:`hypre` use the GPU again
(conversion of its matrices located on a GPU for the preconditioners of
:code:`hypre`).

Direct solver on the GPU
------------------------

When :code:`MFEM` is built with :code:`cuDSS`, the direct solver
:code:`CuDSSSolver` of the factory of linear solvers factorizes the
matrices on the GPU (see :doc:`glossary` for its parameters and
requirements). With the parameter :code:`ReuseAnalysis`, the analysis
(ordering and symbolic factorization) of the first matrix is reused for
the next ones while their pattern does not change, as the tangent
operators of the successive Newton iterations: only the numerical
factorization is then made at each iteration.

On small systems, whose iterative resolutions on a GPU are dominated by
the launches of kernels, the direct solver is much faster than the Krylov
solvers of :code:`hypre`: on one GPU, a factorization of a mechanical
matrix of 28 548 unknowns takes about 20 ms with the reuse of the
analysis, and a resolution a few milliseconds. On large three-dimensional
problems, the fill-in of the factorization costs more than an algebraic
multigrid: on a mechanical problem of 111 843 unknowns, a factorization
takes about 0.24 s, against about 70 ms for a resolution by
:code:`HyprePCG` preconditioned by :code:`HypreBoomerAMG`.

.. _mfem_mgis_batch_computations_amgx:

AmgX
----

When :code:`mfem-mgis` is built with the CMake option :code:`enable-amgx`
(which requires :code:`MFEM` compiled with :code:`CUDA`, :code:`AmgX`
being found with :code:`AMGX_DIR`), the solvers of the :code:`AmgX`
library are available:

- :code:`AmgX`, as a linear solver or as a preconditioner: cycles of the
  algebraic multigrid of :code:`AmgX`, an approximate solver, like
  :code:`HypreBoomerAMG`. Its default configuration is the one of
  :code:`MFEM`;
- :code:`AmgXPCG`, as a linear solver: the conjugate gradient of
  :code:`AmgX`, preconditioned by one V-cycle of its algebraic multigrid.

:code:`AmgX` computes on the current GPU of the process, regardless of the
device of :code:`MFEM`. The local rows of the matrix are uploaded from the
host at each setup, and the resolutions start from a zero initial guess.

.. list-table::
   :header-rows: 1
   :widths: 25 75

   * - Option
     - Description
   * - :code:`Configuration`
     - Configuration of :code:`AmgX`, as a string (:code:`AmgX` only).
       Exclusive with :code:`ConfigurationFile`. A configuration given
       defines all the parameters of :code:`AmgX`: :code:`VerbosityLevel`
       and :code:`AmgXParameters` are then refused.
   * - :code:`ConfigurationFile`
     - File containing the configuration of :code:`AmgX` (:code:`AmgX`
       only), with the same restrictions as :code:`Configuration`.
   * - :code:`AmgXParameters`
     - Parameters of :code:`AmgX`, with their names in :code:`AmgX`, which
       complete or override the default configuration. A name without
       scope is given the scope :code:`amg` (multigrid), a name
       :code:`scope:name` is given as is. For :code:`AmgXPCG`, the
       parameters of the scope :code:`main` (conjugate gradient) are given
       by the other options, and refused.
   * - :code:`Precision`
     - :code:`Double` (default) or :code:`Single`: computations of
       :code:`AmgX` in single precision, the vectors exchanged with
       :code:`MFEM` being converted.
   * - :code:`VerbosityLevel`, :code:`RelativeTolerance`,
       :code:`AbsoluteTolerance`, :code:`MaximumNumberOfIterations`
     - Options of :code:`AmgXPCG`, by default 0, :math:`10^{-12}`, 0 and
       150. :code:`AmgX` only accepts :code:`VerbosityLevel`.

The convergence criteria of :code:`AmgX` have a floor: the relative
tolerance of :code:`AmgXPCG` must be at least :math:`10^{-12}` in double
precision and :math:`10^{-6}` in single precision, and its absolute
tolerance at least :math:`10^{-20}`. In single precision, a relative
tolerance is required, and an absolute tolerance is refused.

Nonlinear solvers
=================

The :code:`NewtonK0` method of the :code:`FixedPoint` nonlinear solver (see
:ref:`mfem_mgis_fixed_point_algorithm`) inverts the consistent tangent
operator by an iterative solver of :code:`MFEM`, preconditioned by the
linear solver of the elastic operator, whose setup is kept. The tangent
operator can then be applied without assembly.

.. _mfem_mgis_batch_computations_example:

Example
=======

In a program
------------

The following snippet builds a parallel mechanical problem whose
behaviours are integrated by batches, the gradients, the inner forces and
the tangent operator being computed by kernels, the latter being applied
without assembly. The behaviour library,
:code:`src/libGenericParallelBehaviour-cuda.so`, is generated by the
:code:`generic-parallel` interface for the GPU (see
:ref:`mfem_mgis_batch_computations_gpu`). The program
calls :code:`mfem_mgis::initialize` and declares the default options, so
that the device is selected on the command line:

.. code:: c++

   mfem_mgis::initialize(argc, argv);
   auto args = mfem::OptionsParser(argc, argv);
   mfem_mgis::declareDefaultOptions(args);
   args.Parse();
   auto ctx = mfem_mgis::Context{};
   auto or_die = ctx.getFatalFailureHandler();
   auto problem =
       mfem_mgis::construct<mfem_mgis::NonLinearEvolutionProblem>(
           ctx, mfem_mgis::Parameters{
                    {"MeshFileName", "cube.mesh"},
                    {"FiniteElementFamily", "H1"},
                    {"FiniteElementOrder", 1},
                    {"UnknownsSize", 3},
                    {"IntegrationRuleOrder", 3},
                    {"Materials", mfem_mgis::Parameters{{"Cube", 1}}},
                    {"Boundaries", mfem_mgis::Parameters{{"Xmin", 5},
                                                         {"Xmax", 3}}},
                    {"Hypothesis", "Tridimensional"},
                    {"BehaviourIntegration", "Batch"},
                    {"GradientsComputation", "Kernels"},
                    {"InnerForcesComputation", "Kernels"},
                    {"TangentOperatorComputation", "MatrixFree"},
                    {"Parallel", true}}) |
       or_die;
   problem.addBehaviourIntegrator(ctx, "Mechanics", "Cube",
                                  "src/libGenericParallelBehaviour-cuda.so",
                                  "IsotropicLinearHardeningPlasticity") |
       or_die;
   problem.setLinearSolver(
       ctx, "CGSolver",
       {{"RelativeTolerance", 1e-10},
        {"MaximumNumberOfIterations", 1000},
        {"Preconditioner",
         mfem_mgis::Parameters{
             {"Name", "AssembledOperator"},
             {"Options",
              mfem_mgis::Parameters{
                  {"Preconditioner",
                   mfem_mgis::Parameters{{"Name", "HypreBoomerAMG"}}}}}}}}) |
       or_die;

The program is then run with the option :code:`--device`:

.. code:: sh

   mpirun -n 2 ./simulation --device cuda

With an existing executable
---------------------------

For an existing executable calling :code:`mfem_mgis::initialize`, the
environment variables give the device and the default values of the
parameters which are not set by the program:

.. code:: sh

   export MFEM_MGIS_DEVICE=cuda
   export MFEM_MGIS_BEHAVIOUR_INTEGRATION=Batch
   export MFEM_MGIS_GRADIENTS_COMPUTATION=Kernels
   export MFEM_MGIS_INNER_FORCES_COMPUTATION=Kernels
   export MFEM_MGIS_TANGENT_OPERATOR_COMPUTATION=Kernels
   mpirun -n 2 ./simulation

The value :code:`Kernels` of the tangent operator keeps an assembled
matrix, which suits the linear solver chosen by the program, for instance
a direct solver. The behaviours are integrated on the GPU only if their
libraries are generated by the :code:`generic-parallel` interface for the
GPU; otherwise, they are integrated on the host, the other computations
being performed on the GPU.

Limitations
===========

- The kernels are not compiled when :code:`MFEM` is compiled with
  :code:`HIP`.
- The integration by batches and the computations by kernels of the inner
  forces and of the tangent operator are not supported with the solvers of
  :code:`PETSc`.
- The computations by kernels require a mesh made of a single geometry, a
  finite element space of uniform order mapped by value (:code:`H1`), and
  a mesh which is not modified after the first computation (see
  :ref:`mfem_mgis_batch_computations_supported`).
- The regularization of Faltus et al. is not computed by kernels in plane
  stress.
- The tangent operator applied without assembly requires a nonlinear form
  which only contains the integrator of :code:`mfem-mgis`.
- The arrays of a material read by another material on the host, as
  material properties or external state variables given with the
  :code:`EXTERNAL_STORAGE` mode, are not synchronized by
  :code:`mfem-mgis` when the first material is integrated on the device,
  except for the point-wise models: the program synchronizes them before
  the integration of the second material (see
  :code:`Material::synchronizeOnHostForReading`), as the example ex8 of
  :code:`mfem-mgis-examples` does for the deformation gradients read by its
  heat transfer behaviours.
- The post-processings read the materials on the host: the arrays of the
  materials are synchronized on the host before their execution, keeping
  their copies on the device valid. After a computation on the device, a
  direct access to the states (:code:`s0`, :code:`s1`) or to the tangent
  operator blocks (:code:`K`) of a material must be preceded by a call to
  its method :code:`synchronizeOnHost`, or :code:`synchronizeOnHostForReading`
  for a read-only access. The accessors of :code:`mfem-mgis`, such as
  :code:`getInternalStateVariable`, make this call.
- The positions of the entries of the stiffness matrices, which avoid
  searching for the entries in the rows of the matrix, are not used with
  the :code:`CUDA`, :code:`HIP` and :code:`debug` devices of :code:`MFEM`,
  and the global matrix whose pattern and exchanges are kept is not used
  when :code:`hypre` computes on the GPU.
- :code:`AmgX` requires :code:`MFEM` compiled with :code:`CUDA`; the matrix
  is uploaded from the host at each setup of its solvers.
