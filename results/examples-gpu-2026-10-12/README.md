# Examples ex1, ex2, ex3, ex5, ex6 and ex7 by batches and on the GPU (12/10/2026)

Six examples of mfem-mgis-examples that the prototype did not follow yet
(ex4 and ex8 already were), with their behaviours generated by the
`generic-parallel` interface:

| Example | Problem | Behaviour | Check of the example |
|---|---|---|---|
| ex1 | cyclic uniaxial tension of a cube (sources installed by mfem-mgis) | plasticity with linear hardening | gradient, force and cumulated plastic strain of each step against the reference |
| ex3 | cube with two layers, six load cases (sources installed by mfem-mgis) | linear elasticity | solution against the analytical solution |
| ex7 | RVE of MOX, one spherical inclusion, periodic conditions, quadratic tetrahedra, GMRES and BoomerAMG | Norton with a threshold (implicit) | mean stresses per material against the reference (relative tolerance 1e-4), 5 steps |
| ex6 | RVE of two layers, periodic conditions, imposed macroscopic deformation gradient, PCG and BoomerAMG | Saint Venant-Kirchhoff | gradient and Piola-Kirchhoff stress at each point against the analytical solution (1e-10) |
| ex2 | ssna303 in plane strain, finite strain (Hencky), MUMPS, without and with FBar | plasticity with linear hardening | force on the upper boundary against the reference, 2 steps |
| ex5 | Satoh plate in plane strain, parabolic temperature imposed at the points, sequential problem, UMFPack | thermoelasticity | temperature seen by the behaviour at each point (1e-9 K) and reactions of the clamped boundaries (1e-8) |

Options added to the examples (mfem-mgis-examples 2d67da3 and b602495):
`-l` (library of the behaviour) for ex2 and ex5, options of mfem-mgis
(`declareDefaultOptions`, including `--device`) for ex6 and ex5. ex1 and
ex3, whose sources are tests of mfem-mgis, already have `-l`; the device
is given to them by the variable `MFEM_MGIS_DEVICE`.

Tests (`cases/ex1`, `cases/ex2`, `cases/ex3`, `cases/ex5`, `cases/ex6`,
`cases/ex7`, build `build/cases-post`, mfem-mgis 9338554cd7): point by point,
everything by kernels with the behaviour of the example, by batches with
the openmp and stlpar backends, and on the GPU (cuda, 2 processes for ex2,
ex6 and ex7, one process for ex1, ex3 and ex5).

| Example | CPU | GPU |

| ex1 | 4/4 | 1/1 |
| ex3 (six cases) | 24/24 | 6/6 |

## Measurements: complete ex7 (40 steps)

RVE of MOX, 656 quadratic tetrahedra, 2,634 unknowns, 109 Newton
iterations (149 evaluations of the residual) in all cases. Processes placed
on cores 4 to 7 (one core per process), one run (two on the GPU). Total
durations and commands: `measure/durations.txt`; timing tables of
mfem-mgis: `measure/*.txt`.

| Variant | Total (s) | Solution (s) | Jacobian (s) | Linear solver (s) |
|---|---|---|---|---|
| CPU, 1 process, point by point | 15.1 | 14.3 | 4.69 | 3.26 |
| CPU, 1 process, kernels | 8.0 | 7.3 | 1.22 | 3.18 |
| CPU, 2 processes, point by point | 10.1 | 9.3 | 2.64 | 3.43 |
| CPU, 2 processes, kernels | 6.3 | 5.5 | 0.60 | 3.39 |
| CPU, 2 processes, openmp batches | 6.1 | 5.5 | 0.60 | 3.38 |
| GPU, 1 process, cuda batches | 6.5 to 6.8 | 5.6 to 5.7 | 0.44 | 4.96 to 5.07 |

- The kernels divide the time on the CPU by 2 (Jacobian by 4).
- On the GPU, the integration and the Jacobian cost almost nothing any
  more, but GMRES and BoomerAMG on the GPU take 5.0 s against 3.2 s on one
  core: the system (2,634 unknowns) is too small for the GPU, like the
  thermal of ex8 (`results/ex8-thermal-gpu-2026-10-11`).
- Measurement trap found on the way: with `scripts/env.sh`
  (`OMP_PROC_BIND=spread`), `mpirun --bind-to none taskset -c ...` puts
  all the processes on the same core (ex7 with 5 steps: 95 s instead of
  2.6 s). The measurement scripts of the prototype
  (`cases/measure-common.sh`) do not use it; here, `taskset` is put around
  `mpirun`, which binds one process per core.

## Static variables of quantities on the GPU

The behaviour of ex5 did not compile for CUDA: its static variable
`@StaticVariable temperature Tref` (with `@UseQt true`) is a constexpr
member of a class type, and `T + dT - Tref` binds a reference to it in the
GPU code, which nvcc refuses ("identifier Tref is undefined in device
code"). Fix in TFEL (837338523, f1ff18259 and d22416824 after review):
MFront writes the static variables `TFEL_STATIC_VARIABLE(v)`, a macro of
`TFELConfig.hxx` that gives the variable itself in the host code
(unchanged) and a copy initialised by a constant expression,
`(decltype(v){v})`, in the GPU code
(`reproducers/mfront-static-quantity-cuda`). Second review (bf143cf46):
stiffness recomputed by the Runge-Kutta algorithms and constants of
rkCastem written with the macro (the six algorithms and rkCastem with
`@UseQt true` failed in CUDA), and Runge-Kutta modifiers returned by value
(a static lambda kept the name of the first behaviour processed by a call
of MFront).

- Test behaviour `StrainHardeningCreep3` of TFEL (0f58645c7): a null
  static strain rate used at run time in the flow rule. With the old
  MFront, the CUDA configuration fails; with the fix, comparisons
  openmp-host-gcc 10/10 and cuda-nvcc 11/11.
- Five test behaviours of TFEL with static variables,
  `StrainHardeningCreep3` and the behaviour of ex5 compile for the
  `generic` interface and for CUDA. The ten behaviours written by the
  review for the corner cases (address, `std::ref`, non-constant
  references, function that returns a reference) compile on the host as
  before.
