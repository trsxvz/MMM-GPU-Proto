Copy of `scratch/tangent/RESULTS.md` (scripts and raw results in `scratch/tangent`, not tracked).


**Correction (evening of 21/11).** The GPU measurements of the first
sections were made with the fields stored point by point, the default of
behaviour-bench at that time, while mfem-mgis stores them component by
component on the GPU (`QuadratureDataLayout`: `Automatic`). They were
redone in this layout (last section); the benches now use the layout of
mfem-mgis by default (component by component on the GPU, point by point on
the CPU). The measurements on the CPU were made in the right layout. The
"gain" of the component by component layout found below is not one: it is
the default of mfem-mgis on the GPU.

- GPU law: RTX 5080, 2^20 points (float), 2^18 (double, FP64 1:64),

The 16 % attributed to the conversion by the profile of the night does not
come from the arithmetic of the conversion: its intermediate tensors stay
in registers. Tangent operator requested (float, code of MFront): DTAU_DDF
(native) 6.86 ms, DSIG_DF (two conversions) 7.01 ms, DPK1_DF 8.14 ms, no
tangent operator 3.54 ms: the 1.13 ms between DSIG_DF and DPK1_DF are still
to be located.

## The 1.13 ms between DSIG_DF and DPK1_DF (float, RTX 5080, 2^20 points)

Same binary (code generated by MFront), only the requested tangent
operator changes. Nsight Compute, integration kernel, 2^18 points:
DSIG_DF 2.10 ms, DPK1_DF 2.39 ms (+14 %); per point: local stores
9,696 -> 12,078 B (hardware counter; +218 B by the stores of the threads,
SASS), global store sectors 72 -> 99, warp instructions +6 %
(`results-ncu-tangent-kinds.txt`).

By source line (`diff-chains.py`, `stall-reasons.py`, without the line
directives of the generated code): the conversion DSIG_DF -> DPK1_DF and
the store of its 81 values in the variant `Dt` (generated line 1037), the
copy of `Dt` in the buffer of the runtime (`ArrayCommonMethods.ixx:150`)
and the writes in global memory (`Integrate.hxx:197`) make about a third of
the additional stall samples. The other two thirds are spread over the
whole kernel: the LU solver, for instance, executes the same instructions
but waits longer for its values in the stack (long scoreboard +13 %).

Experiments (`results-sum-soa.txt`, `results-tangent-soa.txt`):
- one value written per point (sum of the components): the gap goes from
  1.12 to 0.82 ms: the 27 additional writes in global memory cost 0.3 ms;
- tangent operator alone stored component by component (writes of a warp
  coalesced): DSIG_DF 7.0 -> 6.48 ms (-7 %), DPK1_DF 8.14 -> 7.40 ms (-9 %);
  the gap between DSIG_DF and DPK1_DF stays at 0.9 ms. In double, no
  measurable effect (FP64 1:64 of this GPU).
- writes coalesced by staging the values of a warp in shared memory
  (`overlay-coalesced*`): slower (8.83 and 9.90 ms instead of 8.13 ms);
  allocating 8.4 kB of shared memory per block without using it already
  gives 9.7 ms (+19 %): the shared memory reduces the L1 cache, in which
  the stack of the threads lives (`results-coalesced.txt`).

Summary: about 0.3 ms for the 27 additional uncoalesced writes in global
memory, about 0.8 ms for the moves of the larger tangent operator (and of
the intermediate DSIG_DF) in the stack, which compete with the rest of the
kernel for the L1 cache; the arithmetic of the conversion counts little.

## Copies of the tangent operator DPK1_DF (layout of mfem-mgis, 21/11 evening)

chain of conversions, 81 values stored in `Dt`, copy of `Dt` in the buffer
of the runtime (`exportTangentOperator`), copy of the buffer in the field
(scatter). Line by line (component by component, stall samples weighted by
the sampling interval, `results-diff-soa.txt`): the last conversion and
the store in `Dt`, the copy in the buffer and the scatter make a quarter of
