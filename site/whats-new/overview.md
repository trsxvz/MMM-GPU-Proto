# Overview

This page presents the prototype: its goal, the role of each library,
the principles it follows, its vocabulary and its status. The source
document is `docs/overview.md`.

## Goal

The prototype makes the whole chain MFront, MGIS and mfem-mgis able to
compute on the GPU as well as on the CPU: the finite element
computations, the constitutive laws (behaviours) and the linear solvers
can all run on the same device. Keeping the whole computation on one
device keeps the chain consistent and avoids copying the data between
the host and the GPU at each iteration.

The laws are evaluated at each integration point, at each iteration.
The points are independent: they are processed by batches. The same
MFront file must be usable everywhere. The choice between CPU and GPU is
made when the law is compiled or at run time, not in the code of the
law.

## In short

- **TFEL/MFront** generates, for each behaviour, model and material
  property, functions that process a whole batch of integration points. The
  same MFront file compiles for CUDA, HIP, Kokkos, RAJA, SYCL, OpenMP,
  OpenACC and the C++ parallel algorithms. The results are systematically
  compared with those of the `generic` interface.
- **MGIS** loads these libraries and computes batches without copying
  the data. Its existing functions switch to batch computation by
  themselves. The caller chooses the memory, the execution queue, and a
  synchronous (default) or asynchronous computation. The data can be
  stored component by component, or belong to the caller and be
  described by views, on the GPU included, end of step included.
- **mfem-mgis** integrates the behaviours by batches, on CPU and on GPU.
  The data at integration points live in the memory of MFEM. Gradients,
  internal forces, tangent operator (assembled or matrix free),
  prediction, thermal problems, micromorphic problems, FBar and
  post-processings are computed by kernels. Solvers suited to the GPU
  are added to Newton: accelerated fixed point, NewtonK0, inexact
  Newton, cuDSS direct solver. The whole test suite passes on the GPU,
  except the two tests that require the absence of a GPU. The plan
  followed is split into work packages (`docs/plan-mfem-mgis-detailed.md`).
- **mfem-mgis-examples** and **mm-opera-hpc**: all examples and all
  cases (polycrystal, cermet, bubble) run by batches and on the GPU.
- Most changes are not yet proposed to the official repositories. Some
  fixes are already merged there and are part of the bases. How the
  others are split into contributions is described in
  `docs/upstream-integration.md`.

## The chain and the role of each library

Each library only knows the interface of the previous one.

| | TFEL/MFront | MGIS | mfem-mgis |
|---|---|---|---|
| Role | code of one material point, processing of a batch of points | material data, loading of libraries, dispatch | finite elements, solvers, orchestration |
| GPU code | kernels of the batch functions (one backend per generated library) | none in the compiled library; copies and end of step by headers compiled by the caller (`FieldOperations`: kernels of CUDA, HIP, Kokkos, RAJA, SYCL, OpenMP offload and OpenACC, parallel algorithms of C++ on the host or offloaded by `nvc++ -stdpar=gpu`) | kernels of mfem-mgis (gradients, internal forces, tangent, prediction, post-processings), assembly and solvers of MFEM, hypre, AmgX and cuDSS |
| Memory | does not allocate the data of the points; allocates once per device the copies of shared data and the state and statistics blocks, reused from one call to the next (and, with SYCL, copies of inaccessible values) | uses the arrays of the caller, or a memory resource given by the caller | owns the data, decides where they live |
| Exposed interface | versioned C structures, description symbols | `MaterialDataManager`, batch functions | nonlinear forms of MFEM |

A batch is a set of integration points of one material. A batch
function processes all these points in one call.

## Principles

1. **Same meaning as the `generic` interface.** A call on a batch is
   equivalent to calling the `generic` function on each point. The
   results of the `generic` interface on the CPU are the reference of
   all tests.
2. **No duplicated physics.** The class generated by MFront for a law
   is used as is on CPU and on GPU. The `generic-parallel` interface
   only adds a constructor and some adaptation code.
3. **Logic in headers, thin generated code.** The work at one point is
   written once, as templates usable on the host and on the GPU. Each
   backend only writes its parallel loop.
4. **Portability by backend.** A generated library targets one backend:
   CUDA, HIP, C++ parallel algorithms, Kokkos, RAJA, SYCL, OpenMP or
   OpenACC. Several libraries of the same law can be loaded together. The
   choice between CPU and GPU is then made at run time.
5. **The caller chooses the memory.** TFEL chooses neither the GPU nor
   the memory. Each library only declares where the data must be
   accessible. MGIS checks that the arrays of the caller are suitable.
6. **Errors at no cost on success.** The kernels write nothing as long
   as no point fails. An argument error or a backend error throws an
   exception. A failure of the computation at one point is reported as
   such, never confused with an error.
7. **Symmetry.** Behaviours, models and material properties share the
   same execution interface: execution queue, synchronous or
   asynchronous computation, memory space, contract version. The
   remaining differences are justified in `docs/tfel.md`.
8. **No change of the CPU results of the existing interfaces**, except
   defect corrections. Each correction is isolated and justified in
   `docs/tfel.md`.

## Vocabulary

- **Batch**: set of integration points processed by one call.
- **Backend**: programming model targeted by a generated library
  (`cuda`, `hip`, `stlpar`, `kokkos`, `raja`, `sycl`, `openmp`,
  `openacc`).
- **Field**: values of a variable on all points of a batch, given by a
  pointer and strides. A zero stride between points denotes a uniform
  value.
- **Memory space** of a library: where its computations read the data
  (`host`, `device` or `any`). It is fixed at compile time.
- **Location** of the arrays: where the caller has placed them (host,
  GPU or shared memory). MGIS compares it with the memory space.
- **Execution queue**: CUDA or HIP stream, SYCL queue, Kokkos instance,
  resource of camp (RAJA).
- **Synchronous**: the function returns once the computation is
  finished. **Asynchronous**: it returns as soon as the computation is
  submitted to the queue. The caller synchronises the queue before
  reading the results.

## Status

| Part | Status |
|---|---|
| TFEL/MFront: `generic-parallel` interface of behaviours and models | done, validated on 17 configurations |
| TFEL/MFront: `generic-parallel` interface of material properties | extended (execution options, asynchronous calls, new backends) |
| TFEL/MFront: GPU code and corrections | done |
| MGIS: batches of behaviours, models and material properties | done |
| MGIS: asynchronous computation | done, synchronous by default |
| MGIS: views, component by component storage, end of step on the GPU | done |
| Documentation of TFEL and MGIS (web pages, Doxygen, comments) | up to date with the changes |
| mfem-mgis | work packages L0 to L10 done, then direct solvers, ordered assembly, execution settings and HIP (see below) |
| Single precision (float) on the whole chain | done on CPU and GPU (see below) |

mfem-mgis, in detail:

- Work packages L0 to L10 are done: material data in the memory of MFEM,
  batch integration and mechanics by kernels. Fixed point and NewtonK0,
  thermal and micromorphic problems, FBar and Faltus are available.
  Boundary conditions and other integrators are computed by kernels.
  Point-wise models run on the GPU, and post-processings are computed by
  kernels. The whole test suite runs on the GPU. Kokkos and AmgX are
  optional, and the standard host memory is used on the GPU.
- Since then: the cuDSS direct solver and the reuse of the MUMPS
  analysis; the ordered assembly of the tangent operator
  (`MFEM_MGIS_TANGENT_OPERATOR_ASSEMBLY=Ordered`); the execution settings
  (`--execution cpu|gpu|mixed`, placement of each phase, placement of the
  law of each material by `BehaviourExecutionLocation`); kernels compiled
  for HIP (AMD GPU: compilation checked, not run).
- All examples of mfem-mgis-examples and all cases of mm-opera-hpc run
  by batches and on the GPU.

Single precision: the real type of the whole chain is the one of the
installed MFEM (`double` by default, or `float`). In float, the test
suites pass: MGIS 49/49, and 51/51 with CUDA; mfem-mgis 223/223 on the
CPU and 280/280 on the GPU; the examples 21/21; mm-opera-hpc 6/6.

## Performance

The figures below come from `docs/overview.md` and the measurement
folders in `results/`. The GPU is an RTX 5080.

| Case | GPU | CPU |
|---|---|---|
| Beam r4, NewtonK0 | 1.96 s | 9.5 s on 8 cores with the same method (13.6 s with Newton) |
| Polycrystal, NewtonK0 | 9.6 s (8.8 s on 12/10) | 23.5 s on 8 cores with the same method (29.6 s with Newton) |
| ex8 (5 steps) | 2.6 s (cuDSS direct solver for both problems, analysis reused) | 19.2 s on 2 cores by kernels (symmetric MUMPS, analysis reused) |
| ex7 (40 steps) | 2.0 s (cuDSS) | 5.4 s on 2 cores (MUMPS) |
| Bubble of mm-opera-hpc | 5.3 s | 25.2 s on one core |

On the GPU, small linear systems (fewer than 10,000 unknowns) are
better handled by cuDSS than by GMRES and BoomerAMG.

In single precision, at the same Newton criterion (1e-4), the beam r4 is
1.11 times faster than in double on the CPU
(`results/precision-beam-2026-10-14-0514`), and 1.37 times faster on the
GPU, with the same iterations, 3.4e-5 away from the solution in double
(`results/precision-beam-gpu-2026-10-14-0843`).
