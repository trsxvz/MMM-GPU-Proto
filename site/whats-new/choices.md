# Design choices

This page gathers the main design choices of the prototype and the
reasons given for them. The sources, in French, are
`docs/overview.md`, `docs/tfel.md`, `docs/mgis.md`,
`docs/plan-mfem-mgis.md`, `docs/plan-mfem-mgis-detailed.md`,
`docs/plan-execution.md`, `docs/plan-precision.md`,
`docs/plan-ci-site.md` and `docs/gpu-solvers.md`.

## Overall approach

- **Explore and propose.** The work on mfem-mgis has two compatible
  goals: explore (measure, compare, try many variants) and propose to
  the developers of mfem-mgis a clean, complete, flexible and modular
  code, in the spirit of TFEL and MGIS. So everything is selectable: the
  current path of mfem-mgis stays the default, and new paths are enabled
  by options. When several ways exist, they are all implemented, chosen
  by an option, and compared on the same cases.
- **Every option has a test that fails if the option is ignored.**
- **No silent failure.** An unsupported configuration is refused with a
  message, never silently ignored.
- **The `generic` interface on the CPU is the single reference.** For
  each tested law, the same MFront source is compiled with both
  interfaces and the results are compared. Important tests are checked
  against a deliberately wrong version of the code: a test that cannot
  fail is worthless.
- **Compiler defects are worked around, not used as a reason to drop a
  GPU feature.** Each workaround is targeted and has a reproducer.

## Why batches

A mechanical simulation with mfem-mgis spends much of its time in the
constitutive laws, evaluated at each integration point and at each
iteration. The points are independent, so the computation is highly
parallel. A batch function processes all the points of one material in
one call, so that each backend can use the parallel primitive natural to
its programming model.

- **Same meaning as the `generic` interface**: a call on a batch is
  equivalent to calling the `generic` function on each point.
- **No duplicated physics**: the class generated by MFront for a law is
  used as is on CPU and GPU.
- **Logic in headers, thin generated code**: the work at one point is
  written once, as templates usable on the host and the GPU, and each
  backend only writes its parallel loop.
- **One backend per generated library**: several libraries of the same
  law can be loaded together, and the choice between CPU and GPU is then
  made at run time.

## Interface of TFEL

- **A structure rather than a long argument list.** A behaviour has about
  a dozen groups of variables, and a structure can evolve without
  changing the prototype of the functions. Its version is exported, so
  that MGIS can refuse an incompatible library.
- **Fields with two strides** cover both useful layouts: point by point
  (the layout of MGIS) and component by component (coalesced accesses
  on the GPU). TFEL did not have to change when MGIS added views.
- **Local copies at each point.** A direct access to the fields, without
  local copies, was measured: no gain at run time, and 25 to 40 % more
  compile time with nvcc. It was removed.
- **A type (`PointTraits`) rather than a value** describes the data of a
  point, because nvcc cannot generate the host launcher of a kernel whose
  template parameter is a class.
- **Generated function objects, never pointers to members**, call the
  initialize functions and post-processings: `nvc++` silently ignores
  these pointers in device code.
- **Errors at no cost on success.** Kernels write nothing as long as no
  point fails; on CUDA and HIP a warp vote avoids any atomic operation in
  warps without event. The detailed message of a failing point is not
  transmitted, since device code has neither exceptions nor a per-thread
  message buffer: the point is replayed with the `generic` library of the
  same law.
- **Backend specific choices.** SYCL does not use a reduction, because
  its barriers make AdaptiveCpp fail on large kernels running on the
  CPU. An asynchronous computation on an unordered SYCL queue is refused,
  since nothing would guarantee the order. Kokkos must be a shared
  library compiled without relocatable device code with CUDA, because the
  generated libraries are loaded by `dlopen` and must share the same
  Kokkos instance. The kernel is a template parameter of the function
  that reads its attributes, because each library has its own statically
  linked CUDA runtime.
- **The caller chooses the memory.** TFEL chooses neither the GPU nor
  the memory: each library only declares where its data must be
  accessible (memory space symbol).
- **Symmetry between behaviours and material properties**: same
  execution options, same synchronous and asynchronous modes, same
  symbols. The remaining difference, the optional per-point status
  array, was not added to material properties.

## Interface of MGIS

- **No dependency on TFEL at compile time.** MGIS keeps its own copy of
  the C structures of TFEL, with a test that checks the memory layout is
  identical.
- **No dependency on any GPU library.** Arrays come from the caller, or
  from a memory resource it provides. MGIS provides memory resources and
  copy operations as headers, compiled by the caller with its own GPU
  tool chain. As a consequence, MGIS cannot synchronise a queue itself:
  in asynchronous mode the caller synchronises, then reads the result.
- **Location checked against memory space.** MGIS compares the location
  declared by the caller with the memory space exported by the library,
  so a new backend of TFEL needs no change in MGIS.
- **Existing functions switch by themselves** to batch computation, so
  that calling code does not change.
- **Pending computations can be moved but not assigned**: an assignment
  would copy the status while the GPU writes it.
- **Synchronous by default**, asynchronous on request.

## mfem-mgis

- **Data at integration points in the memory of MFEM.** The arrays of
  the materials are `mfem::Vector` objects (`MaterialArrays`), seen by
  MGIS without copy. mfem-mgis owns the data and decides where they
  live. The end of a step is done on the GPU by `update` with copy
  operations provided by mfem-mgis. Swapping the arrays was rejected: it
  is not equivalent to `update`, since a prediction does not write the
  end of step state.
- **Own operator rather than partial assembly of MFEM.** With partial
  assembly, MFEM 4.10 silently ignores boundary integrators (imposed
  pressure) and stops on a domain integrator with markers (heat source).
  An operator specific to mfem-mgis is therefore the main entry point.
- **Kernels written once with `mfem::forall`**, generic on the
  hypothesis and the gradient type, used on CPU and on GPU. Since
  `mfem::forall` only launches a CUDA kernel when the file is compiled by
  nvcc, the files with kernels are compiled as CUDA (or HIP) when MFEM
  is.
- **Element geometry computed once.** For a mesh without nodes, the
  Jacobians are computed by a kernel from the vertices: the geometric
  factors of MFEM required a first order finite element space and a
  projection of the coordinates on the host (1.8 s for 1.6 million
  tetrahedra). Positions of the entries in the sparse matrix are computed
  once.
- **Boundary conditions independent of the unknowns** (pressure, heat
  source) are assembled once for a unit value, then scaled and added on
  the GPU to the internal forces. The nonlinear form then only contains
  the integrator of mfem-mgis: no residual assembled on the host.

## Assembly: atomic or ordered

With a device, the element stiffness matrices are added to the sparse
matrix by atomic additions, in an order that changes from one run to
the next. The last digits of the results change too, and the number of
Newton iterations can vary. The ordered assembly
(`TangentOperatorAssembly=Ordered`) stores the element matrices, then
adds them in a fixed order: one thread per value of the matrix adds its
two or three contributions in a fixed order. With it, four runs of
`FixedPointSolverTest` on the GPU give bit for bit identical iteration
histories; with the atomic assembly, three runs give three different
histories.

The cost, measured on the beam r4 on the GPU: 4.3 ms per tangent
assembly with atomics, 6 ms in order (a first version with one thread
per row took 11 ms), plus 0.13 s for the first assembly, and extra
memory for the element matrices and the contributions. Atomic stays the
default. On the host, elements are already added one after the other,
so both values give the same assembly.

## Solvers on the GPU

- **Fixed point and NewtonK0.** A preliminary study on a J2 beam found
  the fixed point on the elastic operator K0, accelerated by Anderson,
  2.15 times faster than the best Newton on CPU, but 3.3 times slower on
  a polycrystal (8 times more iterations, so more law integrations). No
  method wins everywhere, hence all variants. `NewtonK0` keeps the
  iterations of Newton but builds the AMG of K0 only once, since on the
  GPU the construction of an AMG often costs more than several solves.
- **All MTest accelerations**, not only Anderson: the literature review
  of the study shows Anderson is not always the best.
- **Fair comparisons**: best against best, never against a Newton with
  only a direct solver, which distorts the gains.
- **BoomerAMG**: the `Elasticity` strategy stops the program with hypre
  on the GPU, so mfem-mgis switches to `System` with a warning. The
  options are reapplied after each new operator, because MFEM resets
  some of them.
- **Small systems**: below about 10,000 unknowns, a GMRES and BoomerAMG
  solve on the GPU is dominated by kernel launches. hypre can run on the
  host while the rest stays on the GPU (`--hypre-on-host`), and cuDSS is
  better than GMRES and BoomerAMG for these sizes. cuDSS does not pay on
  large 3D problems.
- **Reuse of the direct solver analysis** (MUMPS and cuDSS): kept while
  the pattern does not change on any process. MFEM does not check the
  pattern, so mfem-mgis compares it before each factorisation.
- **Own AmgX wrapper**: the `AmgXSolver` of MFEM shares resources that
  keep the communicator and configuration of the first solver, imposes
  GPU 0 and hides the convergence status. mfem-mgis uses the C interface
  of AmgX directly.

## Execution modes

Before this work, placing a computation on the GPU required several
independent settings, and each example exposed them its own way. The
goal: one set of options, declared by mfem-mgis and understood the same
way by all examples, and all placement combinations, except real
technical limits, which are documented.

- `--execution cpu|gpu|mixed`, and in `mixed` mode one switch per phase
  (finite elements, behaviours, linear solver, post-processings). The
  per-phase switches are refused outside `mixed`, since they would be
  contradictory.
- Without `--execution`, nothing changes, which keeps the tests of
  mfem-mgis unchanged. With `--execution`, the placement environment
  variables are ignored with a warning. A parameter given to the problem
  keeps priority, so a test can always force a path.
- In `cpu` mode, the finite elements are computed by kernels on the host,
  which is faster (12.2 s instead of 16.5 s on the beam with 8
  processes), with a fallback element by element.
- Real limits are refused with a clear message: solvers that only exist
  on one side (MUMPS, UMFPACK, PETSc on the host; AmgX, cuDSS on the
  GPU), the placement of hypre, global to the process, and the device of
  MFEM, global too.
- **No asynchronous copies.** The copies of the material arrays cost at
  most 0.42 s (0.2 % to 4.5 % of the computation depending on the
  placement); the cost of a mixed placement comes from the processor
  that computes. The possible gain is small compared to the risk (order
  of operations, pinned memory).

## Precision: decisions D1 to D9

The goal is a single real type for a whole computation, given by the
installed MFEM (`mfem::real_t`). A mix must be refused with a clear
message, never give wrong results. The motivation: consumer GPUs, such
as the RTX 5080 of the development machine, compute in double much more
slowly than in single precision (1/64 according to the published
specifications), and memory bound phases read fewer bytes. Mixed
precision is out of scope. All decisions were taken on 13/10/2026
following the recommendations.

| Decision | Choice | Reason |
|---|---|---|
| D1 | The installed MFEM is the source of truth; no option of mfem-mgis | Changing precision means installing another MFEM, which also fixes hypre, PETSc and MUMPS |
| D2 | Macros, plus an option of `mfront` that writes them into the generated sources | A single entry point whatever the backend; the size symbol protects in both cases |
| D3 | (b) rewrite the laws of the examples and tests with typed literals, and (a) let TFEL accept assignment from a wider floating point type | (b) gives honest measurements and is needed anyway for mixed `std::max` and `std::min` calls; (a) accepts the existing laws of users |
| D4 | The CMake function also builds a double library for MTest tests, and MTest refuses a float law | MTest computes in double |
| D5 | MGIS bindings (Python, Fortran, Julia, FEniCS) refused in float at configuration | Start small |
| D6 | Interface of the law parameters (double) and bounds (long double) unchanged | Input data, converted when used; changing it would break all existing libraries |
| D7 | Criteria bounded in float | Criteria written for double are out of reach in float |
| D8 | Parameters of mfem-mgis stored as `double`, converted when read | The API does not depend on precision, and `{"Tolerance", 1e-10}` still compiles |
| D9 | First float version: behaviours only; material properties with a float interface but computed in double; models and AmgX refused | Limited scope |

Values measured for D7: the criterion given by `@Epsilon` is bounded to
ε/10 by MFront at generation, and `numerical_jacobian_epsilon` to ε. A
first value of 10 ε was too loose: with elastic strains of 1e-4 it
leaves about 1 % error on stresses, and Newton did not converge on the
polycrystal of mm-opera-hpc. A first version that bounded the criterion
at load time in MGIS overwrote values given at run time, hence the move
into MFront. Relative tolerances of the solvers of mfem-mgis are bounded
to 100 ε. Two separate spack environments in float (CPU, then GPU) were
also agreed, leaving the main environment untouched.

## Continuous integration and site: decisions E1 to E4

Constraints: GitHub runners have no GPU, so the continuous integration
can compile for CUDA and HIP but not run on a GPU; the main spack
environment is too large for it; and private repositories have limited
minutes and storage, and no GitHub Pages.

| Decision | Choice |
|---|---|
| E1 | Public repository, after an audit of the whole history (done on 13/10/2026, nothing to rewrite); the change of visibility remains to be done |
| E2 | CPU level first, then CUDA and HIP compilation at night |
| E3 | No runner on the development machine; GPU tests stay local (`scripts/mfem-mgis-gpu-suite.sh`) |
| E4 | Site in English, like the documentation of the libraries; the repository keeps its documents in French |

The CPU level checks that the patch series apply, builds TFEL from the
sources of the repository, applies MGIS from its patches, and builds and
tests mfem-mgis, the examples and mm-opera-hpc on the CPU, with ccache,
in double and in single precision (a matrix on the precision; double
by default when started by hand).
It is a draft of 14/10/2026, started by hand and not launched yet. It
reuses the lessons of the continuous integration of mfem-mgis: pinned
versions of the spack packages (otherwise an update of autoconf
invalidates the whole cache), no `continue-on-error` on the upload to
the cache, and read-only tokens for pull requests from forks. A cache of
the dependencies on GHCR, as for mfem-mgis, remains to be done.

The website is built with Sphinx (MyST Markdown) by
`scripts/build-site.sh`: these pages, the web pages of TFEL and MGIS
(pandoc), and the Sphinx and Doxygen documentation of mfem-mgis, all from
the sources of the prototype. `.github/workflows/pages.yml` publishes it
on GitHub Pages, started by hand until the repository is public.
