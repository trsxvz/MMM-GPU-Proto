The page describes the new functionalities of Version 5.2 of the
`TFEL` project.

# Highlights

## Support for the `TDLS` library (Tiny Device-callable Linear Solvers)

The `TDLS` library provides direct linear solvers for small dense
systems, callable on `CPU`s as well as inside `GPU` kernels, and
designed for maximum GPU performance:

- <https://github.com/trsxvz/tdls>
- [API reference](https://trsxvz.github.io/TDLS/api/index.html)

When compiling `TFEL`, one must explicitly enable support for the `TDLS`
library, see below.

## Behaviours on GPUs: the `generic-parallel` interface for behaviours

The `generic-parallel` interface integrates a behaviour, or executes a
standalone model, over a batch of integration points, on CPUs or on GPUs.
It provides the same backends as the `generic-parallel` interface for
material properties: `CUDA`, `HIP`, parallel algorithms of the C++
standard library, Kokkos, SYCL and OpenMP. The code generated by `MFront` and the
headers of `TFEL` can be used in device code. See [this
page](generic-parallel-behaviour-interface.html) for details.

# Known incompatibilities

- `MFront`' interfaces have to implement a method named `setOptions`.

The support of device code by `TFEL` and `MFront` (see the
`generic-parallel` interface for behaviours) leads to the following
changes:

- `MechanicalBehaviour` no longer declares the interface of the behaviours
  as pure virtual functions: a behaviour can't be manipulated through a
  reference to this class. The virtual table requires the run-time type
  information, which is not supported in device code. The generated code
  never used this class this way. The methods expected from a behaviour
  are described by the `MechanicalBehaviourConcept` concept. The generated
  classes no longer declare those methods and their destructors `final` or
  `override`.
- the functions of `BoundsCheck` take the name of the variable as a
  `const char*` and return a boolean. In device code, where exceptions are
  not supported, this boolean is `false` if a bound is violated with the
  `Strict` policy. On the host, an exception is still thrown.
- the implementation of `LogarithmicStrainHandler` is defined in its header:
  the `TFELMaterial` library no longer exports its functions.
- the slip systems of single crystals (`getSlidingSystems` and the
  associated methods) are built at compile time. Their result must be bound
  to a constant reference: it is a copy with `nvc++ -stdpar=gpu` and
  `nvc++ -mp=gpu`, which do not allow device code to access global
  variables.
- `MetallicCFCGenericSlidingSystemsInteractionMatrix::getInteractionMatrix`
  and `getSecondInteractionMatrix` return the matrix by value: the matrix
  is computed at each call instead of being cached at the first call.
- the `mus` member of `PolyCrystalsSlidingSystems` and
  `ExtendedPolyCrystalsSlidingSystems` is a fixed size array
  (`tvector<Ng, tvector<Nss, StrainStensor>>`), so that those classes are
  trivially copyable.
- `FiniteStrainBehaviourTangentOperator` is based on the new
  `TrivialGenTypeBase` class instead of `GenTypeBase`: `std::variant` is
  not supported in device code by `nvc++`.
- the classes generated for the models by the `generic` and
  `generic-parallel` interfaces are declared in an unnamed namespace.
- the eigenvectors of a multiple eigenvalue of a 3D symmetric tensor are
  computed by the Jacobi algorithm in device code, where recursion is not
  supported. The host code is unchanged, except with the compilers
  translating host and device code in a single pass (see the
  `TFEL_DEVICE_CODE` macro). The results may then differ by round-off
  errors.

# Improvements to the build system

## New `cmake` options

- `enable-tdls`: add support for Tiny Device-callable Linear Solvers
  (`TDLS`) library. `OFF` by default.
- `enable-tdls-as-default-linear-system-solver-in-mfront`: use `TDLS`
  as the default linear solver. Requires `enable-tdls` to be `ON`.
  `OFF` by default.

## User-defined `cmake` variables

- `generic-parallel-configurations`: list of configurations to be
  supported. See next paragraph for details and the list of supported
  configurations.
- `TFEL_GXX_COMPILER`: path to the `g++` compiler.
- `TFEL_CLANGXX_COMPILER`: path to the `clang++` compiler.
- `TFEL_ICPX_COMPILER`: path to INTEL's `icpx` compiler.
- `TFEL_NVHPC_COMPILER`: path to NVIDIA's `nvhpc` compiler.
- `TFEL_ACPP_COMPILER`: path to AdaptativeCpp's `acpp` compiler.
- `TFEL_CLANG_CUDA_PATH`: path to the `CUDA` toolkit used by `clang` in
  the `cuda-clang` and `hip-clang` configurations (by default, the
  toolkit of `nvcc`). A version of `clang` only supports the versions of
  `CUDA` released before it.
- `HIP_PLATFORM`: `amd` or `nvidia`, required by the configurations based
  on `HIP`. If not given, its value is read in the environment and cached.
- `tdls_DIR`: directory where to find the `cmake` files installed by the
  Tiny Device-callable Linear Solvers (`TDLS`) library.

## Supported parallel configurations

The following configurations are supported for parallel computations:

- `cuda-nvcc`: configuration associated with the `CUDA` parallel
  programming model and NVIDIA's `nvcc` compiler
- `cuda-clang`: configuration associated with the `CUDA` parallel
  programming model and LLVM's `clang` compiler
- `hip-hipcc`:  configuration associated with the `HIP` parallel
  programming model and AMD's `hipcc` compiler
- `hip-clang`:  configuration associated with the `HIP` parallel
  programming model and LLVM's `clang` compiler, only supported on the
  NVIDIA platform (`HIP_PLATFORM=nvidia`)
- `stlpar-parunseq-gcc`: configuration associated with `C++` standard
  parallel algorithms using the parallel unsequenced execution policy
  and the `gcc` compiler.
- `stlpar-parunseq-clang`: configuration associated with `C++` standard
  parallel algorithms using the parallel unsequenced execution policy
  and the `clang` compiler.
- `stlpar-parunseq-icpx`: configuration associated with `C++` standard
  parallel algorithms using the parallel unsequenced execution policy
  and the `icpx` compiler.
- `stlpar-parunseq-nvhpc-gpu`: configuration associated with `C++`
  standard parallel algorithms using the parallel unsequenced execution
  policy and NVIDIA's `nvhpc` compiler with offloading on the GPU.
- `sycl-default-icpx`: configuration associated with the `SYCL`
  programming model and Intel's `icpx` compiler.
- `sycl-default-acpp`: configuration associated with the `SYCL`
  programming model and AdaptiveCpp's `acpp` compiler.
- `sycl-gpu-acpp`: tests of the `SYCL` backend for material properties on
  the GPU with AdaptiveCpp's `acpp` compiler. Those tests use the
  configuration files of the `sycl-default-acpp` configuration, which are
  installed if one of those two configurations is selected.
- `kokkos`: configuration associated with the `Kokkos` library, using the
  compiler and the flags of the `Kokkos` installation found by `cmake`
  (default execution space and default host execution space).
- `openmp-host-gcc`: configuration associated with `OpenMP` and the `g++`
  compiler, the computations being performed by the threads of the host.
- `openmp-offload-nvhpc-gpu`: configuration associated with `OpenMP` and
  NVIDIA's `nvc++` compiler with offloading on the GPU (`-mp=gpu
  -gpu=mem:managed`).

The selected configurations are used by the tests of the
`generic-parallel` interfaces for material properties and for behaviours.
The associated configuration files are installed in the
`share/tfel/mfront/configuration-files` directory.

## Add a `build-tests` target

In previous versions, tests were compiled and run using the `check`
target, which internally calls `ctest` for running the test. One
drawback of this approach is that `ctest` could not be run in parallel.

The `build-tests` target (which is a dependency of the `check` target)
only compiles the tests. To run the tests, one may still call the
`check` target or call directly `ctest`.

If the `build-tests` target has not been called, the `check` target
works as in previous versions.

# New `TFEL/Math` features

## Views of tensorial objects with coalescent memory access for data separated by a constant stride

In previous versions, the `View` class allows interpreting a contiguous
memory area as a tensorial object. The `CoalescedView` class allows to
create a tensorial object where each component is referred to by its own
pointer.

The `StridedCoalescedView` assumes that each component is separated by a
constant stride in memory, so that it only have to store one pointer and
the value of the stride.

Such views are efficient on GPUs where coalescent memory access are
preferable.

~~~~{.cxx}
int values[8] = {1, 10, 2, 20, 3, 30, 4, 40};
auto s1 = map_strided<stensor<2u, int>>(values, 2);
~~~~

## Walpole basis

The Walpole basis relative to transverse isotropic fourth-order tensors (`st2tost2`)
is introduced with the `struct` `TransverseIsotropicWalpoleBasis`, member of
`tfel::math`.

## Refactoring of quantities

Quantities were deeply refactored to:

- improve maintainability (code is much more compact),
- allow creating surrogate classes for quantities,
- improve error message,
- reduce size of the generated symbols.

## Rotation of vectors and square matrices

`change_basis` is available for `tvector<N>` and `tmatrix<N, N>`,
consistently with the rotation of tensors (see [this page](tensors.html)).

## Functions usable in device code

Many functions are usable in device code:

- the finite strain tools (`LogarithmicStrainHandler`, conversions of the
  tangent operators, `pull_back`, `invert` of `st2tost2`, which returns
  `NaN` values in device code if the tensor is singular);
- the tensor views of symmetric tensors and the accessors of tensors;
- the cubic spline and linear interpolations, the Aitken acceleration;
- the non linear solvers (Broyden, Levenberg-Marquardt, Powell dog leg).

## Aborting the resolution of a non linear system

`TinyNonLinearSolverBase::abortResolution` makes the resolution fail.
This allows to report errors in device code, where exceptions are not
supported (see [this page](tfel-math.html)).

# New features in `tfel-check`

## Parallelization

The commands described in different `.check` files can now be run in
distinct processes.

Note that the command described in a `.check` are still run
sequentially.

By default, as in previous versions, only one process is used.

### Specifying the number of jobs run simultaneously

The command line argument `--jobs` (`-j`) allow specifying the number
of jobs run simultaneously.

If no option is given to `--jobs`, the number of available cores
is used, if the system provide this information.

#### Limit on the number of jobs

By default, this number must be lower than the number of cores
available. This limit can be discarded by
passing`--discard-jobs-limit=true` to `tfel-check`.

### Caution

The user must take care that the commands described in `.check` files
can be run in parallel.

- the jobs shall no exhaust memory.
- the jobs shall not access concurrently to the same resources.

A typical example of conflict would be to have two `.check` files in the
same directory that call `mfront` to build somes shared libraries: the
two `MFront`'s processes may write concurrently files in the `src` and
`include` directories, leading to an undefined behaviour.

Another example would be to use `@CleanDirectories` and `@CleanFiles`
commands inappropriately and erase data used by commands of other
`.check` files.

## Defining environment variables in configuration files

Configuration files can now contain an `environment_variables` sections
which can introduce a map defining a set of environment variables.

### Example of usage

# New features in `MFront`

## The `@LinearSystemSolver` keyword

The `@LinearSystemSolver` keyword is used to select the linear system
solver. It is followed by the name of the solver. Currently, two solvers
are supported:

- `Default`. This uses the solvers provided natively by the `TFEL/Math`
  library. As implied by its name, this solver is used by default.
- `TDLS` (or equivalently `TinyDeviceCallableLinearSolver`). See
  <https://trsxvz.github.io/TDLS/getting_started.html> for details. If
  `TFEL` is not compiled with support for the `TDLS` library, selecting
  this solver falls back to the `Default` solver.

The name of the solver can optionally be followed by a dictionary
allowing to parametrize the solver.

### Supported Parameters

#### Parameters of the `Default` Linear Solver

The `Default` Linear Solver does not accept any parameter.

#### Parameters of the `TDLS` Linear Solver

The following options are supported:

- `tile_size`: the matrix is processed as a grid of `tile_size x
  tile_size` register tiles. This is the main performance axis of the
  solvers. Tune it per system dimension. The `tile_size` can be a
  strictly positive integer or a string. If `tile_size` is a string, it
  is interpreted as an integer formula whose variables can be any integer
  constant (see the `@IntegerConstant` keyword), `N`, `TVectorSize`,
  `StensorSize` or `TensorSize`. This formula must evaluate to a
  strictly positive integer for all hypotheses supported by the
  behaviour.
- `schedule`: expected values are either `left_looking` (or equivalently
  `left`, `left-looking` or `LeftLooking`) or `right_looking` (or
  equivalently `right`, `right-looking` or `RightLooking`). This
  parameter defines the elimination schedule of the tiled factorization.
- `out_of_tile_search_strategy`: expected values are either
  `first_acceptable` (or equivalently `first-acceptable` or
  `FirstAcceptable`) or `full_scan` (or equivalently `full-scan` or
  `FullScan`). With `first_acceptable`, the search below the tile stops
  at the first candidate whose corrected magnitude reaches the
  out-of-tile search threshold. With `full_scan`, all the rows below
  the tile are scanned and the best corrected candidate wins.
- `unroll_inner_loop`: expected values are either `true` or `false`. If
  `true`, loops indexing register tiles carry a forced-unroll pragma,
  the guard that keeps tiles in registers on GPU backends, where a
  rolled loop indexes the tile dynamically and demotes it to slow local
  memory. If `false`, no unroll pragma anywhere, for faster compiles,
  GPU performance not guaranteed.
- `out_of_tile_search_threshold`: acceptable-pivot threshold of the
  out-of-tile search. An in-tile pivot candidate whose magnitude reaches
  this value is accepted without looking outside the tile; below it, the
  search extends to the rows under the tile (out-of-tile pivoting) and
  the best candidate wins.
- `relative_pivot_threshold`: relative threshold of the pivot choice
  inside the diagonal tile, in `]0, 1]`. The row in place keeps the
  pivot when its magnitude reaches both this fraction of the largest
  in-tile candidate and the out-of-tile search threshold; otherwise the
  largest in-tile candidate wins. This threshold governs the in-tile
  choice only: the out-of-tile search keeps its absolute threshold. A
  value of `1` takes the largest in-tile candidate. This option requires
  a version of `TDLS` later than 0.2.0.
- `singular_pivot_threshold`: the factorization is declared singular
  when even the best candidate of the out-of-tile recovery stays below
  this threshold. This option must be set together with the
  `out_of_tile_search_threshold` option and must not exceed it.
- `out_of_tile_search_diagnostics`: expected values are either `true`
  or `false`. If `true`, an integer member `mfront_tdls_oot_count`,
  readable in user code blocks, reports the number of out-of-tile
  searches of the last linear solve. If `false` (the default), the
  generated code is unchanged.

If a parameter is not defined, the default values are inherited from the
`TiledLUppConfig` class defined by the `TDLS` library. See the
[API reference](https://trsxvz.github.io/TDLS/api/index.html) for
details. At the time of writing this documentation, those default values
are:

- `3` for `tile_size`
- `right_looking` for `schedule`
- `first_acceptable` for `out_of_tile_search_strategy`
- `true` for `unroll_inner_loop`
- `1e-10` for `out_of_tile_search_threshold` (or `1e-4` for single
  precision)
- `0.1` for `relative_pivot_threshold` (`TDLS` 0.2.0 takes the largest
  in-tile candidate, as a threshold of `1`)
- `std::numeric_limits<double>::min()` for `singular_pivot_threshold`
  (or `std::numeric_limits<float>::min()` for single precision)

### Examples

~~~~ {#LinearSystemSolver .cpp}
@LinearSystemSolver TDLS{
  tile_size: 4,
  unroll_inner_loop: false
};
~~~~

~~~~ {#LinearSystemSolver .cpp}
@LinearSystemSolver TDLS{
  tile_size: "StensorSize"
};
~~~~

## Configuration file

`MFront` now allows to define options in a configuration file define
through the `--configuration-file` command line argument as follows:

~~~~{bash}
$ mfront --configuration-file=config.json --interface=generic-parallel UO2_ShearModulus.mfront
~~~~

Configuration file follows an extented `JSON`-like syntax. It contains
the following sections:

- `dsl_options`
- `material_property_dsl_options`
- `behaviour_dsl_options`
- `model_dsl_options`
- `interfaces_options`
- `compilation_options`
- `linking_options`

None of those sections is required. All those sections must introduce a
dictionary.

> **Note**
>
> The options given in sections `dsl_options`,
> `material_property_dsl_options`, `behaviour_dsl_options` and
> `model_dsl_options` may also be retrieved in dedicated configurations
> files, respectively specified by the `--dsl-options-file`,
> `--material-property-dsl-options-file`, `--behaviour-dsl-options-file`,
> and `--model-dsl-options-file` command line arguments introduced in
> Version 4.1.

### Example of configuration file

~~~~{.json}
interfaces_options: {
  generic-parallel: {
    backend: {stlpar: {execution_policy: "par_unseq"}}
  }
}
~~~~

### The `interfaces_options` section

This section associates options to interfaces. For the `generic-parallel`
interfaces, the `backend` option selects the backend and its options (see
the pages of the [`generic-parallel` interface for material
properties](generic-parallel-material-property-interface.html) and of the
[`generic-parallel` interface for
behaviours](generic-parallel-behaviour-interface.html)).

### The `compilation_options` section

This section associates compilation options to a language (`c`, `cxx`,
`fortran`, `cuda`, `hip` or `sycl`):

~~~~{.json}
compilation_options : {
  cxx : {
    compiler: "nvc++",
    compilation_flags: "-O2 -stdpar=gpu -gpu=mem:managed,nordc -std=c++20 -march=native" 
  }
}
~~~~

#### The `compiler` option

The `compiler` option gives the compiler of the language.

#### The `compilation_flags` option

The `compilation_flags` option gives the compilation flags, as a string or
an array of strings.

### The `linking_options` section

#### The `linker_flags` option

The `linker_flags` option gives the linker flags, as a string or an array
of strings. Those flags are placed after the object files, so that the
libraries they give (for instance `-ltbb`) are not ignored by the linkers
using the `--as-needed` policy.

## Passing options to interfaces on the command line

### First syntax

~~~~{bash}
$ mfront --obuild --interface='generic-parallel{backend:{"stlpar": {execution_policy:"par_unseq"}}}' UO2_ShearModulus.mfront
~~~~

### Second syntax

~~~~{bash}
$ mfront --obuild --interface='{generic-parallel:{backend:"stlpar"{execution_policy:"par_unseq"}}}' UO2_ShearModulus.mfront
~~~~

## The `generic-parallel` interface for material properties

See [this page for
details](generic-parallel-material-property-interface.html).

### Available backends

- `stlpar`: parallel algorithms of the C++ standard library, on CPUs or on
  NVIDIA GPUs with `nvc++ -stdpar=gpu`;
- `cuda` and `hip`;
- `sycl`;
- `kokkos`;
- `openmp`: threads of the host or offloading to a device.

### Changes of the generated functions

- the generated functions take a last argument giving the execution
  options (`mfront_gpmp_ExecutionOptions`, or null for the default
  options), with the members of the execution options of the behaviours:
  queue, statistics of an asynchronous evaluation and preservation of the
  stack size of the threads of the device. The queue
  of the `SYCL` backend, which was a specific argument of its functions,
  is now given by those options. The version of those functions is given
  by the `MFRONT_GPMP_API_VERSION` macro.
- the output status is specific to the interface
  (`mfront_gpmp_OutputStatus`): as for the behaviours, it gives the number
  of points where the evaluation failed, the first of them, and the number
  of points where a bound is violated with the warning policy. The
  kernels only update the statistics of the evaluation when an event
  occurs at a point: with atomic operations (`cuda`, `hip`, `sycl` and
  `kokkos` backends), the cost of the error reporting is null when the
  evaluation succeeds. The `stlpar` and `openmp` backends merge the
  statuses of the points by a reduction.
- the exceptions thrown by the runtimes of the backends are reported as
  runtime errors (status `-6`), as the errors of the `CUDA` and `HIP`
  runtimes. An empty set of points is accepted without any check.
- the evaluation may be asynchronous: the statistics
  (`mfront_gpmp_Statistics`) are then analysed by the exported
  `<name>_generic_parallel_report` function.
- the libraries export the `<name>_generic_parallel_backend`,
  `<name>_generic_parallel_api_version` and
  `<name>_generic_parallel_memory_space` symbols.
- a bound violated with the warning policy gives the status `1`, as with
  the `generic` interface.
- the `stlpar` and `sycl` backends have a new `device_stack_size` option.
  The `cuda`, `hip` and `kokkos` backends increase the stack size of the
  threads if the kernel requires it, as for the behaviours.
- the automatic data transfers of the `sycl` backend are shared with the
  behaviours: they also copy the statistics of an asynchronous evaluation,
  and the points where the evaluation fails keep their values.
- the default number of threads per block of the `cuda` and `hip`
  backends is `128`, rounded up to a multiple of the warp size, as for the
  behaviours.

## The `generic-parallel` interface for behaviours

The `generic-parallel` interface integrates a behaviour, or executes a
standalone model, over a batch of integration points, on GPUs or on CPUs,
with the backends of the interface for material properties. See [this page
for details](generic-parallel-behaviour-interface.html).

The generated libraries provide:

- the integration of a batch, the initialize functions and the
  post-processings over a batch;
- the rotation functions of the orthotropic behaviours over a batch;
- the execution of the standalone models (`@DSL Model`) over a batch.

The data structures exchanged with the generated functions are declared
in `MFront/GenericParallelBehaviour/BatchData.h`. Their version is given
by the `MFRONT_GPB_API_VERSION` macro. The values of the variables at all
the points are described by fields, which support several layouts (point
by point, component by component, uniform values), and the material
properties and the external state variables can be given variable by
variable. The computations may be asynchronous: the statistics of the
batch are then accumulated on the device and analysed by the
`mfront_gpb_report` function. The libraries export the
`<name>_generic_parallel_backend`, `<name>_generic_parallel_memory_space`
and `<name>_generic_parallel_api_version` symbols. The configuration files
are shared with the `generic-parallel` interface for material properties.

## Writing behaviours usable on GPUs

- the `TFEL_DEVICE_CODE` macro is defined when device code is compiled.
  With the compilers translating host and device code in a single pass
  (`nvc++ -stdpar=gpu`, `nvc++ -mp=gpu`, generic compiler of
  AdaptiveCpp), it is defined in the whole translation unit (see the
  [`TFEL/Config` page](tfel-config.html)).
- `tfel::fail` reports an error in host and device code: it throws an
  exception on the host and returns `false` in device code.
- `abortResolution` (implicit DSLs) and `abortIntegration` (Runge-Kutta
  DSLs) make the integration fail in device code, as an exception does on
  the host. `abortResolution` is a method of `TinyNonLinearSolverBase`.
  The isotropic DSLs have no equivalent: an error reported in their flow
  rules in device code only makes the integration fail once the maximum
  number of iterations is reached.
- the `@SharedData` keyword declares a data shared by all the integration
  points, built once on the host, for instance the slip systems of the
  grains of a polycrystal read from a file. The `generic-parallel`
  interface copies it in the memory of the device (see `mfront
  --help-keyword=Implicit:@SharedData`).
- `tfel::utilities::getConstantObject` gives access to objects built at
  compile time in host and device code.
- the `device_compatible_class` DSL option requires a behaviour class
  usable in device code: dynamically allocated arrays are not used and
  the parameters treated as static variables are declared as constant
  members. This option is set when the `generic-parallel` interface is
  selected, and is given to the behaviour variables.
- the comparison to a numerical jacobian (`@CompareToNumericalJacobian`)
  and the profiling (`@Profiling`) are only performed on the host.

## Improvements to the `Cast3M` interface

### Improved generation of `Gibiane` input file

The `Cast3M` interface generates automatically an example of `Gibiane`
input file to integrate which each `MFront` behaviour. This example is
meant to be used a template and do not pretend to be usable without
modification by the user. For instance, previous versions of `MFront`
did not guarantee that the name of the variables (limited to `4`
characters) were unique. Version 5.2 improves this. To illustrate this,
one may compare the output of Version 5.1 and Version 5.2:

~~~~
* Version prior to 5.2
statev = 'MOTS' 'EERR' 'EEZZ' 'EETT' 'EERZ' 'KHRR' 'KHZZ' 'KHTT' 'KHRZ' 'KHRR' 'KHZZ' 'KHTT' 'KHRZ' 'P';
* Version 5.2
statev = 'MOTS' 'EERR' 'EEZZ' 'EETT' 'EERZ' 'KHRR' 'KHZZ' 'KHTT' 'KHRZ' 'V0' 'V1' 'V2' 'V3' 'P';
~~~~

In Version 5.1, the variable name `KHRR` is declared twice. `Cast3M`
does not generate an error although duplicated names leads to erroneous
results. Version 5.2 avoids this pitfall.

## Other fixes

The following defects have been fixed while adding the support of device
code:

- `generic` interface, finite strain behaviours: the outputs were not
  converted after an unreliable result (status `0`); the `DTAU_DDF`
  tangent operator of the behaviours written in the logarithmic strain
  was computed with the logarithmic strain handler of the beginning of
  the time step; the post-processings did not use the internal state
  variables at the end of the time step; the initialize functions of the
  behaviours written in the Green-Lagrange or Hencky strains did not
  compile; the prediction operator ignored the request of the speed of
  sound.
- `generic` interface, finite strain behaviours: the stress computed by
  an initialize function was lost for the first and second
  Piola-Kirchhoff stresses and for the behaviours written in the
  Green-Lagrange or Hencky strains.
- `generic` interface, rotation functions of orthotropic behaviours: wrong
  offset of the second order tensors in the variants treating arrays of
  points, scalars not copied, vectors not supported. The tangent operator
  blocks associated with arrays of variables, and the blocks mixing a
  vector and a (symmetric) tensor or a tensor and a symmetric tensor, are
  now rotated.
- `generic` interface: an exception thrown by the constructor of the
  behaviour, for instance when a data declared by `@SharedData` can't be
  built, left the generated function. It is now reported as a failure, and
  the time step scaling factor is left unchanged.
- `generic` interface, models: the failures of the physical bounds were
  ignored when device code is selected in the whole translation unit. The
  parameters of a model were shared by the libraries generated for this
  model by the `generic` and `generic-parallel` interfaces. The models
  with material properties and parameters treated as static variables,
  and the static variables of the models using quantities, are now
  supported.
- implicit DSLs: a failure of a substitution in the computation of the
  tangent operator could be erased by a later successful call.
- `StandardElastoViscoPlasticity` brick: wrong name of the derivative of
  a yield radius interpolated by a cubic spline when an identifier is
  used.
- `generic` interface for material properties: the message of a violated
  physical upper bound said below instead of over, and `errno` was not
  restored when an upper bound was violated with the strict policy. The
  documentation of the bounds status now describes its sign as
  implemented: negative if the evaluation failed (physical bound, or bound
  with the strict policy), positive with the warning policy.
- material properties, all interfaces: the physical bounds of an argument
  were only exported if this argument also had standard bounds.
- `MFront`: the linker flags are placed after the object files, so that
  the libraries they give (for instance `-ltbb`) are not ignored by the
  linkers using the `--as-needed` policy.
- `generic-parallel` interface for material properties: `errno` was
  checked after the parallel execution, which made the first call fail;
  the bounds of the output were written past the end of the statuses; the
  headers of the backends overwrote each other; the device memory of the
  `SYCL` backend was never freed; the values between the values of a
  strided output were overwritten.
