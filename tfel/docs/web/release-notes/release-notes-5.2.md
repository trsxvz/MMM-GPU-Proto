The page describes the new functionalities of Version 5.2 of the
`TFEL` project.

# Highlights

## Support for the `TDLS` library (Tiny Device-callable Linear Solvers)

The `TDLS` library provides direct linear solvers for small dense
systems, callable on `CPU`s as well as inside `GPU` kernels, and
designed for maximum GPU performance:

- <https://github.com/trsxvz/tdls>
- [API reference](https://trsxvz.github.io/TDLS/api/index.html)

When compiling `TFEL`, one must explicitly enable support for the `TDLS`
library, see below.

## Behaviours on GPUs: the `generic-parallel` interface for behaviours

The `generic-parallel` interface integrates a behaviour, or executes a
standalone model, over a batch of integration points, on CPUs or on GPUs. It
provides the same backends as the `generic-parallel` interface for material
properties: `CUDA`, `HIP`, parallel algorithms of the C++ standard library,
Kokkos, RAJA, SYCL, OpenMP, OpenACC and the accelerator API of Arccore (the
core component of the Arcane framework). The code generated by `MFront` and
the headers of `TFEL` can be used in device code. See [this
page](generic-parallel-behaviour-interface.html) for details.

# Known incompatibilities

- The `enable-sanitize-options` option is no longer a boolean option: it
  now takes the list of the sanitizers to enable, e.g.
  `-Denable-sanitize-options="address;undefined"`. Enabling all the
  sanitizers at once was indeed meaningless as most sanitizers cannot be
  combined (for instance `address`, `thread` and `memory`). Each
  sanitizer can also be enabled individually using its dedicated
  `enable-<name>-sanitizer` option, see below.
- `cmake` \(3.20\) or later is now required to build `TFEL`.
- `MFront`' interfaces have to implement a method named `setOptions`.
- The boolean argument of `CxxTokenizer::isValidIdentifier` now states,
  as documented, if `C++` keywords are allowed (see Issue #964): its
  meaning has been inverted. With the default value (`true`), `C++`
  keywords are now considered as valid identifiers.
- The static method `get` of the
  `GlobalDomainSpecificLanguageOptionsManager` class has been removed.
  The global options passed to domain specific languages are now handled
  by the `ConfigurationManager` class, which derives from the
  `GlobalDomainSpecificLanguageOptionsManager` class and whose unique
  instance is returned by `ConfigurationManager::get()`.
- `@RotationMatrix<Euler>` of `MTest` now gives the rotation described
  by the Euler angles in the convention of Bunge, as the polycrystal
  classes of `MFront` (see Issue #1270): the rotation matrix was the
  Bunge matrix instead of its transpose, i.e. the inverse rotation was
  applied.
- `Evaluator::getVariablesNames` returns the names of the variables
  ordered by their positions (the order given to the constructor, or the
  order of their first appearance in the expression), instead of the
  alphabetical order (see Issue #1209).
- `MTest` (see Issue #1260): an incomplete set of orthotropic thermal
  expansion coefficients is now an error (except `ThermalExpansion1` and
  `ThermalExpansion2` in plane stress).
- `MTest` assembles the equations associated with the off-diagonal
  components of the deformation gradient of finite strain behaviours
  with the off-diagonal stresses, and applies the imposed off-diagonal
  Cauchy stresses to both of their rows (see Issue #1290): computations
  leaving one of these components free, which failed or converged to a
  wrong state, converge to the right state, and the number of
  iterations of the other ones may change.
- `abaqusexplicit` interface (see Issue #1274): the results of
  orthotropic behaviours using the `MFront` orthotropy management policy
  change when the material frame is not symmetric with respect to the
  global frame: the integration applied the inverse rotation, and the
  second material axis was read beyond the orientation in 2D.
- `computeDeterminantSecondDerivative` of a non-symmetric tensor now
  returns the second derivative of the determinant in 2D and 3D (see
  Issue #1262): the rows of the off-diagonal components differ from the
  previous results, which were the derivative of the adjugate.
- The tiny non-linear solvers (and the `Implicit` DSLs) evaluate the
  estimate given by the last allowed correction (see Issue #1288): an
  integration that converges with exactly `iterMax` corrections now
  succeeds, and a failing one evaluates its residual once more.
- The Levenberg-Marquardt minimisers (`LevenbergMarquardt`,
  `FSLevenbergMarquardt`) reject the steps that increase the cost (see
  Issue #1288): the iterates of every fit change.
- Inputs that were silently ignored are now rejected (see Issue #1256):
  the `overriding_parameters` option of the model DSLs, `@Bounds` and
  `@PhysicalBounds` on gradients and thermodynamic forces, bounds on a
  component of a scalar variable, and the `Ksf` option of the
  `HarmonicSumOfNortonHoffViscoplasticFlows` inelastic flow.
- The Broyden algorithms of the `Implicit` DSLs (`Broyden`,
  `PowellDogLeg_Broyden` and `Broyden2`) update the jacobian, or its
  inverse, again (see Issue #1295): since `TFEL-4.0`, the update was
  hidden by the `updateOrCheckJacobian` method generated in every
  behaviour. The number of iterations of the behaviours using them
  changes, and so do their results within the convergence criterion.
  In `TinyBroydenSolver` and `TinyPowellDogLegBroydenSolver`
  (respectively `TinyBroyden2Solver`), the update is performed by the
  `updateJacobian` (respectively `updateJacobianInvert`) method, which
  replaces their `updateOrCheckJacobian` method.
- The integer values read by `CxxTokenizer::readInt` and
  `CxxTokenizer::readUnsignedInt`, i.e. the integers of the `MTest`,
  `MFront` and `tfel-check` files (numbers of iterations and of
  sub-steps, columns, array sizes of the DSLs, ...), shall be written
  without decimal point nor exponent: `3.0`, `3.` or `3e0` are now
  rejected (see Issue #1326).
- The type identifiers exported by `MFront` for the variables whose
  type is the derivative of a tensorial type alias (such as
  `StressStensor`, `Stensor`, `TVector` or `Tensor`) with respect to a
  non-scalar type follow the encoding described in the documentation:
  for instance, `derivative_type<StressStensor, StrainStensor>` is
  exported as `268`, like `Stensor4`, instead of `76`, which `MTest` and
  `MGIS` decode as `derivative_type<stensor<1, real>, real>`. Behaviours
  declaring such variables must be generated again (see Issue #1332).
- The array sizes of the variables of `MFront` and the integer
  formulas evaluated by `IntegerEvaluator` (for instance the
  `tile_size` option of the `TDLS` linear solver) shall only contain
  integers: a number with a decimal point or an exponent, such as `2.5`
  (which was truncated to `2`), `1e1` or `2.0`, is now rejected (see
  Issue #1321).
- In the homogenisation schemes of `TFEL/Material`, the elasticity of an
  anisotropic `OrientedDistribution` or `Grain`, given in the local basis
  of its inclusions, is rotated to the global basis (see Issue #1299):
  it was used as a global elasticity, so that the orientation of these
  phases was ignored. `computeEllipsoidLocalisationTensor` and
  `computePlaneStrainLocalisationTensor` with an isotropic matrix rotate
  the elasticity of the inclusion as well, as documented. The results of
  the dilute, Mori-Tanaka and self-consistent schemes with such phases
  change.
- The `FiniteStrainSingleCrystal` brick takes into account, in the
  jacobian and the consistent tangent operator, the derivatives of the
  normalisation of the inverse of the plastic deformation gradient
  increment (see Issues #1309 and #1359). These derivatives were
  explicitly neglected, as numerical tests showed (or at least seemed to
  show) that they were negligible. The residual is unchanged, so the
  results only change within the convergence criteria, unless the
  sub-stepping changes: the number of local and global iterations
  changes, and decreases significantly when the deformation gradient is
  not fully imposed. The boolean option
  `plastic_deformation_gradient_normalisation_corrections` of the brick,
  which is `true` by default, allows users to easily test if this
  correction affects their results: setting it to `false` restores the
  previous derivatives.

The support of device code by `TFEL` and `MFront` (see the
`generic-parallel` interface for behaviours) leads to the following
changes:

- `MechanicalBehaviour` no longer declares the interface of the behaviours
  as pure virtual functions: a behaviour can't be manipulated through a
  reference to this class. The virtual table requires the run-time type
  information, which is not supported in device code. The generated code
  never used this class this way. The methods expected from a behaviour
  are described by the `MechanicalBehaviourConcept` concept. The generated
  classes no longer declare those methods and their destructors `final` or
  `override`.
- the functions of `BoundsCheck` take the name of the variable as a
  `const char*` and return a boolean. In device code, where exceptions are
  not supported, this boolean is `false` if a bound is violated with the
  `Strict` policy. On the host, an exception is still thrown.
- the implementation of `LogarithmicStrainHandler` is defined in its header:
  the `TFELMaterial` library no longer exports its functions. A call of
  `LogarithmicStrainHandler<3u>::findSingleEigenValue` with three equal
  eigenvalues is reported by `tfel::reportContractViolation`, which aborts
  the process on the host, instead of throwing a `std::runtime_error`, and
  does nothing in device code.
- the slip systems of single crystals (`getSlidingSystems` and the
  associated methods) are built at compile time. Their result must be bound
  to a constant reference: it is a copy with `nvc++ -stdpar=gpu`,
  `nvc++ -mp=gpu` and `nvc++ -acc=gpu`, which do not allow device code to
  access global variables.
- `MetallicCFCGenericSlidingSystemsInteractionMatrix::getInteractionMatrix`
  and `getSecondInteractionMatrix` return the matrix by value: the matrix
  is computed at each call instead of being cached at the first call.
- the `mus` member of `PolyCrystalsSlidingSystems` and
  `ExtendedPolyCrystalsSlidingSystems` is a fixed size array
  (`tvector<Ng, tvector<Nss, StrainStensor>>`), so that those classes are
  trivially copyable.
- `FiniteStrainBehaviourTangentOperator` is based on the new
  `TrivialGenTypeBase` class instead of `GenTypeBase`: `std::variant` is
  not supported in device code by `nvc++`.
- the classes generated for the models by the `generic` and
  `generic-parallel` interfaces are declared in an unnamed namespace.
- the eigenvectors of a multiple eigenvalue of a 3D symmetric tensor are
  computed by the Jacobi algorithm in device code, where recursion is not
  supported. The host code is unchanged, except with the compilers
  translating host and device code in a single pass (see the
  `TFEL_DEVICE_CODE` macro). The results may then differ by round-off
  errors.

# Improvements to the build system

## New `cmake` options

- `enable-tdls`: add support for Tiny Device-callable Linear Solvers
  (`TDLS`) library. `OFF` by default.
- `enable-tdls-as-default-linear-system-solver-in-mfront`: use `TDLS`
  as the default linear solver. Requires `enable-tdls` to be `ON`.
  `OFF` by default.

## Sanitizers and hardening options

The support for sanitizers has been modularised: the `enable-sanitize-options`
option takes the list of the sanitizers to enable (a comma may be used as a
separator instead of a semicolon), for instance:

~~~~{.bash}
$ cmake <srcdir> -Denable-sanitize-options="address;undefined"
~~~~

The available sanitizers depend on the compiler and on its version. The
`address`, `thread` and `memory` sanitizers cannot be used simultaneously.

Each sanitizer also has a dedicated option, whose name is obtained from the
sanitizer name: `enable-<name>-sanitizer`, e.g.
`-Denable-bounds-strict-sanitizer=ON`. Such options can be combined with the
`enable-sanitize-options` option: the enabled sanitizers are the sanitizers
listed in the `enable-sanitize-options` option and the sanitizers whose
dedicated option is enabled. Dedicated options are also defined for the
sanitizers which are not supported by the current compiler (enabling them
issues a warning and they are ignored), so that the same options can be
used whatever the compiler is.

The following sanitizers are declared for `gcc` (the sanitizers corresponding
to a subset of the undefined behaviour sanitizer can be enabled
individually):

- `address`, `thread`, `leak`, `hwaddress`,
- `undefined` and its subsets: `alignment`, `bool`, `bounds`,
  `bounds-strict`, `builtin`, `enum`, `float-cast-overflow`,
  `float-divide-by-zero`, `null`, `object-size`, `return`, `shift`,
  `shift-base`, `shift-exponent`, `signed-integer-overflow`, `vptr`,
- `pointer-compare`, `pointer-subtract` (the address sanitizer and the link
  time optimization are required and added automatically),
- hardening flags, which can be combined with the sanitizers above:
  `fstack-check`, `fstack-protector-all`, `fno-omit-frame-pointer`.

The following sanitizers are declared for `clang`:

- `address`, `thread`, `memory` (the memory sanitizer also enables
  `-fsanitize-memory-track-origins=2`), `leak`, `hwaddress`,
- `cfi`, `cfi-icall`, `safe-stack`, `shadow-call-stack`, `dataflow`,
- `undefined` and its subsets: `alignment`, `bool`, `bounds`, `builtin`,
  `enum`, `float-cast-overflow`, `float-divide-by-zero`, `integer`,
  `unsigned-integer-overflow`, `null`, `object-size`, `return`, `shift`,
  `shift-base`, `shift-exponent`, `signed-integer-overflow`, `vptr`,
- `pointer-compare`, `pointer-subtract` (the address sanitizer and the link
  time optimization are required and added automatically),
- hardening flags, which can be combined with the sanitizers above:
  `address-use-after-scope` (`-fsanitize-address-use-after-scope`),
  `fstack-check`, `fstack-protector-all`, `fno-omit-frame-pointer`.

Some sanitizers require specific settings to be fully effective (the link
time optimization for `cfi` and `shadow-call-stack`, instrumentation of all
the linked code for `memory` and `safe-stack`, etc.), as described in the
`gcc` and `clang` documentations.

Note that the `vptr` check, which is part of the `undefined` sanitizer,
may lead to pathologically long compilation times with `gcc` for some
files of `MFront`, which implement heavy template code: it takes more
than ninety minutes to compile
`mfront/src/GenericMaterialPropertyInterfaceBase.cxx` with
`-fsanitize=undefined` (`-O2`), whereas a few minutes are needed when the
`vptr` check is disabled. This check can be excluded by listing
individually the sanitizers of interest, using the corresponding
dedicated options (`alignment`, `bool`, `bounds`, `builtin`, `enum`,
etc.) instead of the `undefined` sanitizer.

When at least one sanitizer is enabled, the `-fno-omit-frame-pointer` flag is
added automatically to ease the interpretation of the reports emitted by the
sanitizers.

  configurations.
- `TFEL_GXX_COMPILER`: path to the `g++` compiler.
- `TFEL_CLANGXX_COMPILER`: path to the `clang++` compiler.
- `TFEL_ICPX_COMPILER`: path to INTEL's `icpx` compiler.
- `TFEL_NVHPC_COMPILER`: path to NVIDIA's `nvhpc` compiler.
- `TFEL_ACPP_COMPILER`: path to AdaptiveCpp's `acpp` compiler.
- `TFEL_CLANG_CUDA_PATH`: path to the `CUDA` toolkit used by `clang` in

  toolkit of `nvcc`). A version of `clang` only supports the versions of

- `HIP_PLATFORM`: `amd` or `nvidia`, required by the configurations based

- `tdls_DIR`: directory where to find the `cmake` files installed by the
  Tiny Device-callable Linear Solvers (`TDLS`) library.

## Supported parallel configurations

The following configurations are supported for parallel computations:

- `cuda-nvcc`: configuration associated with the `CUDA` parallel
  programming model and NVIDIA's `nvcc` compiler
- `cuda-clang`: configuration associated with the `CUDA` parallel
  programming model and LLVM's `clang` compiler
- `hip-hipcc`:  configuration associated with the `HIP` parallel
  programming model and AMD's `hipcc` compiler
- `hip-clang`:  configuration associated with the `HIP` parallel
  programming model and LLVM's `clang` compiler, only supported on the
  NVIDIA platform (`HIP_PLATFORM=nvidia`)
- `stlpar-parunseq-gcc`: configuration associated with `C++` standard
  parallel algorithms using the parallel unsequenced execution policy
  and the `gcc` compiler.
- `stlpar-parunseq-clang`: configuration associated with `C++` standard
  parallel algorithms using the parallel unsequenced execution policy
  and the `clang` compiler.
- `stlpar-parunseq-icpx`: configuration associated with `C++` standard
  parallel algorithms using the parallel unsequenced execution policy
  and the `icpx` compiler.
- `stlpar-parunseq-nvhpc-gpu`: configuration associated with `C++`
  standard parallel algorithms using the parallel unsequenced execution
  policy and NVIDIA's `nvhpc` compiler with offloading on the GPU.
- `sycl-default-icpx`: configuration associated with the `SYCL`
  programming model and Intel's `icpx` compiler.
- `sycl-default-acpp`: configuration associated with the `SYCL`
  programming model and AdaptiveCpp's `acpp` compiler.
- `sycl-gpu-acpp`: tests of the `SYCL` backend for material properties on
  the GPU with AdaptiveCpp's `acpp` compiler. Those tests use the
  configuration files of the `sycl-default-acpp` configuration, which are
  installed if one of those two configurations is selected.
- `kokkos`: configuration associated with the `Kokkos` library, using the
  compiler and the flags of the `Kokkos` installation found by `cmake`
  (default execution space and default host execution space).
- `raja`: configuration associated with the `RAJA` library, compiled by
  `nvcc` if RAJA is built with `CUDA`, by the `C++` compiler otherwise
  (default execution policy and default host execution policy).
- `arcane`: configuration associated with the accelerator API of Arccore,
  built with `CUDA`, compiled by `clang++` as a `CUDA` compiler (the queue
  given at runtime selects the GPU or the cores of the host).
- `openmp-host-gcc`: configuration associated with `OpenMP` and the `g++`
  compiler, the computations being performed by the threads of the host.
- `openmp-offload-nvhpc-gpu`: configuration associated with `OpenMP` and
  NVIDIA's `nvc++` compiler with offloading on the GPU (`-mp=gpu
  -gpu=mem:managed`).
- `openacc-nvhpc-gpu`: configuration associated with `OpenACC` and NVIDIA's
  `nvc++` compiler on the GPU, with the unified memory mode (`-acc=gpu
  -gpu=mem:unified`).
- `openacc-nvhpc-multicore`: configuration associated with `OpenACC` and
  NVIDIA's `nvc++` compiler on the cores of the host (`-acc=multicore`).

The selected configurations are used by the tests of the
`generic-parallel` interfaces for material properties and for behaviours.
The associated configuration files are installed in the
`mfront/configuration-files` subdirectory of the data directory of `TFEL`
(`share/tfel`, or `share/tfel-<suffix>` if `TFEL_APPEND_SUFFIX` is set).
If a file given by the `--configuration-file` option is not found in the
current directory, `MFront` searches it in the directories given by the
preceding `--search-path` options, then in the directories listed by the
`MFRONT_INCLUDE_PATH` variable, then in
`share/tfel/mfront/configuration-files` (or
`share/tfel-<suffix>/mfront/configuration-files` if `TFEL_APPEND_SUFFIX`
is set).

## Add a `build-tests` target

In previous versions, tests were compiled and run using the `check`
target, which internally calls `ctest` for running the test. One
drawback of this approach is that `ctest` could not be run in parallel.

The `build-tests` target (which is a dependency of the `check` target)
only compiles the tests. To run the tests, one may still call the
`check` target or call directly `ctest`.

If the `build-tests` target has not been called, the `check` target
works as in previous versions.

## TFEL's default substitutions

The `getTFELDefaultSubstitutions` function returns some default
substitutions used by `MFront` when reading configuration files and
`tfel-check` when analysing `.check` files. The keys listed below are
delimited by the `@` character in those files and in the map returned
by this function, e.g. `@TFEL_CXX_STANDARD@`.

### General substitutions

- `TFEL_CXX_STANDARD`: the `C++` standard used by the project.

### Supported compilers

- `TFEL_GXX_COMPILER`: path the `g++` compiler. The value associated
  with this key is determined as follows, by order of priority:

  1. by passing the variable `TFEL_GXX_COMPILER` during the invocation of
  `cmake`.
  2. by using `g++` as the main compiler to compile `TFEL`
  3. by searching `g++` using `cmake`'s `find_program` function.
- `TFEL_CLANGXX_COMPILER`: path to `LLVM` `clang++` compiler. The value
  associated with this key is determined as follows, by order of
  priority:

  1. by passing the variable `TFEL_CLANGXX_COMPILER` during the invocation of
  `cmake`,
  2. by using `clang++` as the main compiler to compile `TFEL`,
  3. by searching `clang++` using `cmake`'s `find_program` function.
- `TFEL_ICPX_COMPILER`: path to INTEL's `icpx` compiler. The value
  associated with this key is determined as follows, by order of
  priority:

  1. by passing the variable `TFEL_ICPX_COMPILER` during the invocation of
  `cmake`,
  2. by using `icpx` as the main compiler to compile `TFEL`,
  3. by searching `icpx` using `cmake`'s `find_program` function.
- `TFEL_ACPP_COMPILER`: path to AdaptiveCpp `acpp` compiler. The value
  associated with this key is determined as follows, by order of
  priority:

  1. by passing the variable `TFEL_ACPP_COMPILER` during the invocation of
  `cmake`,
  2. by searching `acpp` using `cmake`'s `find_program` function.
- `TFEL_NVHPC_COMPILER`: path to NVIDIA's `nvhpc` compiler. The value
  associated with this key is determined as follows, by order of
  priority:

  1. by passing the variable `TFEL_NVHPC_COMPILER` during the invocation of
  `cmake`,
  2. by using `nvhpc` as the main compiler to compile `TFEL`,
  3. by searching `nvc++` using `cmake`'s `find_program` function.
- `TFEL_NVCC_COMPILER`: path to NVIDIA's `nvcc` as found by
  `FindCUDAToolkit`.
- `TFEL_HIPCC_COMPILER`: path to AMD's `hipcc` compiler. The value
  associated with this key is determined as follows, by order of
  priority:

  1. by passing the variable `TFEL_HIPCC_COMPILER` during the invocation
    of `cmake`,
  2. by searching `hipcc` using `cmake`'s `find_program` function.

# New `TFEL/Math` features

## Views of tensorial objects with coalescent memory access for data separated by a constant stride

In previous versions, the `View` class allows interpreting a contiguous
memory area as a tensorial object. The `CoalescedView` class allows to
create a tensorial object where each component is referred to by its own
pointer.

The `StridedCoalescedView` assumes that each component is separated by a
constant stride in memory, so that it only have to store one pointer and
the value of the stride.

Such views are efficient on GPUs where coalescent memory access are
preferable.

~~~~{.cxx}
int values[8] = {1, 10, 2, 20, 3, 30, 4, 40};
auto s1 = map_strided<stensor<2u, int>>(values, 2);
~~~~

## Walpole basis

The Walpole basis relative to transverse isotropic fourth-order tensors (`st2tost2`)
is introduced with the `struct` `TransverseIsotropicWalpoleBasis`, member of
`tfel::math`.

## Refactoring of quantities

Quantities were deeply refactored to:

- improve maintainability (code is much more compact),
- allow creating surrogate classes for quantities,
- improve error message,
- reduce size of the generated symbols.

## Adjugate of a tensor and its derivative

# New `TFEL/Material` features

## Logarithmic strain handler

The `LogarithmicStrainHandler` class can be built from the deformation
gradient and the Green-Lagrange strain, computed by the caller without
cancellation (for instance from the displacement gradient).

The divided differences of the logarithm used by the conversions of the
stresses and of the tangent operators are computed with `log1p` from the
eigenvalues of $C - I$, without cancellation when two eigenvalues
are close, whatever the constructor: the special cases for equal
eigenvalues are removed. This changes the results of the behaviours
written in the Hencky strain framework at the level of the rounding
errors in double precision. In single precision, the former formulas
lost all precision when two eigenvalues were close (for a rotated
uniaxial strain of 10 % and a stress not coaxial with the strain, the
relative error reached $10^{-1}$ on the second Piola-Kirchhoff
stress and $4.6\,10^{2}$ on its derivative); it is now below
$4\,10^{-6}$. The former special case of two equal eigenvalues was also
inaccurate in any precision: for a diagonal deformation gradient with
two equal stretches and an anisotropic tangent operator, the material
tangent operator departed from a finite difference by $1.4\,10^{-4}$
in long double ($9\,10^{-8}$ now, the precision of the finite
difference).

## Parallelization

available. This limit can be discarded by
passing`--discard-jobs-limit=true` to `tfel-check`.

### Caution

The user must take care that the commands described in `.check` files
can be run in parallel.

- the jobs shall no exhaust memory.
- the jobs shall not access concurrently to the same resources.

A typical example of conflict would be to have two `.check` files in the
same directory that call `mfront` to build somes shared libraries: the
two `MFront`'s processes may write concurrently files in the `src` and
`include` directories, leading to an undefined behaviour.

Another example would be to use `@CleanDirectories` and `@CleanFiles`
commands inappropriately and erase data used by commands of other
`.check` files.

# New features in `MFront`

## The `@LinearSystemSolver` keyword

The `@LinearSystemSolver` keyword is used to select the linear system
solver. It is followed by the name of the solver. Currently, two solvers
are supported:

- `Default`. This uses the solvers provided natively by the `TFEL/Math`
  library. As implied by its name, this solver is used by default.
- `TDLS` (or equivalently `TinyDeviceCallableLinearSolver`). See
  <https://trsxvz.github.io/TDLS/getting_started.html> for details. If
  `TFEL` is not compiled with support for the `TDLS` library, selecting
  this solver falls back to the `Default` solver.

The name of the solver can optionally be followed by a dictionary
allowing to parametrize the solver.

### Supported Parameters

#### Parameters of the `Default` Linear Solver

The `Default` Linear Solver does not accept any parameter.

#### Parameters of the `TDLS` Linear Solver

The following options are supported:

- `tile_size`: the matrix is processed as a grid of `tile_size x
  tile_size` register tiles. This is the main performance axis of the
  solvers. Tune it per system dimension. The `tile_size` can be a
  strictly positive integer or a string. If `tile_size` is a string, it
  is interpreted as an integer formula whose variables can be any integer
  constant (see the `@IntegerConstant` keyword), `N`, `TVectorSize`,
  `StensorSize` or `TensorSize`. This formula must evaluate to a
  strictly positive integer for all hypotheses supported by the
  behaviour.
- `schedule`: expected values are either `left_looking` (or equivalently
  `left`, `left-looking` or `LeftLooking`) or `right_looking` (or
  equivalently `right`, `right-looking` or `RightLooking`). This
  parameter defines the elimination schedule of the tiled factorization.
- `out_of_tile_search_strategy`: expected values are either
  `first_acceptable` (or equivalently `first-acceptable` or
  `FirstAcceptable`) or `full_scan` (or equivalently `full-scan` or
  `FullScan`). With `first_acceptable`, the search below the tile stops
  at the first candidate whose corrected magnitude reaches the
  out-of-tile search threshold. With `full_scan`, all the rows below
  the tile are scanned and the best corrected candidate wins.
- `unroll_inner_loop`: expected values are either `true` or `false`. If
  `true`, loops indexing register tiles carry a forced-unroll pragma,
  the guard that keeps tiles in registers on GPU backends, where a
  rolled loop indexes the tile dynamically and demotes it to slow local
  memory. If `false`, no unroll pragma anywhere, for faster compiles,
  GPU performance not guaranteed.
- `out_of_tile_search_threshold`: acceptable-pivot threshold of the
  out-of-tile search. An in-tile pivot candidate whose magnitude reaches
  this value is accepted without looking outside the tile; below it, the
  search extends to the rows under the tile (out-of-tile pivoting) and
  the best candidate wins.
- `relative_pivot_threshold`: relative threshold of the pivot choice
  inside the diagonal tile, in `]0, 1]`. The row in place keeps the
  pivot when its magnitude reaches both this fraction of the largest
  in-tile candidate and the out-of-tile search threshold; otherwise the
  largest in-tile candidate wins. This threshold governs the in-tile
  choice only: the out-of-tile search keeps its absolute threshold. A
  value of `1` takes the largest in-tile candidate. This option requires
  a version of `TDLS` later than 0.2.0.
- `singular_pivot_threshold`: the factorization is declared singular
  when even the best candidate of the out-of-tile recovery stays below
  this threshold. This option must be set together with the
  `out_of_tile_search_threshold` option and must not exceed it.
- `out_of_tile_search_diagnostics`: expected values are either `true`
  or `false`. If `true`, an integer member `mfront_tdls_oot_count`,
  readable in user code blocks, reports the number of out-of-tile
  searches of the last linear solve. If `false` (the default), the
  generated code is unchanged.

If a parameter is not defined, the default values are inherited from the
`TiledLUppConfig` class defined by the `TDLS` library. See the
[API reference](https://trsxvz.github.io/TDLS/api/index.html) for
details. At the time of writing this documentation, those default values
are:

- `3` for `tile_size`
- `right_looking` for `schedule`
- `first_acceptable` for `out_of_tile_search_strategy`
- `true` for `unroll_inner_loop`
- `1e-10` for `out_of_tile_search_threshold` (or `1e-4` for single
  precision)
- `0.1` for `relative_pivot_threshold` (`TDLS` 0.2.0 takes the largest
  in-tile candidate, as a threshold of `1`)
- `std::numeric_limits<double>::min()` for `singular_pivot_threshold`
  (or `std::numeric_limits<float>::min()` for single precision)

### Examples

~~~~ {#LinearSystemSolver .cpp}
@LinearSystemSolver TDLS{
  tile_size: 4,
  unroll_inner_loop: false
};
~~~~

~~~~ {#LinearSystemSolver .cpp}
@LinearSystemSolver TDLS{
  tile_size: "StensorSize"
};
~~~~

## Configuration file

`MFront` now allows to define options in a configuration file define
through the `--configuration-file` command line argument as follows:

~~~~{.bash}
$ mfront --configuration-file=config.json --interface=generic-parallel UO2_ShearModulus.mfront
~~~~

Configuration file follows an extented `JSON`-like syntax. It contains
the following sections:

- `dsl_options`
- `material_property_dsl_options`
- `behaviour_dsl_options`
- `model_dsl_options`
- `interfaces_options`
- `material_property_interfaces_options`
- `behaviour_interfaces_options`
- `model_interfaces_options`
- `compilation_options`
- `linking_options`

None of those sections is required. All those sections must introduce a
dictionary.

> **Note**
>
> The options given in sections `dsl_options`,
> `material_property_dsl_options`, `behaviour_dsl_options` and
> `model_dsl_options` may also be retrieved in dedicated configurations
> files, respectively specified by the `--dsl-options-file`,
> `--material-property-dsl-options-file`, `--behaviour-dsl-options-file`,
> and `--model-dsl-options-file` command line arguments introduced in
> Version 4.1.

### Example of configuration file

~~~~{.json}
interfaces_options: {
  generic-parallel: {
    backend: {stlpar: {execution_policy: "par_unseq"}}
  }
}
~~~~

### The `interfaces_options` section

The `interfaces_options` section associates to the name of an interface
a dictionary of options passed to this interface, as in the previous
example. The `material_property_interfaces_options`,
`behaviour_interfaces_options` and `model_interfaces_options` sections
have the same syntax, but their options are only passed to the
interfaces dedicated to material properties, behaviours and models
respectively.

For the `generic-parallel` interfaces, the `backend` option selects the
backend and its options (see the pages of the [`generic-parallel`
interface for material
properties](generic-parallel-material-property-interface.html) and of
the [`generic-parallel` interface for
behaviours](generic-parallel-behaviour-interface.html)).

### The `compilation_options` section

The `compilation_options` section associates to a language (`c`,
`cxx`, `cuda` or `hip`) a dictionary of options, as follows:

~~~~{.json}
compilation_options : {
  cxx : {
    compiler: "nvc++",
    compilation_flags: "-O2 -stdpar=gpu -gpu=mem:managed,nordc -std=c++20 -march=native" 
  }
}
~~~~

#### The `compiler` option

The `compiler` option specifies the compiler used for the given
language. The environment variables `CC`, `CXX`, `CUDA_COMPILER` and
`HIP_COMPILER` take precedence over this option.

#### The `compilation_flags` option

The `compilation_flags` option specifies the compilation flags used for
the given language, as a string or as an array of strings. The
environment variables `CFLAGS`, `CXXFLAGS`, `CUDAFLAGS` and `HIPFLAGS`
take precedence over this option.

#### The `preprocessor_flags` option

The `preprocessor_flags` option specifies the preprocessor flags used
for the given language, as a string or as an array of strings. Those
flags are written before the compilation flags.

### The `linking_options` section

The `linking_options` section defines the options passed to the linker.

#### The `linker_flags` option

The `linker_flags` option specifies the flags passed to the linker, as a
string or as an array of strings. Those flags are placed after the
object files, so that the libraries they give (for instance `-ltbb`) are
not ignored by the linkers using the `--as-needed` policy. The
environment variable `LDFLAGS` takes precedence over this option.

### Available backends

- `stlpar`: parallel algorithms of the C++ standard library, on CPUs or on
  NVIDIA GPUs with `nvc++ -stdpar=gpu`;
- `cuda` and `hip`;
- `sycl`;
- `kokkos`;
- `raja`;
- `openmp`: threads of the host or offloading to a device;
- `openacc`: device selected by the compiler and the OpenACC runtime (GPU
  or cores of the host with `nvc++`);
- `arcane`: accelerator API of Arccore, the core component of the Arcane
  framework (device selected by the queue given at runtime).

### Changes of the generated functions

The functions generated for a material property `S` are now (version 4
of those functions, `MFRONT_GPMP_API_VERSION` macro):

~~~~{.cxx}
int S_generic_parallel(mfront_gpmp_OutputStatus* const,
                       const mfront_gpmp_BatchData* const);
int S_generic_parallel_report(mfront_gpmp_OutputStatus* const,
                              const mfront_gpmp_Statistics* const);
~~~~

- the data of a batch (`mfront_gpmp_BatchData`) give the number of
  points, the output and the arguments (pointer and stride between two
  points), the out of bounds policy, the optional statuses of the points,
  the optional statistics and the execution policy, as for the
  behaviours (see the section on the execution policies below). The
  queue of the `SYCL` backend, which was a specific argument of its
  functions, is now given by its execution policy. The function with
  contiguous arrays (suffix `2`) is removed: the backends treat the
  contiguous arrays as a special case.
- the names of the functions end with `_generic_parallel`, and the names
  of the material properties can't contain `_generic_parallel`. A library
  generated by this interface does not contain the function of a point of
  the `generic` interface: it is recognized by the
  `<name>_generic_parallel_api_version` symbol, next to the
  `<name>_generic_parallel_backend`,
  `<name>_generic_parallel_memory_space` and
  `<name>_generic_parallel_execution_policy` symbols.
- the evaluation at each point is the one of the `generic` interface:
  same checks, same status at each point (`0`, `1`, `-1` or `-4`, written
  in the optional array of the statuses of the points), same retained
  check. The output is `NaN` where the evaluation fails, and the computed
  value where it is not finite.
- the output status (`mfront_gpmp_OutputStatus`) is specific to the
  interface: as for the behaviours, it gives the numbers of points where
  the evaluation failed and where a bound is violated with the warning
  policy, and the first point of each kind. Its status is the error of the
  batch, otherwise the status of the first point where the evaluation
  failed, otherwise the status of the first point where the result is
  unreliable. The errors of the batch are `-5` (invalid arguments), `-6`
  (invalid parameters) and `-7` (runtime error of the backend, including
  the exceptions thrown on the host by its runtime). An empty batch is
  accepted without any check.
- the codes change: `-7` now denotes a runtime error of the backend (an
  inconsistent uniform output gives `-5`), `-2` is no longer used (the
  exceptions thrown on the host give `-7`), `-6` only reports invalid
  parameters (the errors of the `CUDA` and `HIP` runtimes give `-7`), and
  the output is `NaN` at the points where the evaluation fails instead of
  being left unchanged.
- the kernels only update the statistics of the evaluation when an event
  occurs at a point: with atomic operations (`cuda`, `hip`, `sycl`,
  `kokkos` and `raja` backends), the cost of the error reporting is null
  when the evaluation succeeds. The `stlpar`, `openmp` and `openacc`
  backends merge the statuses of the points by a reduction.
- with statistics given by the calling code, on all the backends, the
  output status only reports the errors of the batch, and the result is
  given by the `<name>_generic_parallel_report` function once the
  computations are completed. If the execution policy requests an
  asynchronous evaluation, the backends with a queue may return before
  the end of the computations.
- the `stlpar` and `sycl` backends have a new `device_stack_size` option.
  The new `openmp` backend has the `offload` and `device_stack_size`
  options, the new `openacc` backend the `device_stack_size` option. The
  `cuda`, `hip`, `kokkos` and `raja` backends increase the stack size of
  the threads if the kernel requires it, as for the behaviours.
- the automatic data transfers of the `sycl` backend are shared with the
  behaviours: they also copy the statuses of the points and the
  statistics.
- the default number of threads per block of the `cuda` and `hip`
  backends is `128`, rounded up to a multiple of the warp size, as for the
  behaviours.

## The `generic-parallel` interface for behaviours

The `generic-parallel` interface integrates a behaviour, or executes a
standalone model, over a batch of integration points, on GPUs or on CPUs,
with the backends of the interface for material properties. See [this page
for details](generic-parallel-behaviour-interface.html).

The generated libraries provide, under the names of the functions of the
`generic` interface followed by `_generic_parallel`:

- the integration of a batch, the initialize functions and the
  post-processings over a batch;
- the rotation functions of the orthotropic behaviours over a batch;
- the execution of the standalone models (`@DSL Model`) over a batch.

The data structures exchanged with the generated functions are declared
in `MFront/GenericParallelBehaviour/BatchData.h`. Their version is given
by the `MFRONT_GPB_API_VERSION` macro (`4`). The values of the variables
at all the points are described by fields, which support several layouts
(point by point, component by component, uniform values), and the
material properties and the external state variables can be given
variable by variable. The statistics of the batch may be given by the
calling code: they are then accumulated on the device and analysed by the
`<name>_generic_parallel_report` function exported by the library, and
the computations may be asynchronous. The output status, the statistics,
the execution policies and the errors of the batch (`-5` invalid
arguments, `-6` invalid parameters, `-7` runtime error of the backend)
are the ones of the material properties,
the time step scaling factor being added. The libraries export the
`<name>_generic_parallel_backend`, `<name>_generic_parallel_memory_space`,
`<name>_generic_parallel_execution_policy` and
`<name>_generic_parallel_api_version` symbols. The configuration files
are shared with the `generic-parallel` interface for material properties.
The name of a behaviour or of a model can't contain `_generic_parallel`.

## Execution policies of the `generic-parallel` interfaces

The functions generated by the `generic-parallel` interfaces receive an
execution policy (`execution_policy` member of the data of a batch), or a
null pointer for the default policy of the backend (default stream,
default instance of the execution space, default resource). The policies
are `C++` classes of the `mfront::generic_parallel` namespace, one per
backend, declared in the headers of `MFront/GenericParallel`:

- `CUDABackendExecutionPolicy` and `HIPBackendExecutionPolicy`, which hold
  a stream;
- `SyclBackendExecutionPolicy`, which holds a queue. The `sycl` backend has
  no default policy;
- `KokkosBackendExecutionPolicy<ExecutionSpace>`, which holds an instance
  of the execution space;
- `RAJABackendExecutionPolicy<Resource>`, which holds a resource of camp;
- `ArcaneBackendExecutionPolicy`, which holds a queue of Arccore. The
  `arcane` backend has no default policy;
- `ParallelSTLBackendExecutionPolicy`, `OpenMPBackendExecutionPolicy` and
  `OpenACCBackendExecutionPolicy`.

All the policies have two common options (`BackendExecutionCommonPolicy`):
`preserve_stack_size` (the stack size of the threads of the device is
never modified) and `asynchronous` (the function may return once the
computations are submitted). An asynchronous computation requires
statistics. A policy of another backend is refused. A policy is created by
a function taking its options, which can be given by designated
initializers:

~~~~{.cxx}
#include "MFront/GenericParallel/CUDABackendExecutionPolicy.hxx"
const auto policy = mfront::generic_parallel::makeCUDABackendExecutionPolicy(
    {.common_options = {.asynchronous = true}, .stream = stream});
d.statistics = statistics;
d.execution_policy = &policy;
~~~~

Each generated library exports the identifier of the policy it expects
(`<name>_generic_parallel_execution_policy` symbol). In `C`, the type of
the policies is opaque (`mfront_gp_AbstractBackendExecutionPolicy`, see
`MFront/GenericParallel/BackendExecutionPolicy.h`): a `C` code can only
select the default policy. The base class of the policies,
`AbstractBackendExecutionPolicy`, is defined by the new
`MFrontGenericParallelRuntime` library (`--mfront-generic-parallel-runtime`
option of `tfel-config`), which must be linked by the codes creating
policies. The generated libraries do not need it. Its table of virtual
functions starts with `getIdentifier` with the ABI of Visual Studio and
with the Itanium ABI: a policy created by a program built by Visual
Studio can be checked by a library generated by a `TFEL` built with
MinGW, and the reverse.

## Libraries of the `generic-parallel` interfaces also containing the functions of the `generic` interface

The `generic-parallel` interfaces for material properties, behaviours and
models are built on their `generic` interface: the code evaluating a
material property at a point is written once for the `generic`, `Cyrano`
and `generic-parallel` interfaces, and the interface of the models
derives from the `generic` one.

With the `generic_functions` option of the interface, the generated
library also contains the functions of the `generic` interface:

~~~~{.cxx}
interfaces_options: {
  generic-parallel: {
    generic_functions: true
  }
}
~~~~

Such a library exports `Generic` as interface and can be used as a
library of the `generic` interface (by `MTest` or `MGIS` for instance).
Its functions of batches of points are detected by the
`<name>_generic_parallel_api_version` symbol. It has one set of
parameters, shared by both kinds of functions, and, for a behaviour, one
out of bounds policy. See the pages of the interfaces for
[material properties](generic-parallel-material-property-interface.html)
and for [behaviours](generic-parallel-behaviour-interface.html).

The configuration files associated with the `icpx` compiler
(`stlpar-parunseq-icpx` and `sycl-default-icpx`) request a precise
floating point model (`-fp-model=precise`, the default one being fast).
This model also restores the support of `errno` by the mathematical
functions, so that the functions of a point report the statuses `-3` as
the `generic` interface. With `nvc++`, the mathematical functions only
set `errno` with the `-Mnobuiltin` option, which the configuration files
do not give.

## Writing behaviours usable on GPUs

- the `TFEL_DEVICE_CODE` macro is defined when device code is compiled.
  With the compilers translating host and device code in a single pass
  (`nvc++ -stdpar=gpu`, `nvc++ -mp=gpu`, `nvc++ -acc=gpu`, generic
  compiler of AdaptiveCpp), it is defined in the whole translation unit (see the
  [`TFEL/Config` page](tfel-config.html)).
- `tfel::fail` reports an error in host and device code: it throws an
  exception on the host and returns `false` in device code.
- `abortResolution` (implicit DSLs) and `abortIntegration` (Runge-Kutta
  DSLs) make the integration fail in device code, as an exception does on
  the host. `abortResolution` is a method of `TinyNonLinearSolverBase`.
  The isotropic DSLs have no equivalent: an error reported in their flow
  rules in device code only makes the integration fail once the maximum
  number of iterations is reached.
- the `@SharedData` keyword declares a data shared by all the integration
  points, built once on the host, for instance the slip systems of the
  grains of a polycrystal read from a file. The `generic-parallel`
  interface copies it in the memory of the device (see `mfront
  --help-keyword=Implicit:@SharedData`).
- `tfel::utilities::getConstantObject` gives access to objects built at
  compile time in host and device code.
- the static variables read by the code blocks are replaced by
  `TFEL_STATIC_VARIABLE(<class>::<name>)`, which gives a temporary copy
  of the variable in device code (and in the whole translation unit with
  the compilers translating host and device code in a single pass), since
  device code can't refer to a constexpr static variable defined in host
  code (for instance a quantity given to an operator taking its arguments
  by reference). The address of such a variable can't be taken, and
  a reference derived from it is only valid until the end of the full
  expression (see the [`TFEL/Config` page](tfel-config.html)).
- the `device_compatible_class` DSL option requires a behaviour class
  usable in device code: dynamically allocated arrays are not used and
  the parameters treated as static variables are declared as constant
  members. This option is set when the `generic-parallel` interface is
  selected, and is given to the behaviour variables.
- the comparison to a numerical jacobian (`@CompareToNumericalJacobian`)
  and the profiling (`@Profiling`) are only performed on the host, and
  never with the compilers translating host and device code in a single
  pass (see the `TFEL_DEVICE_CODE` macro).

## Numerical type of the generic interfaces: the `real_type` DSL option

The `real_type` DSL option selects the numerical type of the behaviours
and of the material properties generated by the `generic` and
`generic-parallel` interfaces: `double` (the default) or `float`, for
instance:

~~~~{.bash}
$ mfront --obuild --interface=generic --dsl-option=real_type:float \
    Plasticity.mfront
~~~~

- the type of the data exchanged with the generated functions,
  `mfront_gb_real` and `mfront_gmp_real`, is given by the
  `MFRONT_GB_REAL_TYPE` and `MFRONT_GMP_REAL_TYPE` macros (`double` if
  they are not defined), which the interfaces define at the beginning of
  the generated headers and sources.
- each entry point exports the size in bytes of its numerical type
  (`<name>_real_size`), read by
  `ExternalLibraryManager::getRealSize` (`sizeof(double)` for a library
  generated before this option) and checked by
  `ExternalLibraryManager::checkRealSize`. The versions of the
  application programming interfaces (`<name>_api_version`,
  `<name>_generic_parallel_api_version`) are shifted by 1000 for another
  type than `double`, so that a caller expecting `double` refuses the
  library even if it does not read the size.
- the other interfaces and the standalone models (`@DSL Model`) refuse
  another type than `double`. The `mfront` interface is accepted: it
  generates the material laws used by the behaviours (`@MaterialLaw`),
  computed in `double` and called with conversions.
- `MTest` only accepts behaviours, material properties and evolutions
  generated with `double`.
- with `float`, the convergence criteria of the implicit, Runge-Kutta and
  isotropic DSLs (`@Epsilon`) are raised to a tenth of the machine
  epsilon of `float` (about `1.2e-8`), and the perturbation of the
  numerical jacobian to the machine epsilon (about `1.2e-7`), with a
  warning: the values chosen for `double` (`1e-14` or less) can't be
  reached. The criteria of these DSLs are absolute and their residuals are
  expressed in strains: a looser criterion leaves errors on the stresses
  of the order of the criterion times the elastic moduli. The default
  criterion (`1e-8`, when `@Epsilon` is not used), close to this bound, is
  kept, and the default perturbation (a tenth of the criterion) is raised
  without warning. The warnings advising more stringent criteria are
  written for `double`: with `float`, only a criterion looser than `1e-5`
  is reported. The comparison to a numerical jacobian
  (`@CompareToNumericalJacobian`) uses by default the convergence
  criterion, which is too strict for finite differences computed in
  `float`: its criterion must then be given explicitly
  (`@JacobianComparisonCriterion`).
- an expression of a floating-point type can be assigned to a
  mathematical object of `TFEL` of another floating-point type, possibly
  narrower (`IsAssignableTo`), so that the existing behaviours, which use
  `double` literals, compile with `float`. Writing the literals with the
  numerical type of the behaviour (`real(2)`) avoids computations in
  `double`, which are slow on most GPUs. Mixed calls to `std::max` or
  `std::min` (`std::max(x, 0.)` with `x` in `float`) do not compile and
  must be rewritten.
- the coefficients of a behaviour must be representable in `float`: for
  instance, a Norton law written in Pa with a coefficient `A = 8e-67`
  gives `A = 0` in `float`. Writing it as `A (seq / K)^n` with
  `K = A^(-1/n)`, or in MPa, avoids it.

## Displacement gradient for finite strain behaviours

The caller of a finite strain behaviour generated by the `generic` or
`generic-parallel` interfaces may give the displacement gradient
$H = F - I$ instead of the deformation gradient $F$, which keeps the
relative precision of small strains in single precision. This option is
given at runtime and accepted by the behaviours exporting the symbol
`<behaviour_function_name>_AcceptsDisplacementGradient`. See [this
section](generic-behaviours-interface.html#sec:generic_behaviour_interface:displacement_gradient)
for details.

## Plane stress in the `generic` and `generic-parallel` interfaces

In plane stress (`PlaneStress` and
`AxisymmetricalGeneralisedPlaneStress`), the axial component of the
deformation gradient given by the caller is no longer used by the
interface in the conversions of the stresses and of the tangent
operators of the finite strain behaviours: they use the one computed by
the behaviour. The callers (MGIS, MTest) give an axial component equal
to one. Before:

- the behaviours written with the deformation gradient added the
  computed component to it: their first and second Piola-Kirchhoff
  stresses were wrong by a factor of two;
- in the Green-Lagrange strain framework, the same addition made the
  Cauchy stress wrong by a factor of two;
- in the Hencky strain framework, the conversions used the axial
  component of the caller: the first and second Piola-Kirchhoff stresses
  were wrong by the axial strain, in relative value.

The axial component of the strain given to the behaviours written in the
Green-Lagrange or Hencky strain frameworks is now zero, whatever the
caller gives. For the behaviours written with the deformation gradient,
the initial value of the `AxialDeformationGradient` internal state
variable, set by the caller, shall be one.

## Improvements to the `Cast3M` interface

### Improved generation of `Gibiane` input file

The `Cast3M` interface generates automatically an example of `Gibiane`
input file to integrate which each `MFront` behaviour. This example is
meant to be used a template and do not pretend to be usable without
modification by the user. For instance, previous versions of `MFront`
did not guarantee that the name of the variables (limited to `4`
characters) were unique. Version 5.2 improves this. To illustrate this,
one may compare the output of Version 5.1 and Version 5.2:

~~~~
* Version prior to 5.2
statev = 'MOTS' 'EERR' 'EEZZ' 'EETT' 'EERZ' 'KHRR' 'KHZZ' 'KHTT' 'KHRZ' 'KHRR' 'KHZZ' 'KHTT' 'KHRZ' 'P';
* Version 5.2
statev = 'MOTS' 'EERR' 'EEZZ' 'EETT' 'EERZ' 'KHRR' 'KHZZ' 'KHTT' 'KHRZ' 'V0' 'V1' 'V2' 'V3' 'P';
~~~~

In Version 5.1, the variable name `KHRR` is declared twice. `Cast3M`
does not generate an error although duplicated names leads to erroneous
results. Version 5.2 avoids this pitfall.

## The `plastic_deformation_gradient_normalisation_corrections` option of the `FiniteStrainSingleCrystal` brick

The `FiniteStrainSingleCrystal` brick normalises the inverse of the
plastic deformation gradient increment by the cubic root of its
determinant. The derivatives of this normalisation with respect to the
plastic slips were explicitly neglected in the jacobian and in the
consistent tangent operator, as numerical tests showed (or at least
seemed to show) that they were negligible.

These derivatives are now taken into account by default (see Issue
#1359). The results are not affected, up to the convergence criteria,
but the convergence is when the deformation gradient is not fully
imposed: the global iterations recover their quadratic convergence. The
boolean option
`plastic_deformation_gradient_normalisation_corrections` allows to
neglect them:

~~~~{.cpp}
@Brick FiniteStrainSingleCrystal{
  plastic_deformation_gradient_normalisation_corrections : false
};
~~~~

The same derivatives are explicitly neglected in the
`FiniteStrainSingleCrystal`, `FiniteStrainSingleCrystal2` and
`FiniteStrainSingleCrystal_NumericalJacobian` test behaviours. Versions
taking them into account are provided by the
`FiniteStrainSingleCrystal_WithCorrections`,
`FiniteStrainSingleCrystal2_WithCorrections` and
`FiniteStrainSingleCrystal_NumericalJacobian_WithCorrections` test
behaviours.

## Other fixes

The following defects have been fixed while adding the support of device
code:

- `generic` interface, finite strain behaviours: the outputs were not
  converted after an unreliable result (status `0`); the `DTAU_DDF`
  tangent operator of the behaviours written in the logarithmic strain
  was computed with the logarithmic strain handler of the beginning of
  the time step; the post-processings did not use the internal state
  variables at the end of the time step; the initialize functions of the
  behaviours written in the Green-Lagrange or Hencky strains did not
  compile; the prediction operator ignored the request of the speed of
  sound.
- `generic` interface, finite strain behaviours: the stress computed by
  an initialize function was lost for the first and second
  Piola-Kirchhoff stresses and for the behaviours written in the
  Green-Lagrange or Hencky strains.
- `generic` interface, rotation functions of orthotropic behaviours: wrong
  offset of the second order tensors in the variants treating arrays of
  points, scalars not copied, vectors not supported. The tangent operator
  blocks associated with arrays of variables, and the blocks mixing a
  vector and a (symmetric) tensor or a tensor and a symmetric tensor, are
  now rotated.
- `generic` interface: an exception thrown by the constructor of the
  behaviour, for instance when a data declared by `@SharedData` can't be
  built, left the generated function. It is now reported as a failure, and
  the time step scaling factor is left unchanged.
- `generic` interface, models: the failures of the physical bounds were
  ignored when device code is selected in the whole translation unit. The
  parameters of a model were shared by the libraries generated for this
  model by the `generic` and `generic-parallel` interfaces. The models
  with material properties and parameters treated as static variables,
  and the static variables of the models using quantities, are now
  supported.
- implicit DSLs: a failure of a substitution in the computation of the
  tangent operator could be erased by a later successful call.
- `StandardElastoViscoPlasticity` brick: wrong name of the derivative of
  a yield radius interpolated by a cubic spline when an identifier is
  used.
- `generic` interface for material properties: the message of a violated
  physical upper bound said below instead of over, and `errno` was not
  restored when an upper bound was violated with the strict policy. The
  documentation of the bounds status now describes its sign as
  implemented: negative if the evaluation failed (physical bound, or bound
  with the strict policy), positive with the warning policy.
- material properties, all interfaces: the physical bounds of an argument
  were only exported if this argument also had standard bounds.
- `MFront`: the linker flags are placed after the object files, so that
  the libraries they give (for instance `-ltbb`) are not ignored by the
  linkers using the `--as-needed` policy.
- `generic-parallel` interface for material properties: `errno` was
  checked after the parallel execution, which made the first call fail;
  the bounds of the output were written past the end of the statuses; the
  headers of the backends overwrote each other; the device memory of the
  `SYCL` backend was never freed; the values between the values of a
  strided output were overwritten.
- `RungeKutta` DSL, `rkCastem` algorithm: the `young` variable, when
  defined, is used again as the stress error normalization factor, as
  stated in the release notes of Version 4.1: the other choices (first
  component of the stiffness tensor, variable associated with the
  `YoungModulus` glossary name) were used instead, and a behaviour whose
  `young` variable is a static variable was refused. The time steps may
  change for the behaviours whose `young` variable differs from the factor
  which was used instead.
- `DDIF2` brick: a single non constant fracture stress was refused, and
  three non constant fracture stresses or fracture energies were replaced
  by the first one in all directions. Only one of the `softening_slope`,
  `softening_slopes`, `fracture_energy` and `fracture_energies` options
  can be given (the other combinations failed later with an unclear
  message), and the sign of the constant components following a non
  constant first component of `fracture_stresses`, `softening_slopes` or
  `fracture_energies` is now checked.
- isotropic DSLs: with the `use_stress_update_algorithm` option, the code
  evaluating a non constant Poisson ratio at the beginning of the time
  step did not compile with `@UseQt true`.
- files of parameters of the material properties and of the behaviours:
  the line given in the error messages was always the first one. For
  the material properties, `errno` was not restored after the reading of
  this file: a value setting `errno` when converted (a subnormal number)
  made the first evaluation of the `generic` interface fail with the
  status `-3`.
- `tfel-check`: a command with the `shall_fail` option set to `true`
  which succeeded was reported as a success.
