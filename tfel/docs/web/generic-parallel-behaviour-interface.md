The `generic-parallel` interface integrates a behaviour, or executes a
standalone model, over a batch of integration points, on GPUs or on CPUs,
with one of the following backends: `CUDA`, `HIP`, parallel algorithms of
the C++ standard library, Kokkos, RAJA, SYCL, OpenMP, OpenACC and the
accelerator API of Arccore, the core component of the Arcane framework. It
follows the
design of the [`generic-parallel` interface for material
properties](generic-parallel-material-property-interface.html): backends
selected by an option, configuration files, libraries suffixed by the name
of the backend. The options shared by the backends of both interfaces have
the same meaning.

The implementation differs. The code of a material property is a function
of its arguments: the backends of the interface for material properties
write a loop over the points in the generated code. The integration of a
behaviour involves many more steps (gathering the data of a point, choice
of the tangent operator, finite strain kinematics, statistics of the
batch): the backends of the interface for behaviours call function
templates, defined in the `MFront/GenericParallelBehaviour` headers, which
only differ by the primitive applying a function at each point.

Integrating a batch is equivalent to calling the function generated by the
[`generic` interface](generic-behaviours-interface.html) at each
integration point, with the same time increment and the same computation
options. The two interfaces can be used together:

~~~~{.bash}
$ mfront --obuild --interface=generic --interface=generic-parallel \
         --configuration-file=config-cuda-nvcc.json Plasticity.mfront
The following libraries have been built :
- libBehaviour.so :  Plasticity_Tridimensional ...
- libGenericParallelBehaviour-cuda.so :  Plasticity_Tridimensional_generic_parallel ...
~~~~

# Generated functions

For each modelling hypothesis, the interface generates a function whose
name is the one generated by the `generic` interface followed by
`_generic_parallel`:

~~~~{.cxx}
int Plasticity_Tridimensional_generic_parallel(
    mfront_gpb_OutputStatus* const, const mfront_gpb_BatchData* const);
~~~~

The library also exports the function analysing the statistics given by
the calling code, for instance for asynchronous computations, common to
all the modelling hypotheses and to all the functions of the behaviour
(see the `Execution policies and statistics` section):

~~~~{.cxx}
int Plasticity_generic_parallel_report(mfront_gpb_OutputStatus* const,
                                       const mfront_gpb_Statistics* const);
~~~~

This is the naming of the functions of the material properties
(`S_generic_parallel` and `S_generic_parallel_report`). The name of a
behaviour or of a model can't contain `_generic_parallel`.

The functions are declared in the
`MFront/GenericParallelBehaviour/<name>-generic-parallel-<backend>.hxx`
header, where `<name>` is the name of the generated functions without the
modelling hypothesis. In the previous example, this header is
`Plasticity-generic-parallel-cuda.hxx`.

The initialize functions and the post-processings are also executed over
a batch:

~~~~{.cxx}
int Plasticity_Tridimensional_InitializeFunction_ElasticStrainFromInitialStress_generic_parallel(
    mfront_gpb_OutputStatus* const,
    const mfront_gpb_BatchData* const,
    const mfront_gpb_ConstField* const inputs);
int Plasticity_Tridimensional_PostProcessing_PrincipalStrain_generic_parallel(
    mfront_gpb_OutputStatus* const,
    const mfront_gpb_Field* const outputs,
    const mfront_gpb_BatchData* const);
~~~~

As with the `generic` interface:

- an initialize function is executed on the state at the beginning of the
  time step and writes the thermodynamic forces and the internal state
  variables of the state at the end of the time step. Its inputs may be null
  if the initialize function has no input.
- a post-processing is executed on the state at the end of the time step.

The output status and the `statuses` field have the same meaning as for
the integration. In particular, the status is `1` on success, whereas the
functions of the `generic` interface return `0` on success. Those
functions write the `statuses` field but not the `rdts` field, so that
they can be called with the batch data of the integration without
overwriting the time step scaling factors proposed by the behaviour.

For orthotropic behaviours, the rotation functions of the `generic`
interface are generated for batches (`rotateGradients`,
`rotateThermodynamicForces`, `rotateTangentOperatorBlocks`, and for finite
strain behaviours the variants associated with the stress measures and the
tangent operators, such as `rotateThermodynamicForces_PK1Stress`):

~~~~{.cxx}
int OrthotropicElastic_Tridimensional_rotateGradients_generic_parallel(
    mfront_gpb_OutputStatus* const, const mfront_gpb_RotationData* const);
~~~~

~~~~{.cxx}
typedef struct mfront_gpb_RotationData {
  mfront_gb_size_type number_of_points;
  mfront_gpb_Field destination;
  mfront_gpb_ConstField source;             // may be the destination
  mfront_gpb_ConstField rotation_matrices;  // 9 values per point
  mfront_gpb_Statistics* statistics;        // optional, see below
  const mfront_gp_AbstractBackendExecutionPolicy* execution_policy;  // see below
} mfront_gpb_RotationData;
~~~~

The rotation matrix is uniform if the point stride of the
`rotation_matrices` field is null. The rotation matrices have the meaning
and the storage of the `generic` interface (rotation from the global frame
to the material frame, stored in column-major format).

All the tangent operator blocks can be rotated, with both interfaces. A
block associated with arrays of variables is rotated entry by entry. A
block for which TFEL has no type which can be rotated (derivative of a
vector with respect to a symmetric tensor or a tensor, and conversely,
derivative of a tensor with respect to a symmetric tensor) is rotated by
`mfront::gb::rotateTangentOperatorBlock`, which computes
\(Q_{1}\,K\,Q_{2}^{T}\), where \(Q_{i}\) is the matrix of the rotation of the
objects of each variable by `change_basis`.

The library also exports the same symbols as the `generic` interface
(names and types of the variables, parameters, etc.) and the functions
changing the parameters and the out of bounds policy. The standalone
models use their default out of bounds policy: no function changing it is
generated for them. The `<name>_mfront_interface` symbol is equal to
`GenericParallel`, for the behaviours and for the standalone models, so
that a library of this interface can't be taken for a library of the
`generic` interface. The `<name>_generic_parallel_backend` symbol gives the
backend of the library (`cuda`, `hip`, `stlpar`, `kokkos`, `raja`, `sycl`,
`openmp`, `openacc` or `arcane`). The `<name>_generic_parallel_execution_policy`
symbol (a `const char*`) gives the identifier of the execution policy
expected by the generated functions (see the `Execution policies and
statistics` section). The `<name>_generic_parallel_memory_space` symbol
(a `const char*`) tells the calling code where the fields must be located:

- `host`: the computations are performed on the host, the fields must be
  accessible by the host;
- `device`: the computations are performed on a device, which may not
  access the ordinary memory of the host: the fields must be accessible by
  the device (memory of the device, managed or shared memory). The library
  can't assume that the device accesses the ordinary memory of the host,
  even if the device is a CPU (`sycl` backend without data transfers and
  `arcane` backend, the device being the one of the queue of the execution
  policy given at runtime);
- `any`: the fields may be located anywhere (SYCL backend with automatic
  transfers, `nvc++` with the unified memory mode).

This memory space is set when the library is compiled, since the target of
some programming models is selected by the compiler (C++ parallel
algorithms, OpenMP and OpenACC with `nvc++`) or by the configuration of a
library
(execution space of Kokkos, execution policy of RAJA). See
`MFront/GenericParallel/MemorySpace.hxx`.

The data structures are declared in
`MFront/GenericParallelBehaviour/BatchData.h`. Their version is given by the
`MFRONT_GPB_API_VERSION` macro, incremented at each incompatible change, and
exported by the libraries (`<name>_generic_parallel_api_version` symbol,
an `unsigned short`), so that the calling code can check that it uses the same
structures. The structures are named (`typedef struct mfront_gpb_BatchData
{...} mfront_gpb_BatchData;`), so that they can be forward declared.
In `C++`, they are also available in the `mfront::gpb` namespace
(`mfront::gpb::BatchData`, `mfront::gpb::OutputStatus`, etc.). The header
also declares the types of the pointers to the generated functions
(`mfront_gpb_BatchBehaviourPtr`, `mfront_gpb_BatchInitializeFunctionPtr`,
`mfront_gpb_BatchPostProcessingPtr`, `mfront_gpb_BatchRotationPtr` and
`mfront_gpb_ReportPtr`).

## Fields

The values of a group of variables (gradients, internal state variables,
etc.) at all the integration points are described by a field:

~~~~{.cxx}
typedef struct mfront_gpb_ConstField {
  const mfront_gb_real* values;
  mfront_gb_size_type point_stride;
  mfront_gb_size_type component_stride;
} mfront_gpb_ConstField;
~~~~

The `j`-th component at the `i`-th point is stored at
`values[i * point_stride + j * component_stride]`. Usual layouts are:

- point by point: `point_stride` is the size of the group and
  `component_stride` is equal to one. This is the layout of `MGIS`.
- component by component: `point_stride` is equal to one and
  `component_stride` is the number of points. On GPUs, this layout gives
  coalesced memory accesses.
- uniform values (inputs only): `point_stride` is null.

`values` may be null if the group is empty or if an optional output
(energies, time step scaling factors) is not requested.

`mfront_gpb_Field` is the mutable version of `mfront_gpb_ConstField`. The
group of variables of a point are the ones of the `generic` interface: for
instance, the temperature is the first external state variable.

## States

The states at the beginning and at the end of the time step are described
by the following structures:

~~~~{.cxx}
typedef struct mfront_gpb_InitialState {
  mfront_gpb_ConstField gradients;
  mfront_gpb_ConstField thermodynamic_forces;
  mfront_gpb_ConstField mass_density;
  mfront_gpb_ConstField material_properties;
  mfront_gpb_ConstField internal_state_variables;
  mfront_gpb_ConstField stored_energy;
  mfront_gpb_ConstField dissipated_energy;
  mfront_gpb_ConstField external_state_variables;
  const mfront_gpb_ConstField* material_properties_by_variable;       // optional
  const mfront_gpb_ConstField* external_state_variables_by_variable;  // optional
} mfront_gpb_InitialState;

typedef struct mfront_gpb_State {
  mfront_gpb_ConstField gradients;
  mfront_gpb_Field thermodynamic_forces;      // output
  mfront_gpb_ConstField mass_density;
  mfront_gpb_ConstField material_properties;
  mfront_gpb_Field internal_state_variables;  // output
  mfront_gpb_Field stored_energy;             // output, optional
  mfront_gpb_Field dissipated_energy;         // output, optional
  mfront_gpb_ConstField external_state_variables;
  const mfront_gpb_ConstField* material_properties_by_variable;       // optional
  const mfront_gpb_ConstField* external_state_variables_by_variable;  // optional
} mfront_gpb_State;
~~~~

The members have the meaning of the members of the states of the
`generic` interface. In the state at the end of the time step, the
thermodynamic forces, the internal state variables and the energies are
outputs. The energies are optional outputs. The mass density is only
required if the speed of sound is requested.

### Material properties and external state variables given variable by variable

The material properties and the external state variables can also be given
variable by variable, with one field per variable. This allows a different
layout for each variable, for instance uniform values for some material
properties only, as in `MGIS`:

~~~~{.cxx}
mfront_gpb_ConstField mps[2];
mps[0] = {&young_modulus, 0, 1};       // uniform value
mps[1] = {poisson_ratios, 1, 1};       // one value per point
d.s0.material_properties_by_variable = mps;
d.s1.material_properties_by_variable = mps;
~~~~

The variables follow the order of the material properties (or of the
external state variables) of a point, the elements of an array being
distinct variables. The components of a variable are given by the
`component_stride` of its field. If `material_properties_by_variable` (or
`external_state_variables_by_variable`) is null, the group field
`material_properties` (or `external_state_variables`) is used.

The arrays of fields are only read on the host: only the values must be
accessible by the device. Both forms are converted on the host in the same
description, so that the code executed at each point does not depend on
the form. The material properties and the external state variables of a
point are always copied in local arrays.

## Batch data

~~~~{.cxx}
typedef struct mfront_gpb_BatchData {
  mfront_gb_size_type number_of_points;
  mfront_gb_real dt;
  mfront_gb_real options[3];   // the three first values of K
  mfront_gb_real rdt;          // initial time step scaling factor
  mfront_gpb_Field tangent_operators;
  mfront_gpb_Field rdts;       // optional
  mfront_gpb_Field speed_of_sound;
  mfront_gpb_InitialState s0;
  mfront_gpb_State s1;
  int* statuses;               // optional
  mfront_gpb_Statistics* statistics;  // optional, see below
  const mfront_gp_AbstractBackendExecutionPolicy* execution_policy;  // see below
} mfront_gpb_BatchData;
~~~~

`options` has the meaning of the three first values of the array `K` of the
`generic` interface (type of computation, stress measure and tangent
operator for finite strain behaviours). The tangent or prediction operators
are written in `tangent_operators`, which is not used if no tangent
operator is requested. The time step scaling factors of the points are
written in `rdts`, if its values are not null. `speed_of_sound` is only
used if the speed of sound is requested by the options.

If not null, `statuses[i]` is the status of the `i`-th point: `1` if the
integration succeeded, `0` if it succeeded with a time step scaling factor
lower than `0.99`, and `-1` if it failed.

For finite strain behaviours, the sizes of the thermodynamic forces and of
the tangent operator of a point depend on those options, as with the
`generic` interface: the thermodynamic forces are a tensor for the first
Piola-Kirchhoff stress and a symmetric tensor otherwise, and the tangent
operator is the derivative of a symmetric tensor with respect to a
symmetric tensor for `DS_DEGL`, of a tensor with respect to a tensor for
`DPK1_DF`, and of a symmetric tensor with respect to a tensor otherwise.
Those three kinds of finite strain behaviours (standard finite strain
behaviours and small strain behaviours written in the Hencky or in the
Green-Lagrange strain) are supported, as well as the displacement
gradient given instead of the deformation gradient (stress measure offset
by `10`, see the [`generic` interface
page](generic-behaviours-interface.html#sec:generic_behaviour_interface:displacement_gradient)).
Invalid options of a finite strain behaviour (invalid stress measure or
tangent operator) are reported for the whole batch, as invalid arguments
(status `-5`), whereas the function of the `generic` interface reports an
integration failure (`-1`) at the point.

All the fields and the `statuses` array must be located in the memory
space exported by the library (see the `<name>_generic_parallel_memory_space`
symbol above). The arrays of fields given variable by variable are only
read on the host.

## Output status

~~~~{.cxx}
typedef struct mfront_gpb_OutputStatus {
  int status;
  mfront_gb_size_type number_of_failures;
  mfront_gb_size_type first_failure_index;
  mfront_gb_size_type number_of_unreliable_results;
  mfront_gb_size_type first_unreliable_result_index;
  mfront_gb_real rdt;  // minimum over the batch
  char msg[512];
} mfront_gpb_OutputStatus;
~~~~

The members are the ones of the output status of the material properties
(`mfront_gpmp_OutputStatus`), the time step scaling factor taking the place
of the check retained at the reported point.

The status, also returned by the function, is:

- `1` if the integration succeeded at all points;
- `0` if the integration succeeded at all points but the time step scaling
  factor is lower than `0.99` at some points;
- `-1` if the integration failed at some points (`first_failure_index`
  gives the first one, `statuses` locates all of them);
- `-5` if the arguments are invalid: no output status (returned value
  only) or no batch data, an invalid option of a finite strain behaviour,
  more than \(2^{48}-1\)
  points, more blocks of threads than the grid of the device can hold
  (`CUDA` and `HIP` backends), an execution policy of another backend, no
  execution policy given to the `SYCL` backend, an asynchronous
  computation without statistics or with an out-of-order `SYCL` queue, or
  no statistics, or statistics which do not come from a behaviour, given
  to the report function. Nothing is computed;
- `-6` if the parameters are invalid: a parameters file read at the first
  call (`<name>-parameters.txt`) can't be read. Nothing is computed;
- `-7` in case of a runtime error of the backend (allocation, data
  transfer, launch or execution of a kernel, stack size of the threads of
  the device, exceptions thrown on the host by the runtimes). No exception
  goes through the generated functions.

Those codes are the ones of the material properties. The codes `1`, `0`
and `-1` are the ones of the reported point: the first point where the
integration failed, otherwise the first point where the time step scaling
factor is too low.

An empty batch (no point) is accepted without any check: nothing is read,
written or submitted, the fields may be null, and the status is `1`. The
same rule applies to the material properties, whose status of success is
`0`.

The status follows the conventions of the `generic` interface for
behaviours, where `1` denotes a success. The interface for material
properties follows the conventions of the `generic` interface for material
properties, where `0` denotes a success. Its output status
(`mfront_gpmp_OutputStatus`) also gives the number of points where the
evaluation failed and the first of them.

The message describes invalid arguments and runtime errors. The error
messages of the points (`error_message` of the `generic` interface) are not
reported: the code executed on a device can't throw exceptions, and a
buffer per point would increase the stack of the threads. The index of the
first point where the integration failed is reported, whatever the order
of the computations, and the `statuses` field locates all of them: the
error message of such a point can be obtained by integrating it with the
`generic` interface. If no point failed, `first_failure_index` is the
maximal value of its type. `first_unreliable_result_index` gives the first
point where the time step scaling factor is lower than `0.99`, or the
maximal value of its type if there is no such point.

## Execution policies and statistics

The `execution_policy` member of the batch data (and of the rotation
data) gives the execution policy of the computations. The optional
`statistics` member gives the statistics of the computations (see below).

### Execution policies

The execution policies are `C++` classes of the
`mfront::generic_parallel` namespace, one per backend, each one declared
in the header of the same name in `MFront/GenericParallel`. They derive
from `AbstractBackendExecutionPolicy`, whose pure virtual method
`getIdentifier` gives the identifier of the policy. The type of the
`execution_policy` member, `mfront_gp_AbstractBackendExecutionPolicy`, is
declared in `MFront/GenericParallel/BackendExecutionPolicy.h`: it is an
alias of `mfront::generic_parallel::AbstractBackendExecutionPolicy` in
`C++` and an opaque structure in `C`. A `C` code can thus only give a null
policy, which selects the default policy of the backend.

| Backend   | Execution policy                               | Identifier                                          | Specific member                     |
|:----------|:-----------------------------------------------|:----------------------------------------------------|:------------------------------------|
| `cuda`    | `CUDABackendExecutionPolicy`                   | `cuda`                                              | `stream` (a `cudaStream_t`)         |
| `hip`     | `HIPBackendExecutionPolicy`                    | `hip`                                               | `stream` (a `hipStream_t`)          |
| `kokkos`  | `KokkosBackendExecutionPolicy<ExecutionSpace>` | `kokkos:` followed by `ExecutionSpace::name()`      | `execution_space` (an instance)     |
| `raja`    | `RAJABackendExecutionPolicy<Resource>`         | `raja:host`, `raja:cuda` or `raja:hip`              | `resource` (a resource of camp)     |
| `sycl`    | `SyclBackendExecutionPolicy`                   | `sycl:oneapi` (`icpx`) or `sycl:acpp` (AdaptiveCpp) | `queue` (a `sycl::queue`)           |
| `stlpar`  | `ParallelSTLBackendExecutionPolicy`            | `stlpar`                                            | none                                |
| `openmp`  | `OpenMPBackendExecutionPolicy`                 | `openmp`                                            | none                                |
| `openacc` | `OpenACCBackendExecutionPolicy`                | `openacc`                                           | none                                |
| `arcane`  | `ArcaneBackendExecutionPolicy`                 | `arcane:cuda`, `arcane:hip` or `arcane:host`        | `queue` (an `Arcane::Accelerator::RunQueue`) |

`ExecutionSpace` is the execution space selected by the `execution_space`
option of the `kokkos` backend. `Resource` is the resource of camp
associated with the execution policy of RAJA selected by the
`execution_policy` option of the `raja` backend (see
`mfront::generic_parallel::raja::Resource`). The identifier of the policy
of the `sycl` backend depends on the implementation of `SYCL`
(`SYCL_IMPLEMENTATION_ONEAPI` or `SYCL_IMPLEMENTATION_ACPP` macro). The
identifier of the policy of the `arcane` backend depends on the accelerator
mode of Arccore (`ARCCORE_HAS_CUDA` or `ARCCORE_HAS_HIP` macro), not on the
compiler: a calling code compiled by a `C++` compiler and a library compiled
by a `CUDA` compiler agree on it. Each
library exports the identifier of the policy expected by its functions
(`<name>_generic_parallel_execution_policy` symbol).

All the policies derive from `BackendExecutionPolicyBase`, which derives
from `AbstractBackendExecutionPolicy` and from the common options:

~~~~{.cxx}
struct BackendExecutionCommonPolicy {
  bool preserve_stack_size = false;
  bool asynchronous = false;
};
~~~~

A policy is created by the function of its header:
`makeCUDABackendExecutionPolicy`, `makeHIPBackendExecutionPolicy`,
`makeKokkosBackendExecutionPolicy`, `makeRAJABackendExecutionPolicy`,
`makeSyclBackendExecutionPolicy`, `makeParallelSTLBackendExecutionPolicy`,
`makeOpenMPBackendExecutionPolicy`, `makeOpenACCBackendExecutionPolicy` or
`makeArcaneBackendExecutionPolicy`.
The functions of the `cuda`, `hip`, `kokkos` and `raja` backends take a
structure of options (`CUDABackendExecutionOptions`,
`HIPBackendExecutionOptions`, `KokkosBackendExecutionOptions` and
`RAJABackendExecutionOptions`), whose members are the common options
(`common_options`) and the specific member, which can be given by
designated initializers:

~~~~{.cxx}
#include "MFront/GenericParallel/CUDABackendExecutionPolicy.hxx"
const auto policy = mfront::generic_parallel::makeCUDABackendExecutionPolicy(
    {.common_options = {.asynchronous = true}, .stream = stream});
d.statistics = statistics;
d.execution_policy = &policy;
~~~~

The functions of the `kokkos` and `raja` backends are templates: the
execution space or the resource is deduced from the type of the options,
or given as template argument (for instance
`makeKokkosBackendExecutionPolicy<Kokkos::Cuda>({.execution_space = space})`).
The specific member keeps its default value if it is not given: the
default instance of the execution space, or the default resource of the
`raja` backend (see below). The functions of the `sycl` and `arcane`
backends take the queue, which is required, and the common options. The functions of the
`stlpar`, `openmp` and `openacc` backends only take the common options.

`AbstractBackendExecutionPolicy` is defined by the
`MFrontGenericParallelRuntime` library (`--mfront-generic-parallel-runtime`
option of `tfel-config`), which must be linked by the codes creating
policies. The generated libraries do not need it. `getIdentifier`
is declared before the virtual destructor, so that it has the same place
in the table of virtual functions with the ABI of Visual Studio and with
the Itanium ABI: a policy created by a program built by Visual Studio can
be checked by a library generated by a `TFEL` built with MinGW, and the
reverse.

The generated functions (integration, initialize functions,
post-processings, rotations and standalone models) apply the following
rules:

- a null policy selects the default policy of the backend: the default
  stream of the `cuda` and `hip` backends, the default instance of the
  execution space of the `kokkos` backend, the default resource of the
  `raja` backend (the default stream of the current device with `CUDA`
  and `HIP`, the default resource of camp otherwise), and the default
  common options. The `sycl` and `arcane` backends have no default policy:
  a null policy is refused (status `-5`), as a null queue with the `arcane`
  backend.
- a policy whose identifier is not the one of the backend is refused
  (status `-5`).
- an asynchronous computation (`asynchronous` option) requires
  statistics, for all the functions, including the rotations (status `-5`
  otherwise).
- the generated function copies what it needs from the policy (stream,
  queue, options): the policy does not have to outlive the call, even for
  an asynchronous computation.

### Statistics

By default (`statistics` is null), the function returns once the
computations are completed and reports the statistics of the batch in the
output status.

If `statistics` is not null, the statistics are accumulated in the given
structure, which must be accessible by the device as the fields (and by
the host with the `stlpar`, `openmp` and `openacc` backends, which
accumulate them on the host). The output status then only reports the
errors of the batch (`-5`, `-6` and `-7`), and the report function gives
the result once the computations are completed, whether the computations
are asynchronous or not. The report function reads the statistics on the
host: statistics located in the memory of the device must be copied to the
host before calling it (managed or shared memory avoids this copy, as for
the material properties). With the automatic data transfers of the
`SYCL` backend, statistics which are not accessible by the device are
copied, as the fields:

~~~~{.cxx}
typedef struct mfront_gpb_Statistics {
  unsigned long long number_of_failures;
  unsigned long long first_failure;            // opaque key
  unsigned long long number_of_unreliable_results;
  unsigned long long first_unreliable_result;  // opaque key
  unsigned long long rdt;  // see mfront_gpb_getTimeStepScalingFactor
} mfront_gpb_Statistics;
~~~~

The members are the ones of the statistics of the material properties
(`mfront_gpmp_Statistics`), followed by the minimum of the time step
scaling factors. The keys are opaque: the minimum of the keys gives the
first point, whatever the order of the computations, and only the report
function of the same library decodes them.

If the `asynchronous` option of the policy is false, the function returns
once the computations are completed. If it is true, the function may
return once the computations are submitted to the queue of the policy:
its stream, its instance of the execution space, its resource of camp or
its `sycl::queue` or its queue of Arccore (`CUDA`, `HIP`, `Kokkos`, `RAJA`
and `Arcane` backends, `SYCL` backend if no field is copied). The calling code must then synchronize the queue before
reading the outputs and the statistics. This allows to submit the
integration of several batches, and other computations such as the
assembly of a finite element system, before a single synchronization. The
`stlpar`, `openmp` and `openacc` backends, and the `SYCL` backend if a
field is copied, always wait for the completion of the computations.

The computations are always executed after the computations previously
submitted to the queue, if any, which may compute the inputs. With the `SYCL`
backend, an out-of-order queue gives no order between the kernels:

- asynchronous computations require an in-order queue
  (`sycl::property::queue::in_order`). An asynchronous computation on an
  out-of-order queue is refused (status `-5`).
- a synchronous computation synchronizes an out-of-order queue before the
  kernel, so that the computations already submitted to the queue are
  completed.

The statistics are initialized on the host by
`mfront_gpb_initializeStatistics`, whose second argument must be the
initial value of the time step scaling factor of the batch (the `rdt`
member of the batch data), then copied in device memory if needed. The
minimum of the time step scaling factors is stored as an unsigned
integer, so that the device can update it with an integer atomic
operation: it is decoded by `mfront_gpb_getTimeStepScalingFactor`. Once
the computations are completed, the report function of the library
(`<name>_generic_parallel_report`) fills an output status from the
statistics, as the generated functions do without statistics (status,
numbers of points, indices of the first failure and of the first
unreliable result, time step scaling factor and error message), as the
report functions of the material properties. The report function is only
meaningful if the generated function returned `1`. On all the backends,
the time step scaling factor of the statistics is the minimum of the
value given to `mfront_gpb_initializeStatistics` and of the factors of
the points which are lower than the initial value of the batch. The rotations never fail and never lower the time step
scaling factor: they leave the statistics unchanged.

The devices only write in the statistics when an event occurs at a point
(failure, unreliable result, decrease of the time step scaling factor), by
atomic operations (`CUDA`, `HIP`, `SYCL`, `Kokkos`, `RAJA` and `Arcane`
backends): the
reporting of the statistics then costs nothing when the computations
succeed. The `OpenMP` and `OpenACC` backends and the C++ parallel algorithms
merge the statistics of the points by a parallel reduction, whose result, a
few integers, is copied to the host at each call. Without statistics given
by the calling code, the
`CUDA`, `HIP`, `SYCL`, `Kokkos`, `RAJA` and `Arcane` backends hold the
statistics in a block of memory accessible by the host and by the device
(managed memory, shared USM memory, `Kokkos::SharedSpace`, managed memory of
the resources of camp, unified memory of Arccore), initialized and read by the host: no data is transferred between the
host and the device when no event occurs.
Those blocks are allocated at the first call on a device and reused by the
following calls (see `mfront::generic_parallel::StatusBlockPool`), as the
statistics of the material properties. With `CUDA` and `HIP`, on
devices which do not support concurrent accesses to managed memory by the
host and the device (for instance on Windows), no other kernel may run
during a call without statistics.

The stack size of the threads of a GPU is a property of the context of the
device, shared by all the computations of the process. It is increased if
needed by the `CUDA`, `HIP`, `Kokkos`, `RAJA` and `Arcane` backends, and by
the other
backends if the `device_stack_size` option is given. If the
`preserve_stack_size` option of the execution policy is true, the stack
size is never modified and a runtime error is reported if
it is too small: the calling code is then responsible for the stack size.

## Parameters

The parameters initializers of the behaviours can't be accessed from device
code. The interface adds a constructor to the behaviour class, which reads
the parameters in a structure filled on the host from the parameters
initializers and passed by value to the kernel. The functions changing the
values of the parameters can thus be used as with the `generic` interface.

This structure (`mfront_parameters_values`, declared by the behaviour class)
also holds the values of the parameters of the behaviour variables, read
from their own parameters initializers, recursively: the behaviour gives
them to its behaviour variables, and to the behaviour variables created by
its factories.

## Numerical type

As with the `generic` interface, the `real_type` DSL option selects the
numerical type of the data exchanged with the generated functions:
`double` (the default) or `float` (`--dsl-option=real_type:float`). The
`MFRONT_GB_REAL_TYPE` macro is defined by the generated sources, the size
of the type is exported (`<name>_real_size`) and the version of the
interface (`<name>_generic_parallel_api_version`) is shifted by 1000 for
another type than `double`. The key of the time step scaling factor in
the statistics of a batch is built from its value converted to `double`,
whatever the numerical type. The standalone models (`@DSL Model`) only
support `double`.

## Library also containing the functions of the `generic` interface

With the `generic_functions` option of the interface, the generated
library also contains the functions of the `generic` interface, which
integrate the behaviour at a point (and execute its initialize
functions, its post-processings and its rotations at a point, or execute
a standalone model at a point):

~~~~{.cxx}
interfaces_options: {
  generic-parallel: {
    generic_functions: true
  }
}
~~~~

The library keeps its name (`GenericParallelBehaviour-<backend>`) and
exports `Generic` as interface (`<name>_mfront_interface` symbol): it can
be used as a library of the `generic` interface (by `MTest` or `MGIS` for
instance), its functions of batches of points being detected by the
`<name>_generic_parallel_api_version` symbol. The functions of a point are
the ones of the `generic` interface, declared in the
`MFront/GenericBehaviour/<name>-generic-parallel-<backend>-generic.hxx`
header (the `generic` interface may be used in the same call of `MFront`
for other modelling hypotheses). The library has one
set of parameters and one out of bounds policy, changed by the functions
of the `generic` interface (`<name>_setParameter`,
`<name>_setOutOfBoundsPolicy`, etc.) and used by all its functions. The
behaviour class has the constructors of both interfaces. The
`@GenerateMTestFileOnFailure` keyword makes the functions of a point
generate an `MTest` file when the integration fails, as with the
`generic` interface: the functions of batches of points never generate
such files.

The functions of a point of a behaviour are written in a separate source
file, compiled by the `C++` compiler of the configuration (the compiler of
the backend for the backends based on `C++` programming models, the `C++`
compiler for the `CUDA` and `HIP` backends). The functions of a point of
a standalone model are written in the source of the functions of batches
of points. Their results are the ones of the `generic` interface up to
the rounding differences between compilers. With the compilers which
translate host and device code in a single pass (`nvc++ -stdpar=gpu`,
`nvc++ -mp=gpu`, `nvc++ -acc=gpu`, generic compiler of AdaptiveCpp), the
device code is selected in the whole translation unit (`TFEL_DEVICE_CODE`
macro): the functions of a point then follow the rules of device code, as
the functions of batches of points (for instance, a bound violated with
the strict policy makes the integration fail without the message of the
`generic` interface).

# Standalone models

The interface is also available for standalone models (`@DSL Model`). As
with the `generic` interface for models, a model is treated as a behaviour
without gradients: its outputs are internal state variables, its inputs are
external state variables and its constant material properties are material
properties. For each modelling hypothesis, the interface generates a
function whose name is the one generated by the `generic` interface
followed by `_generic_parallel`, which executes all the functions of the
model over a batch. The library also exports the report function of the
model (`NeutronFluence_generic_parallel_report`):

~~~~{.bash}
$ mfront --obuild --interface=generic --interface=generic-parallel \
         --configuration-file=config-cuda-nvcc.json NeutronFluence.mfront
The following libraries have been built :
- libModel.so :  NeutronFluence_Tridimensional ...
- libGenericParallelModel-cuda.so :  NeutronFluence_Tridimensional_generic_parallel ...
~~~~

~~~~{.cxx}
int NeutronFluence_Tridimensional_generic_parallel(
    mfront_gpb_OutputStatus* const, const mfront_gpb_BatchData* const);
~~~~

The functions are declared in the
`MFront/GenericParallelModel/<name>-generic-parallel-<backend>.hxx` header.
The parameters are handled as for behaviours (`<name>_setParameter`
function).

As with the `generic` interface, the time step scaling factor is set to
`0.1` at the points where the model fails. A model has no prediction
operator: as with the `generic` interface, the model is executed and the
state at the end of the time step is updated whatever the type of
computation. In device code, a bound
which is not satisfied makes the model fail and string parameters are not
supported.

# Backends

The backend is selected in a configuration file:

~~~~{.json}
interfaces_options: {
  generic-parallel: {
    backend: {cuda : {number_of_threads_per_block: 128}}
  }
}
~~~~

The same section is used by the `generic-parallel` interface for material
properties, so that the same configuration files can be used. If no
backend is given, the `stlpar` backend is used with its default options.

## `CUDA` and `HIP` backends

One thread integrates the behaviour at one point. The kernel is launched on
the stream of the execution policy. The summary of the batch is
reduced by warp: the warps where no point failed, gave an unreliable result
or decreased the time step scaling factor do nothing more (vote), the
others use one atomic operation per member of the statistics.

The values of a point are copied in local arrays and the results are
copied back after the integration, whatever the layout of the fields.
Reading and writing the fields directly when they are stored point by point
gave no measurable gain, on GPUs and CPUs, and increased the compilation
time by 25 to 40% with `nvcc`.

The default stack size of `CUDA` threads (1024 bytes) is too small for some
behaviours. The generated function increases it, if needed, before launching
the kernel (see the `preserve_stack_size` option of the execution
policies).

`nvcc` only emits a warning (numbers 20011 and 20014) when device code calls a host
function, and the resulting library gives wrong results or crashes. The
configuration files using `nvcc` (`cuda-nvcc`, and `hip-hipcc` on NVIDIA
GPUs) turn this warning into an error. `clang` always reports an error,
including for the `constexpr` host functions that `nvcc` accepts with the
`--expt-relaxed-constexpr` option.

The configurations using `clang` (`cuda-clang`, and `hip-clang` on NVIDIA
GPUs) use the `CUDA` toolkit given by the `TFEL_CLANG_CUDA_PATH` variable
of `cmake`, by default the one of `nvcc`. A version of `clang` only
supports the versions of `CUDA` released before it.

Options:

- `number_of_threads_per_block` (128 by default, 64 in the configuration
  files delivered with `TFEL`), rounded up to a multiple of the warp size.
  This option has the same meaning for material properties.

The execution policy is a `CUDABackendExecutionPolicy` or a
`HIPBackendExecutionPolicy`, whose `stream` member is a `cudaStream_t` or
a `hipStream_t` (the default stream if null). The default policy uses the
default stream. The fields must be accessible by
the device (device or managed memory).

## Parallel STL backend (`stlpar`)

The behaviour is integrated by `std::transform_reduce` with the given
execution policy. The indices of the points are given by a counting
iterator: with `libstdc++`, iterators of `std::views::iota` are not random
access iterators in the sense of the C++17 iterator categories and the
parallel algorithms run sequentially. With `libstdc++`, the parallel
algorithms use the threads of TBB: the configurations linking TBB mark the
library as never unloaded (`-Wl,-z,nodelete`), since unloading TBB while its
threads are alive crashes the process, for instance when the libraries
loaded by a calling code are closed at the end of the process.

With `nvc++ -stdpar=gpu`, the computations are offloaded to an NVIDIA GPU.
The memory mode shall be given explicitly by `-gpu=mem:managed` (see the
`stlpar-parunseq-nvhpc-gpu` configuration): this mode does not depend on
the support of heterogeneous memory management by the system, and the
`unified` mode, selected by default on such systems by `nvc++` 25.11,
miscompiles some behaviours. The device code of each source file is also
compiled without relocatable device code (`-gpu=nordc`): `nvc++` 25.11
exports some constant data of the device code under names which are only
unique in a source file (`__staticinit_<counter>_<function>`), so that the
device link of several behaviours fails at random. The sources generated
by `MFront` do not call device functions defined in other files.

Options:

- `execution_policy`: `sequenced_policy` (or `seq`), `unsequenced_policy`
  (or `unseq`), `parallel_policy` (or `par`), `parallel_unsequenced_policy`
  (or `par_unseq`, default).
- `device_stack_size`: minimal stack size, in bytes, of the threads of the
  GPU when the computations are offloaded by `nvc++`. The stack required by
  `nvc++` is larger than with `nvcc`: 16384 bytes are used in the
  `stlpar-parunseq-nvhpc-gpu` configuration.

## Kokkos backend (`kokkos`)

The behaviour is integrated by `Kokkos::parallel_for` in the given
execution space, the statistics being updated by atomic operations.
Without statistics given by the calling code, they are held by a block of
`Kokkos::SharedSpace`, as for
the material properties: this memory space is provided by all the backends
of Kokkos except the `OpenACC` and `OpenMPTarget` backends (a static
assertion reports this requirement). Kokkos must be initialized by the
calling code. The execution policy
(`KokkosBackendExecutionPolicy<ExecutionSpace>`, where `ExecutionSpace` is
the execution space of the library) holds an instance of the execution
space (`execution_space` member). The default policy uses the default
instance. The fields must be accessible from this execution space.

The generated libraries are compiled with the compiler and the options of
Kokkos (for instance `nvcc_wrapper`) and are linked with Kokkos, which must
be a shared library, built without relocatable device code, so that the
calling code and the generated libraries share the same instance of Kokkos.
On GPUs, the stack size of the threads is increased if needed, as for the
`CUDA` and `HIP` backends.

The `kokkos` and `kokkos-host` configurations use the compiler, the
compilation flags and the linker flags of the Kokkos installation found by
`cmake` (`TFEL_KOKKOS_CXX_COMPILER`, `TFEL_KOKKOS_CXX_FLAGS` and
`TFEL_KOKKOS_LINKER_FLAGS` substitutions, see the [`TFEL/Config`
page](tfel-config.html)). With `CUDA`, Kokkos uses the shared `CUDA`
runtime (`-cudart shared`): the calling code must use the same runtime.

Options:

- `execution_space`: `Kokkos::DefaultExecutionSpace` by default, for
  instance `Kokkos::DefaultHostExecutionSpace` (`kokkos-host`
  configuration). The execution space is copied in the generated code: it
  must be the name of a type, made of identifiers separated by `::`.

## RAJA backend (`raja`)

The behaviour is integrated by `RAJA::forall` with the given execution
policy, the statistics being updated by the atomic operations of RAJA.
Without statistics given by the calling code, they are held by a block of
managed memory allocated by
the resource of camp associated with the execution policy, one per device,
kept until the end of the process. The execution policy of the backend
(`RAJABackendExecutionPolicy<Resource>`, where `Resource` is the resource
of camp associated with the execution policy of RAJA:
`camp::resources::Cuda`, `camp::resources::Hip` or
`camp::resources::Host`) holds a resource (`resource` member). By default,
and with the default policy, this resource is the default stream of the
current device with `CUDA` and `HIP`, as for the
`CUDA` and `HIP` backends, and the default resource of camp otherwise (the
default resource of camp for `CUDA` and `HIP` is a stream created by camp
on the device 0). The fields must be accessible from the execution policy
of RAJA. The computations can only be asynchronous (`asynchronous` option
of the execution policy of the backend) with an asynchronous execution
policy of RAJA (such as the default one on GPUs). RAJA needs no
initialization.

The generated libraries are compiled by `nvcc` with extended lambdas
(`--extended-lambda`, same host compiler as `TFEL`) if RAJA is built with
`CUDA`, by the `C++` compiler of `TFEL` otherwise, and are linked with the
shared library of RAJA (and with the one of camp if camp is a shared
library: a static camp, the default, is included in the library of RAJA).
RAJA must be a shared library (`+shared` with `spack`), so that the calling
code and the generated libraries share the same instance of RAJA. With
`CUDA`, they use the shared `CUDA` runtime (`-cudart shared`), as the
calling code must. On GPUs, the stack size of the threads is increased if
needed, as for the `CUDA` and `HIP` backends. The `raja` configuration does
not support a RAJA built with `HIP`: the `HIP` policies are handled by the
headers, but not tested.

The `raja` and `raja-host` configurations use the compiler, the
compilation flags and the linker flags deduced from the RAJA installation
found by `cmake` (`TFEL_RAJA_CXX_COMPILER`, `TFEL_RAJA_CXX_FLAGS` and
`TFEL_RAJA_LINKER_FLAGS` substitutions, see the [`TFEL/Config`
page](tfel-config.html)).

Options:

- `execution_policy`: `mfront::generic_parallel::raja::DefaultExecutionPolicy`
  by default, defined in `MFront/GenericParallel/RAJAExecutionPolicy.hxx`:
  `RAJA::cuda_exec_async<128>` in code compiled for `CUDA`,
  `RAJA::hip_exec_async<128>` in code compiled for `HIP`,
  `RAJA::omp_parallel_for_exec` if RAJA is built with OpenMP,
  `RAJA::seq_exec` otherwise. The `raja-host` configuration uses
  `mfront::generic_parallel::raja::DefaultHostExecutionPolicy` (the parallel
  loop of OpenMP if RAJA is built with OpenMP, the sequential loop
  otherwise). The execution policy is copied in the generated code: it must
  be the name of a type, made of qualified identifiers, integers, the
  boolean literals and template arguments (for instance
  `RAJA::cuda_exec<256, true>`). The memory space of the library is
  `device` for the policies of `CUDA` and `HIP`, `host` otherwise. The
  policies of OpenMP target and `SYCL` are refused at compile time: the
  resources of camp associated with them can't allocate the managed memory
  holding the statistics, and the `raja` configuration only compiles for
  `CUDA` and for the host.

## Arcane backend (`arcane`)

The behaviour is integrated by a command of the accelerator API of
Arccore, the core component of the Arcane framework (`RUNCOMMAND_LOOP1`),
on the queue of the execution policy (`ArcaneBackendExecutionPolicy`),
which is required: the backend has no default policy. The execution policy
of the queue (`CUDA`, `HIP`, `Thread` or `Sequential`) is selected at
runtime: a library compiled for `CUDA` integrates the behaviour on the GPU
with a `CUDA` queue, on the threads of the host with a `Thread` queue, and
sequentially with a `Sequential` queue. The `CUDA` (`HIP`) queues require a
library compiled by a `CUDA` (`HIP`) compiler; the other queues are refused
(status `-5`), as a null queue. The fields must be accessible by the device
of the queue: the memory space of the library is `device`, the device being
only known at runtime (unified memory of Arccore, or managed memory, for a
library used with all the queues).

The statistics are updated by native atomic operations (the atomic
operations of Arccore do not support the unsigned 64 bits integers of the
statistics, and its reductions synchronize the queue). Without statistics
given by the calling code, they are held by a block of the unified memory
of Arccore, kept until the end of the process. The commands are launched
asynchronously, whatever the asynchronous state of the queue, which is
restored afterwards (`RunQueue::ScopedAsync`): a synchronous computation
then waits for the completion of the commands of the queue (`barrier`),
whereas an asynchronous one (`asynchronous` option of the execution
policy) returns once they are launched, the commands of the `Thread` and
`Sequential` queues being completed when launched. The queue has a
reference semantics: the policy refers to the queue of the calling code,
which must not be used by another thread during the call. The loops of
Arccore have 32 bits indices, and its kernels compute the index of a thread
on 32 bits: a batch of more than `2^30` points is split in several
commands. The calling code initializes the accelerator
runtime of Arccore (for instance with an `AcceleratorInitializer`) and
creates the queue (`makeQueue`). On GPUs, the stack size of the threads of
the current device of the calling thread, which must be the device of the
queue, is increased if needed, as for the `CUDA` and `HIP` backends.

The generated source (`.cu` file) is compiled by `clang++` as a `CUDA`
compiler (`TFEL_ARCANE_CXX_FLAGS` substitution, see the [`TFEL/Config`
page](tfel-config.html)), and the sources shared with the `generic`
interface by `clang++` as a `C++` compiler. The code of the behaviours is
also executed on the host by the `Thread` and `Sequential` queues: the
device functions of `CUDA` are excluded from the overloads in the
compilation for the host (`-Xarch_host -fgpu-exclude-wrong-side-overloads`),
so that an unqualified call to `max` or `min` in the code of a behaviour is
resolved to the function of the standard library. The libraries are linked with the shared libraries
of Arccore and with the shared `CUDA` runtime, as Arccore
(`TFEL_ARCANE_LINKER_FLAGS` substitution). The `arcane` configuration
requires an Arccore built with `CUDA` (`ARCCORE_ACCELERATOR_MODE=CUDA`) as
shared libraries, found in `Arccore_ROOT`; the `HIP` queues are handled by
the headers, but are not supported by the `arcane` configuration.

This backend has no option.

## SYCL backend (`sycl`)

The behaviour is integrated by a `parallel_for` on the queue of the
execution policy (`SyclBackendExecutionPolicy`), which is required: the
backend has no default policy. The statistics of the
batch are updated by atomic operations (a parallel reduction would require
synchronisation barriers, which are not supported by AdaptiveCpp on CPUs
for large kernels).

Options:

- `data_transfer_policy`: `automatic` (or `auto`, default): the fields
  which are not accessible by the device associated with the queue (host
  memory not allocated by SYCL, if the device is not the host) are copied
  in device memory and the outputs are copied back; `none`: all the fields
  are assumed to be accessible by the device. Any allocation of unified
  shared memory (device, shared or host) is accessible. This option has the
  same meaning as for material properties: both interfaces use the same
  copies (`MFront/GenericParallel/SYCLDeviceCopies.hxx`).
- `device_stack_size`: minimal stack size, in bytes, of the threads of the
  GPU when the computations are performed on an NVIDIA GPU through the CUDA
  runtime (AdaptiveCpp). 8192 bytes are used in the `sycl-default-acpp`
  configuration.

With AdaptiveCpp, the generic compiler (default) translates host and device
code in a single pass: device code is then selected in the whole
translation unit (see the `TFEL_DEVICE_CODE` macro below).

## OpenMP backend (`openmp`)

The points are distributed among the threads of the host (`parallel for`
construct) or offloaded to the default device (`target teams distribute
parallel for` construct). The statistics of the batch are computed by
reductions.

When the computations are offloaded, the fields of the batch must be
accessible from the device. With `nvc++ -mp=gpu`, the memory mode shall be
given explicitly by `-gpu=mem:managed`, as with the `stlpar` backend (see
the `openmp-offload-nvhpc-gpu` configuration). A program compiled by
`nvc++ -mp=gpu -gpu=mem:managed` which loads libraries compiled by other
compilers must be linked with `libnvhpcmanaux` (`-lnvhpcmanaux`), whose
`free` function handles the managed memory: `nvc++` 25.11 links it with
`-stdpar=gpu` but not with `-mp=gpu`. The `openmp-host-gcc`
configuration uses the threads of the host.

Two constructs lead `nvc++ -mp=gpu` to generate wrong device code, and
are therefore avoided in the generated code and in the headers of `TFEL`.
Both defects have been observed with the versions 25.11 and 26.3 of
`nvc++`, and the first one also with the version 26.9:

- a local object holding a reference to a local boolean flag, at `-O2`
  and `-O3`. The function objects given to the tangent operator of the
  implicit DSLs (`getPartialJacobianInvert`) own their status flag.
- an assertion in device code. Its text is registered as a static block
  which is not emitted, so that the library can't be loaded on the
  device.

Options:

- `offload`: if true (default), the computations are offloaded to the
  default device. Otherwise, they are performed by the threads of the host.
- `device_stack_size`: minimal stack size, in bytes, of the threads of the
  GPU when the computations are offloaded to an NVIDIA GPU through the CUDA
  runtime (16384 bytes in the `openmp-offload-nvhpc-gpu` configuration).

## OpenACC backend (`openacc`)

The points are processed by a `parallel loop` construct of OpenACC, on the
device selected by the compiler and by the OpenACC runtime: a GPU with
`nvc++ -acc=gpu` (`openacc-nvhpc-gpu` configuration), the cores of the host
with `nvc++ -acc=multicore` (`openacc-nvhpc-multicore` configuration). The
statistics of the batch are computed by reductions, as with the `OpenMP`
backend, and the computations are synchronous: only the common options of
the execution policy are used.

The memory space of the library is deduced from the compilation options
(`mfront::generic_parallel::getOpenACCMemorySpace`): the one of the
computations offloaded by `nvc++` with `-acc=gpu` (`device`, or `any` with
the unified memory mode), `host` with `-acc=multicore` only, `device` with
the other compilers, whose device is only known at runtime. The
`openacc-nvhpc-gpu` configuration uses the unified memory mode of `nvc++`
(`-acc=gpu -gpu=mem:unified`, which requires the heterogeneous memory
management of the NVIDIA driver or a hardware coherent platform): with the
separate and managed memory modes, `nvc++` 25.11 fails to compile the
headers of `TFEL` for OpenACC (the device code refers to an undefined global
variable created for an empty function object, such as the lambdas given to
the loops over the components of the tensors), whereas `-mp=gpu` compiles
them. As with the `OpenMP` backend, a program compiled by `nvc++ -acc=gpu`
which loads libraries compiled by other compilers must be linked with
`libnvhpcmanaux` (`-lnvhpcmanaux`): `nvc++` allocates the dynamic memory
with its own allocator, and the memory freed by the other libraries must go
through its `free` function.

The OpenACC runtime of `nvc++` uses the CUDA driver without the CUDA
runtime. The stack size of the threads of the GPU is therefore set through
the driver, on the CUDA context of OpenACC
(`MFront/GenericParallel/OpenACCStackSize.hxx`): the `NV_ACC_CUDA_STACKSIZE`
environment variable of `nvc++` only sets it when the device is
initialized.

The minimum reductions of OpenACC on `long long` and `unsigned long long`
integers are wrong on NVIDIA GPUs with `nvc++` 25.11 (they return `1`, at
`-O0` as at `-O2`); the maximum reductions and the minimum reductions on
`unsigned long`, `long`, `unsigned int`, `double` and `float` are right. The
index of the first failed point is reduced as a `size_t`, and the material
properties reduce their indices as `unsigned long` when this type has the
size of `unsigned long long`.

Options:

- `device_stack_size`: minimal stack size, in bytes, of the threads of the
  GPU when the computations are performed by an NVIDIA GPU (16384 bytes in
  the `openacc-nvhpc-gpu` configuration).

# Writing behaviours compatible with GPUs

The code generated by `MFront` is compatible with GPUs. Device specific code
is selected by the `TFEL_DEVICE_CODE` macro, which is defined when device
code is compiled: the behaviour of the other interfaces on CPUs is not
changed. With compilers translating host and device code in a single pass
(`nvc++ -stdpar=gpu`, `nvc++ -mp=gpu` and `nvc++ -acc=gpu`, generic compiler
of AdaptiveCpp), this macro is defined in the whole translation unit: the
host code of the libraries built by those compilers then follows the rules
of device code (no exceptions, eigenvectors of multiple eigenvalues computed
by the Jacobi algorithm, etc.). The results may thus differ from the ones of
the `generic` interface by round-off errors, and the errors reported by
exceptions in the `generic` interface are reported as failures.

Behaviours are not polymorphic: the methods expected from a behaviour are
described by the `tfel::material::MechanicalBehaviourConcept` concept, and
virtual functions are not supported in device code by SYCL. This concept is
checked by the functions integrating a behaviour at one point
(`mfront::gb::integrate`), which are shared by the `generic` and
`generic-parallel` interfaces.

The following rules apply to the code blocks written by the user:

- exceptions are not supported in device code. The `tfel::fail` function
  reports an error in host and device code: on the host, it throws an
  exception of the given type, as before; in device code, it returns
  `false`, which must be returned by the code block:

  ~~~~{.cxx}
  if (q3 > q1) {
    return tfel::fail<std::runtime_error>("q3 is greater than q1");
  }
  ~~~~

  The `raise` and `raise_if` functions can't be used in device code.
- returning `false` from the `@Integrator` code block of the implicit DSLs
  (or from `@Derivative` in the Runge-Kutta DSLs) does not make the
  integration fail: the correction of the Newton algorithm (or the time
  step) is reduced. An exception, on the contrary, makes the integration
  fail. The same result is obtained in device code by calling
  `this->abortResolution()` (implicit DSLs) or `this->abortIntegration()`
  (Runge-Kutta DSLs) before `tfel::fail`:

  ~~~~{.cxx}
  if (omega < 0) {
    this->abortResolution();
    return tfel::fail<std::runtime_error>("negative value of omega");
  }
  ~~~~
- in the `IsotropicMisesCreep`, `IsotropicMisesPlasticFlow` and
  `IsotropicStrainHardeningMisesCreep` DSLs, returning `false` from the
  `@FlowRule` code block only modifies the correction of the Newton
  algorithm: in device code, an error reported by `tfel::fail` in this code
  block makes the integration fail once the maximum number of iterations is
  reached. The flow rules of the `MultipleIsotropicMisesFlows` DSL return
  nothing: an error can't be reported in them in device code.
- the initialize functions and the post-processings return nothing: they
  can't report an error in device code. On the host, the exceptions they
  throw are reported as failures.
- data built on the host at runtime, for instance the slip systems of the
  grains of a polycrystal read from a file, are declared by the
  `@SharedData` keyword:

  ~~~~{.cxx}
  @SharedData PCSlidingSystems gs =
      PCSlidingSystems::getPolyCrystalsSlidingSystems("PolyCrystalsAngles.txt");
  ~~~~

  The expression is evaluated once on the host. The `generic-parallel`
  interface copies the result in a memory accessible by the device at the
  first call of a function of the generated library. This copy is never
  freed, except with the `Kokkos` backend:

  - with the `CUDA` and `HIP` backends, in the memory of the current device,
    one copy per device;
  - with the `SYCL` backend, in the memory of the device of the queue of
    the execution policy, one copy per device and context;
  - with the `Kokkos` backend, in the memory space of the execution space
    (Kokkos uses one device per process). The copy is freed when Kokkos is
    finalized;
  - with the `RAJA` backend, in the memory of the resource of the default
    execution policy (memory of the current device for the policies of
    `CUDA` and `HIP`, one copy per device);
  - with the `Arcane` backend, in the unified memory of Arccore, accessible
    by the host and by the devices whatever the queue, one copy;
  - with the `OpenACC` backend, in the memory of the current device of
    OpenACC (`acc_malloc`), one copy per device;
  - otherwise, on the heap, which must be accessible by the device when the
    computations are offloaded (unified or managed memory, as with the
    `stlpar` backend of `nvc++`).

  A process using several GPUs can thus share the library between them.
  The type of the data must be trivially copyable. Shared data are not
  supported in behaviour variables: the behaviour variables are built by
  their default constructor in device code, which can't build them.
- the standard streams (`std::cout`) can't be used in device code. They
  can be kept on the host:

  ~~~~{.cxx}
  #ifndef TFEL_DEVICE_CODE
  std::cout << "sig: " << sig << '\n';
  #endif /* TFEL_DEVICE_CODE */
  ~~~~
- error messages built at runtime (`std::ostringstream`, `std::to_string`)
  are only available on the host, in the same way.
- function scope static variables must be constant expressions. Constant
  objects built at compile time must be accessed through
  `tfel::utilities::getConstantObject` (`nvcc` does not initialize the
  device copy of a function scope `static constexpr` object whose
  constructor is called).
- the static variables (`@StaticVariable`) read by the code blocks are
  replaced by `MFront` by `TFEL_STATIC_VARIABLE(<class>::<name>)`, which
  gives a temporary copy of the variable in device code, and in the whole
  library with the compilers translating host and device code in a single
  pass (see the [`TFEL/Config` page](tfel-config.html)). The address of
  such a variable can't be taken, and a reference derived from it, for
  instance the result of `std::min(Tref, T)` bound to a `const auto&`, is
  only valid until the end of the full expression.
- functions called by the code blocks must be callable in device code
  (`TFEL_HOST_DEVICE`).

The following points are specific to device code:

- the bounds checks return a failure if a bound is violated and if the out
  of bounds policy is `Strict`. Warnings are not displayed.
- material properties called by the behaviour (`@MaterialLaw`,
  `@ElasticMaterialProperties`, `@ComputeThermalExpansion`, etc.) are
  evaluated by an implementation generated in the `mfront::device`
  namespace, which returns `NaN` if a physical bound is not satisfied.
- the behaviour class is shared by all the interfaces selected in the same
  call of `MFront`. When the `generic-parallel` interface is selected, the
  class is written so that it can be used in device code, with the same
  definition in host and device code: dynamically allocated arrays are not
  used, and the parameters treated as static variables are declared as
  constant members, since static data members can't be used by reference
  in device code. Behaviour variables follow the behaviour which uses them.
- the profiling of the behaviour is disabled.
- the slip systems of single crystals (`@CrystalStructure`,
  `@SlidingSystem`) are built at compile time.
- initialize functions and post-processings are called through function
  objects generated by `MFront`, never through pointers to members, which
  `nvc++` ignores in device code.
- behaviour variables (`@BehaviourVariable`, `@BehaviourVariableFactory`,
  external models declared by `@Model`) can be used in device code, with
  the values of their parameters given on the host, as the ones of the
  behaviour (see the `Parameters` section).
- the parameters of the material properties called by the behaviour are
  constants, in host and device code.
- the linear system solvers of the implicit DSLs can be used in device
  code, including the `TDLS` solver (`@LinearSystemSolver TDLS`) when
  `TFEL` is built with `TDLS` support.

The configurations have been tested with `nvcc` 13.0, `hipcc` 5.7 and 7.2
on top of `nvcc` (NVIDIA platform), `clang` 20 (with `CUDA` 12.9), `g++`
14, `icpx` 2026.1, `nvc++` 25.11 (also for OpenACC), Kokkos 5.0 and 5.2,
RAJA 2026.07, AdaptiveCpp 25.10 and Arccore 2.8 (Arcane 4.1.16, with
`clang` 20 and `CUDA` 12.9).
Some compiler defects found during these tests are
worked around in the generated code and the headers (see the comments of
the headers of `MFront/GenericParallelBehaviour` and
`MFront/GenericParallel`, of `TFEL/Utilities/ConstantObject.hxx`, and of
the backends of the material properties).

# Current limitations

- the comparison of the jacobian to a numerical jacobian
  (`@CompareToNumericalJacobian`) prints its results on the standard
  output: it is only performed on the host, and never with the compilers
  translating host and device code in a single pass (see the
  `TFEL_DEVICE_CODE` macro above).
- the `HIP` backend has not been tested on AMD GPUs.
- the SYCL backend has been tested with AdaptiveCpp (CPU and NVIDIA GPU)
  and with Intel's `icpx` (CPU).

# Tests

The tests are installed in
`share/tfel/test-suite/behaviours/generic-parallel`. For each configuration,
the `build-libraries.sh` script builds the test behaviours twice: with the
`generic` interface and the default compiler of `MFront` (reference), and
with the `generic` and `generic-parallel` interfaces and the tested
configuration (which checks that both interfaces can be used together). The
reference then does not depend on the tested compiler. The
`MFRONT_GPB_REFERENCE_CONFIGURATION_FILE` environment variable may give the
configuration file used to build the reference library. The results of the
batch integration are compared to the results of the reference on two time
steps of a random loading, the second one being computed asynchronously,
for three layouts of the fields (point by point, component by component,
and component by component with the material properties and the external
state variables given variable by variable) and three types of computation, including
the energies, the speed of sound and the statuses of batches where the
integration fails at some points. The asynchronous step is analysed by
the report function of the library, which is also tested on statistics
where nothing happened and on null statistics (status `-5`). A policy of
another backend and an asynchronous computation without statistics are
checked to be refused (status `-5`), for the integration and for the
rotations, and a synchronous integration with statistics is compared to
the reference, its result being given by the report function. An invalid
parameters file, of a behaviour and of a behaviour variable, is reported
as invalid parameters (status `-6`). The initialize functions, the
post-processings, the rotation functions and the standalone models are
compared on random states. The `check-generic-functions.sh` script builds
libraries of a few test behaviours and models with the `generic_functions`
option and compares their functions of a point to their functions of
batches of points, the latter being compared to the reference, with
parameters and an out of bounds policy changed in the library.
The list of the comparisons, shared by all the configurations, is given by
the `compare-all.sh` script; `compare.cxx` documents its options. The sizes
of the variables are read in the symbols of the reference library. The
behaviours using the `TDLS` linear system solver are tested in the `tdls`
subdirectory of each configuration (`compare-tdls.sh` script) if `TFEL` is
built with `TDLS` support. The definitions shared by `compare-all.sh` and
`compare-tdls.sh` are given by the `compare-functions.sh` script.

The tests of a configuration are in the directory of the same name. Some
directories test the other configuration files of a configuration: the
`kokkos-host` directory tests the `kokkos` configuration with the
`config-kokkos-host.json` file, the `raja-host` directory tests the `raja`
configuration with the `config-raja-host.json` file, the `arcane` directory
tests the library of the `arcane` configuration with a `CUDA` queue, a
`Thread` queue and a `Sequential` queue (`MFRONT_GPB_COMPARE_ARCANE_QUEUE`
environment variable of `compare.cxx`), the
`sycl-default-acpp-2` directory tests the `sycl-default-acpp` configuration
with the `config-sycl-default-acpp-2.json` file (no data transfer), and the
`sycl-default-acpp-omp` directory also tests the `sycl-default-acpp`
configuration, with the computations performed on the CPU by the OpenMP
backend of AdaptiveCpp (`ACPP_VISIBILITY_MASK=omp`). The `raja-options`
directory checks that the `execution_policy` option of the `raja` backend
accepts the valid execution policies and refuses the invalid ones, the
policy being copied in the generated code
(`check-execution-policies.sh` script, generation of the sources only).
