The `generic-parallel` interface integrates a behaviour, or executes a
standalone model, over a batch of integration points, on GPUs or on CPUs,
with one of the following backends: `CUDA`, `HIP`, parallel algorithms of
the C++ standard library, Kokkos, SYCL and OpenMP. It follows the design of
the
[`generic-parallel` interface for material
properties](generic-parallel-material-property-interface.html): backends
selected by an option, configuration files, libraries suffixed by the name
of the backend. The options shared by the backends of both interfaces have
the same meaning.

The implementation differs. The code of a material property is a function
of its arguments: the backends of the interface for material properties
write a loop over the points in the generated code. The integration of a
behaviour involves many more steps (gathering the data of a point, choice
of the tangent operator, finite strain kinematics, statistics of the
batch): the backends of the interface for behaviours call function
templates, defined in the `MFront/GenericParallelBehaviour` headers, which
only differ by the primitive applying a function at each point.

Integrating a batch is equivalent to calling the function generated by the
[`generic` interface](generic-behaviours-interface.html) at each
integration point, with the same time increment and the same computation
options. The two interfaces can be used together:

~~~~{.bash}
$ mfront --obuild --interface=generic --interface=generic-parallel \
         --configuration-file=config-cuda-nvcc.json Plasticity.mfront
The following libraries have been built :
- libBehaviour.so :  Plasticity_Tridimensional ...
- libGenericParallelBehaviour-cuda.so :  Plasticity_Tridimensional ...
~~~~

# Generated functions

For each modelling hypothesis, the interface generates a function with the
same name as the one generated by the `generic` interface:

~~~~{.cxx}
int Plasticity_Tridimensional(mfront_gpb_OutputStatus* const,
                              const mfront_gpb_BatchData* const);
~~~~

The initialize functions and the post-processings are also executed over
a batch:

~~~~{.cxx}
int Plasticity_Tridimensional_InitializeFunction_ElasticStrainFromInitialStress(
    mfront_gpb_OutputStatus* const,
    const mfront_gpb_BatchData* const,
    const mfront_gpb_ConstField* const inputs);
int Plasticity_Tridimensional_PostProcessing_PrincipalStrain(
    mfront_gpb_OutputStatus* const,
    const mfront_gpb_Field* const outputs,
    const mfront_gpb_BatchData* const);
~~~~

As with the `generic` interface:

- an initialize function is executed on the state at the beginning of the
  time step and writes the thermodynamic forces and the internal state
  variables of the state at the end of the time step. Its inputs may be null
  if the initialize function has no input.
- a post-processing is executed on the state at the end of the time step.

The output status and the `statuses` field have the same meaning as for
the integration. In particular, the status is `1` on success, whereas the
functions of the `generic` interface return `0` on success.

For orthotropic behaviours, the rotation functions of the `generic`
interface are generated for batches (`rotateGradients`,
`rotateThermodynamicForces`, `rotateTangentOperatorBlocks`, and for finite
strain behaviours the variants associated with the stress measures and the
tangent operators, such as `rotateThermodynamicForces_PK1Stress`):

~~~~{.cxx}
int OrthotropicElastic_Tridimensional_rotateGradients(
    mfront_gpb_OutputStatus* const, const mfront_gpb_RotationData* const);
~~~~

~~~~{.cxx}
typedef struct {
  mfront_gb_size_type number_of_points;
  mfront_gpb_Field destination;
  mfront_gpb_ConstField source;             // may be the destination
  mfront_gpb_ConstField rotation_matrices;  // 9 values per point
  mfront_gpb_ExecutionOptions execution;    // see below
} mfront_gpb_RotationData;
~~~~

The rotation matrix is uniform if the point stride of the
`rotation_matrices` field is null. The rotation matrices have the meaning
and the storage of the `generic` interface (rotation from the global frame
to the material frame, stored in column-major format).

All the tangent operator blocks can be rotated, with both interfaces. A
block associated with arrays of variables is rotated entry by entry. A
block for which TFEL has no type which can be rotated (derivative of a
vector with respect to a symmetric tensor or a tensor, and conversely,
derivative of a tensor with respect to a symmetric tensor) is rotated by
`mfront::gb::rotateTangentOperatorBlock`, which computes
\(Q_{1}\,K\,Q_{2}^{T}\), where \(Q_{i}\) is the matrix of the rotation of the
objects of each variable by `change_basis`.

The library also exports the same symbols as the `generic` interface
(names and types of the variables, parameters, etc.) and the functions
changing the parameters and the out of bounds policy. The `mfront_interface`
symbol is equal to `GenericParallel`, for the behaviours and for the
standalone models. The `<name>_generic_parallel_backend` symbol gives the
backend of the library (`cuda`, `hip`, `stlpar`, `kokkos`, `sycl` or
`openmp`). The `<name>_generic_parallel_memory_space` symbol (a `const
char*`) tells the calling code where the fields must be located:

- `host`: the computations are performed on the host, the fields must be
  accessible by the host;
- `device`: the computations are performed on a device which can't access
  the ordinary memory of the host, the fields must be accessible by the
  device (memory of the device, managed or shared memory);
- `any`: the fields may be located anywhere (SYCL backend with automatic
  transfers, `nvc++` with the unified memory mode).

This memory space is set when the library is compiled, since the target of
some programming models is selected by the compiler (C++ parallel
algorithms and OpenMP with `nvc++`) or by the configuration of a library
(execution space of Kokkos). See `MFront/GenericParallel/MemorySpace.hxx`.

The data structures are declared in
`MFront/GenericParallelBehaviour/BatchData.h`. Their version is given by the
`MFRONT_GPB_API_VERSION` macro, incremented at each incompatible change, and
exported by the libraries (`<name>_generic_parallel_api_version` symbol,
an `unsigned short`), so that the calling code can check that it uses the same
structures.

## Fields

The values of a group of variables (gradients, internal state variables,
etc.) at all the integration points are described by a field:

~~~~{.cxx}
typedef struct {
  const mfront_gb_real* values;
  mfront_gb_size_type point_stride;
  mfront_gb_size_type component_stride;
} mfront_gpb_ConstField;
~~~~

The `j`-th component at the `i`-th point is stored at
`values[i * point_stride + j * component_stride]`. Usual layouts are:

- point by point: `point_stride` is the size of the group and
  `component_stride` is equal to one. This is the layout of `MGIS`.
- component by component: `point_stride` is equal to one and
  `component_stride` is the number of points. On GPUs, this layout gives
  coalesced memory accesses.
- uniform values (inputs only): `point_stride` is null.

`mfront_gpb_Field` is the mutable version of `mfront_gpb_ConstField`. The
group of variables of a point are the ones of the `generic` interface: for
instance, the temperature is the first external state variable.

### Material properties and external state variables given variable by variable

The material properties and the external state variables can also be given
variable by variable, with one field per variable. This allows a different
layout for each variable, for instance uniform values for some material
properties only, as in `MGIS`:

~~~~{.cxx}
mfront_gpb_ConstField mps[2];
mps[0] = {&young_modulus, 0, 1};       // uniform value
mps[1] = {poisson_ratios, 1, 1};       // one value per point
d.s0.material_properties_by_variable = mps;
d.s1.material_properties_by_variable = mps;
~~~~

The variables follow the order of the material properties (or of the
external state variables) of a point, the elements of an array being
distinct variables. The components of a variable are given by the
`component_stride` of its field. If `material_properties_by_variable` (or
`external_state_variables_by_variable`) is null, the group field
`material_properties` (or `external_state_variables`) is used.

The arrays of fields are only read on the host: only the values must be
accessible by the device. Both forms are converted on the host in the same
description, so that the code executed at each point does not depend on
the form. The material properties and the external state variables of a
point are always copied in local arrays.

## Batch data

~~~~{.cxx}
typedef struct {
  mfront_gb_size_type number_of_points;
  mfront_gb_real dt;
  mfront_gb_real options[3];   // the three first values of K
  mfront_gb_real rdt;          // initial time step scaling factor
  mfront_gpb_Field tangent_operators;
  mfront_gpb_Field rdts;       // optional
  mfront_gpb_Field speed_of_sound;
  int* statuses;               // optional
  mfront_gpb_InitialState s0;
  mfront_gpb_State s1;
  mfront_gpb_ExecutionOptions execution;  // see below
} mfront_gpb_BatchData;
~~~~

`options` has the meaning of the three first values of the array `K` of the
`generic` interface (type of computation, stress measure and tangent
operator for finite strain behaviours). The tangent or prediction operators
are written in `tangent_operators`, which is not used if no tangent
operator is requested.

For finite strain behaviours, the sizes of the thermodynamic forces and of
the tangent operator of a point depend on those options, as with the
`generic` interface: the thermodynamic forces are a tensor for the first
Piola-Kirchhoff stress and a symmetric tensor otherwise, and the tangent
operator is the derivative of a symmetric tensor with respect to a
symmetric tensor for `DS_DEGL`, of a tensor with respect to a tensor for
`DPK1_DF`, and of a symmetric tensor with respect to a tensor otherwise.
Those three kinds of finite strain behaviours (standard finite strain
behaviours and small strain behaviours written in the Hencky or in the
Green-Lagrange strain) are supported.

All the pointers must be accessible by the device on which the computations
are performed.

## Output status

~~~~{.cxx}
typedef struct {
  int status;
  mfront_gb_size_type number_of_failures;
  mfront_gb_size_type first_failure_index;
  mfront_gb_size_type number_of_unreliable_results;
  mfront_gb_real rdt;  // minimum over the batch
  char msg[512];
} mfront_gpb_OutputStatus;
~~~~

The status, also returned by the function, is:

- `1` if the integration succeeded at all points;
- `0` if the integration succeeded at all points but the time step scaling
  factor is lower than `0.99` at some points;
- `-1` if the integration failed at some points (`first_failure_index`
  gives the first one, `statuses` locates all of them);
- `-2` if the arguments are invalid (nothing is computed);
- `-3` in case of a runtime error of the backend (allocation, launch of a
  kernel, etc.).

The status follows the conventions of the `generic` interface for
behaviours, where `1` denotes a success. The interface for material
properties follows the conventions of the `generic` interface for material
properties (`mfront_gmp_OutputStatus`), where `0` denotes a success.

The message describes invalid arguments and runtime errors. The error
messages of the points (`error_message` of the `generic` interface) are not
reported: the code executed on a device can't throw exceptions, and a
buffer per point would increase the stack of the threads. The index of the
first point where the integration failed is reported, whatever the order
of the computations, and the `statuses` field locates all of them: the
error message of such a point can be obtained by integrating it with the
`generic` interface. If no point failed, `first_failure_index` is the
maximal value of its type.

## Execution options

~~~~{.cxx}
typedef struct {
  void* queue;
  mfront_gpb_BatchStatistics* statistics;  // optional
  int preserve_stack_size;
} mfront_gpb_ExecutionOptions;
~~~~

The meaning of `queue` depends on the backend (see the section of each
backend).

By default (`statistics` is null), the computations are synchronous: the
function returns once they are completed and reports the statistics of the
batch in the output status.

If `statistics` is not null, the statistics are accumulated in the given
structure, which must be accessible by the device as the fields:

~~~~{.cxx}
typedef struct {
  unsigned long long number_of_failures;
  unsigned long long first_failure_index;
  unsigned long long number_of_unreliable_results;
  unsigned long long rdt;  // see mfront_gpb_getTimeStepScalingFactor
} mfront_gpb_BatchStatistics;
~~~~

The computations may then be asynchronous: the function returns once they
are submitted to the queue (`CUDA`, `HIP` and `Kokkos` backends, `SYCL`
backend if no field is copied). The calling code must synchronize the queue
before reading the outputs and the statistics. With the `SYCL` backend,
asynchronous computations require an in-order queue
(`sycl::property::queue::in_order`): an out-of-order queue gives no order
between the kernels. With an out-of-order queue, the computations are
synchronous and the queue is synchronized before the kernel. The output status only
reports invalid arguments and runtime errors. This allows to submit the
integration of several batches, and other computations such as the
assembly of a finite element system, before a single synchronization. The
other backends wait for the completion of the computations and accumulate
the statistics on the host.

The statistics are initialized on the host by
`mfront_gpb_initializeBatchStatistics`, then copied in device memory if
needed. The minimum of the time step scaling factors is stored as an
unsigned integer, so that the device can update it with an integer atomic
operation: it is decoded by `mfront_gpb_getTimeStepScalingFactor`, and
`mfront_gpb_getStatus` gives the status associated with the statistics
(`1`, `0` or `-1`). The rotations never fail and leave the statistics
unchanged.

The reporting of the statistics costs nothing when the computations
succeed: the devices only write in the statistics when an event occurs at
a point (failure, unreliable result, decrease of the time step scaling
factor), by atomic operations (`CUDA`, `HIP`, `SYCL`, `Kokkos` in
asynchronous mode) or by parallel reductions (`Kokkos` in synchronous
mode, `OpenMP`, C++ parallel algorithms). In synchronous mode, the
`CUDA`, `HIP` and `SYCL` backends hold the statistics in a block of memory
accessible by the host and by the device (managed memory, shared USM
memory), initialized and read by the host: no data is transferred between
the host and the device when no event occurs. Those blocks are allocated at
the first call on a device and reused by the following calls (see
`mfront::generic_parallel::StatusBlockPool`), as the statuses of the
bounds checks of the material properties. With `CUDA` and `HIP`, on
devices which do not support concurrent accesses to managed memory by the
host and the device (for instance on Windows), no other kernel may run
during a synchronous call.

The stack size of the threads of a GPU is a property of the context of the
device, shared by all the computations of the process. It is increased if
needed by the `CUDA`, `HIP` and `Kokkos` backends, and by the other backends
if the `device_stack_size` option is given. If `preserve_stack_size` is not
null, the stack size is never modified and a runtime error is reported if
it is too small: the calling code is then responsible for the stack size.

## Parameters

The parameters initializers of the behaviours can't be accessed from device
code. The interface adds a constructor to the behaviour class, which reads
the parameters in a structure filled on the host from the parameters
initializers and passed by value to the kernel. The functions changing the
values of the parameters can thus be used as with the `generic` interface.

This structure (`mfront_parameters_values`, declared by the behaviour class)
also holds the values of the parameters of the behaviour variables, read
from their own parameters initializers, recursively: the behaviour gives
them to its behaviour variables, and to the behaviour variables created by
its factories.

# Standalone models

The interface is also available for standalone models (`@DSL Model`). As
with the `generic` interface for models, a model is treated as a behaviour
without gradients: its outputs are internal state variables, its inputs are
external state variables and its constant material properties are material
properties. For each modelling hypothesis, the interface generates a
function with the same name as the one generated by the `generic` interface,
which executes all the functions of the model over a batch:

~~~~{.bash}
$ mfront --obuild --interface=generic --interface=generic-parallel \
         --configuration-file=config-cuda-nvcc.json NeutronFluence.mfront
The following libraries have been built :
- libModel.so :  NeutronFluence_Tridimensional ...
- libGenericParallelModel-cuda.so :  NeutronFluence_Tridimensional ...
~~~~

~~~~{.cxx}
int NeutronFluence_Tridimensional(mfront_gpb_OutputStatus* const,
                                  const mfront_gpb_BatchData* const);
~~~~

The functions are declared in the
`MFront/GenericParallelModel/<name>-generic-parallel-<backend>.hxx` header.
The parameters are handled as for behaviours (`<name>_setParameter`
function).

As with the `generic` interface, the time step scaling factor is set to
`0.1` at the points where the model fails. A model has no prediction
operator: if a prediction is requested, the model is not executed and the
state at the end of the time step is not updated. In device code, a bound
which is not satisfied makes the model fail and string parameters are not
supported.

# Backends

The backend is selected in a configuration file:

~~~~{.json}
interfaces_options: {
  generic-parallel: {
    backend: {cuda : {number_of_threads_per_block: 128}}
  }
}
~~~~

The same section is used by the `generic-parallel` interface for material
properties, so that the same configuration files can be used.

## `CUDA` and `HIP` backends

One thread integrates the behaviour at one point. The kernel is launched on
the queue given by the execution options. The summary of the batch is
reduced by warp: the warps where no point failed, gave an unreliable result
or decreased the time step scaling factor do nothing more (vote), the
others use one atomic operation per member of the statistics.

The values of a point are copied in local arrays and the results are
copied back after the integration, whatever the layout of the fields.
Reading and writing the fields directly when they are stored point by point
gave no measurable gain, on GPUs and CPUs, and increased the compilation
time by 25 to 40% with `nvcc`.

The default stack size of `CUDA` threads (1024 bytes) is too small for some
behaviours. The generated function increases it, if needed, before launching
the kernel (see the `preserve_stack_size` execution option).

`nvcc` only emits a warning (numbers 20011 and 20014) when device code calls a host
function, and the resulting library gives wrong results or crashes. The
configuration files using `nvcc` (`cuda-nvcc`, and `hip-hipcc` on NVIDIA
GPUs) turn this warning into an error. `clang` always reports an error,
including for the `constexpr` host functions that `nvcc` accepts with the
`--expt-relaxed-constexpr` option.

The configurations using `clang` (`cuda-clang`, and `hip-clang` on NVIDIA
GPUs) use the `CUDA` toolkit given by the `TFEL_CLANG_CUDA_PATH` variable
of `cmake`, by default the one of `nvcc`. A version of `clang` only
supports the versions of `CUDA` released before it.

Options:

- `number_of_threads_per_block` (128 by default), rounded up to a multiple
  of the warp size.

The queue is a `cudaStream_t` or a `hipStream_t` (the default stream if
null). The fields must be accessible by
the device (device or managed memory).

## Parallel STL backend (`stlpar`)

The behaviour is integrated by `std::transform_reduce` with the given
execution policy. The indices of the points are given by a counting
iterator: with `libstdc++`, iterators of `std::views::iota` are not random
access iterators in the sense of the C++17 iterator categories and the
parallel algorithms run sequentially. With `libstdc++`, the parallel
algorithms use the threads of TBB: the configurations linking TBB mark the
library as never unloaded (`-Wl,-z,nodelete`), since unloading TBB while its
threads are alive crashes the process, for instance when the libraries
loaded by a calling code are closed at the end of the process.

With `nvc++ -stdpar=gpu`, the computations are offloaded to an NVIDIA GPU.
The memory mode shall be given explicitly by `-gpu=mem:managed` (see the
`stlpar-parunseq-nvhpc-gpu` configuration): this mode does not depend on
the support of heterogeneous memory management by the system, and the
`unified` mode, selected by default on such systems by `nvc++` 25.11,
miscompiles some behaviours. The device code of each source file is also
compiled without relocatable device code (`-gpu=nordc`): `nvc++` 25.11
exports some constant data of the device code under names which are only
unique in a source file (`__staticinit_<counter>_<function>`), so that the
device link of several behaviours fails at random. The sources generated
by `MFront` do not call device functions defined in other files.

Options:

- `execution_policy`: `sequenced_policy` (or `seq`), `unsequenced_policy`
  (or `unseq`), `parallel_policy` (or `par`), `parallel_unsequenced_policy`
  (or `par_unseq`, default).
- `device_stack_size`: minimal stack size, in bytes, of the threads of the
  GPU when the computations are offloaded by `nvc++`. The stack required by
  `nvc++` is larger than with `nvcc`: 16384 bytes are used in the
  `stlpar-parunseq-nvhpc-gpu` configuration.

## Kokkos backend (`kokkos`)

The behaviour is integrated by `Kokkos::parallel_reduce` in the given
execution space, or by `Kokkos::parallel_for` with atomic operations if the
execution options give statistics. Kokkos must be initialized by the calling
code. The queue may point to an instance of the execution space. The fields
must be accessible from this execution space.

The generated libraries are compiled with the compiler and the options of
Kokkos (for instance `nvcc_wrapper`) and are linked with Kokkos, which must
be a shared library, built without relocatable device code, so that the
calling code and the generated libraries share the same instance of Kokkos.
On GPUs, the stack size of the threads is increased if needed, as for the
`CUDA` and `HIP` backends.

Options:

- `execution_space`: `Kokkos::DefaultExecutionSpace` by default, for
  instance `Kokkos::DefaultHostExecutionSpace`.

## SYCL backend (`sycl`)

The behaviour is integrated by a `parallel_for` on the queue given by the
execution options, which must point to a `sycl::queue`. The statistics of the
batch are updated by atomic operations (a parallel reduction would require
synchronisation barriers, which are not supported by AdaptiveCpp on CPUs
for large kernels).

Options:

- `data_transfer_policy`: `automatic` (or `auto`, default): the fields
  which are not accessible by the device associated with the queue (host
  memory not allocated by SYCL) are copied in device memory and the outputs
  are copied back; `none`: all the fields are assumed to be accessible by
  the device. This option has the same meaning as for material properties.
- `device_stack_size`: minimal stack size, in bytes, of the threads of the
  GPU when the computations are performed on an NVIDIA GPU through the CUDA
  runtime (AdaptiveCpp).

With AdaptiveCpp, the generic compiler (default) translates host and device
code in a single pass: device code is then selected in the whole
translation unit (see the `TFEL_DEVICE_CODE` macro below).

## OpenMP backend (`openmp`)

The points are distributed among the threads of the host (`parallel for`
construct) or offloaded to the default device (`target teams distribute
parallel for` construct). The statistics of the batch are computed by
reductions.

When the computations are offloaded, the fields of the batch must be
accessible from the device. With `nvc++ -mp=gpu`, the memory mode shall be
given explicitly by `-gpu=mem:managed`, as with the `stlpar` backend (see
the `openmp-offload-nvhpc-gpu` configuration). A program compiled by
`nvc++ -mp=gpu -gpu=mem:managed` which loads libraries compiled by other
compilers must be linked with `libnvhpcmanaux` (`-lnvhpcmanaux`), whose
`free` function handles the managed memory: `nvc++` 25.11 links it with
`-stdpar=gpu` but not with `-mp=gpu`. The `openmp-host-gcc`
configuration uses the threads of the host.

Two constructs lead `nvc++ -mp=gpu` (25.11 to 26.9) to generate wrong
device code at `-O2` and `-O3`, and are therefore avoided in the generated
code and in the headers of `TFEL`:

- a local object holding a reference to a local boolean flag. The function
  objects given to the tangent operator of the implicit DSLs
  (`getPartialJacobianInvert`) own their status flag.
- an assertion in device code. Its text is registered as a static block
  which is not emitted, so that the library can't be loaded on the
  device.

Options:

- `offload`: if true (default), the computations are offloaded to the
  default device. Otherwise, they are performed by the threads of the host.
- `device_stack_size`: minimal stack size, in bytes, of the threads of the
  GPU when the computations are offloaded to an NVIDIA GPU through the CUDA
  runtime.

# Writing behaviours compatible with GPUs

The code generated by `MFront` is compatible with GPUs. Device specific
code is selected by the `TFEL_DEVICE_CODE` macro, which is defined when
device code is compiled: the behaviour of the other interfaces on CPUs is
not changed. With compilers translating host and device code in a single
pass (`nvc++ -stdpar=gpu` and `nvc++ -mp=gpu`, generic compiler of
AdaptiveCpp), this macro is defined in the whole translation unit: the
host code of the libraries built by those compilers then follows the rules
of device code (no exceptions, eigenvectors of multiple eigenvalues computed
by the Jacobi algorithm, etc.). The results may thus differ from the ones of
the `generic` interface by round-off errors, and the errors reported by
exceptions in the `generic` interface are reported as failures.

Behaviours are not polymorphic: the methods expected from a behaviour are
described by the `tfel::material::MechanicalBehaviourConcept` concept, and
virtual functions are not supported in device code by SYCL.

The following rules apply to the code blocks written by the user:

- exceptions are not supported in device code. The `tfel::fail` function
  reports an error in host and device code: on the host, it throws an
  exception of the given type, as before; in device code, it returns
  `false`, which must be returned by the code block:

  ~~~~{.cxx}
  if (q3 > q1) {
    return tfel::fail<std::runtime_error>("q3 is greater than q1");
  }
  ~~~~

  The `raise` and `raise_if` functions can't be used in device code.
- returning `false` from the `@Integrator` code block of the implicit DSLs
  (or from `@Derivative` in the Runge-Kutta DSLs) does not make the
  integration fail: the correction of the Newton algorithm (or the time
  step) is reduced. An exception, on the contrary, makes the integration
  fail. The same result is obtained in device code by calling
  `this->abortResolution()` (implicit DSLs) or `this->abortIntegration()`
  (Runge-Kutta DSLs) before `tfel::fail`:

  ~~~~{.cxx}
  if (omega < 0) {
    this->abortResolution();
    return tfel::fail<std::runtime_error>("negative value of omega");
  }
  ~~~~
- data built on the host at runtime, for instance the slip systems of the
  grains of a polycrystal read from a file, are declared by the
  `@SharedData` keyword:

  ~~~~{.cxx}
  @SharedData PCSlidingSystems gs =
      PCSlidingSystems::getPolyCrystalsSlidingSystems("PolyCrystalsAngles.txt");
  ~~~~

  The expression is evaluated once on the host. The `generic-parallel`
  interface copies the result in a memory accessible by the device at the
  first call of a function of the generated library, and never frees it:

  - with the `CUDA` and `HIP` backends, in the memory of the current device,
    one copy per device;
  - with the `SYCL` backend, in the memory of the device of the queue, one
    copy per device and context;
  - with the `Kokkos` backend, in the memory space of the execution space
    (Kokkos uses one device per process);
  - otherwise, on the heap, which must be accessible by the device when the
    computations are offloaded (unified or managed memory, as with the
    `stlpar` backend of `nvc++`).

  A process using several GPUs can thus share the library between them.
  The type of the data must be trivially copyable.
- the standard streams (`std::cout`) can't be used in device code. They
  can be kept on the host:

  ~~~~{.cxx}
  #ifndef TFEL_DEVICE_CODE
  std::cout << "sig: " << sig << '\n';
  #endif /* TFEL_DEVICE_CODE */
  ~~~~
- error messages built at runtime (`std::ostringstream`, `std::to_string`)
  are only available on the host, in the same way.
- function scope static variables must be constant expressions. Constant
  objects built at compile time must be accessed through
  `tfel::utilities::getConstantObject` (`nvcc` does not initialize the
  device copy of a function scope `static constexpr` object whose
  constructor is called).
- functions called by the code blocks must be callable in device code
  (`TFEL_HOST_DEVICE`).

The following points are specific to device code:

- the bounds checks return a failure if a bound is violated and if the out
  of bounds policy is `Strict`. Warnings are not displayed.
- material properties called by the behaviour (`@MaterialLaw`,
  `@ElasticMaterialProperties`, `@ComputeThermalExpansion`, etc.) are
  evaluated by an implementation generated in the `mfront::device`
  namespace, which returns `NaN` if a physical bound is not satisfied.
- the behaviour class is shared by all the interfaces selected in the same
  call of `MFront`. When the `generic-parallel` interface is selected, the
  class is written so that it can be used in device code, with the same
  definition in host and device code: dynamically allocated arrays are not
  used, and the parameters treated as static variables are declared as
  constant members, since static data members can't be used by reference
  in device code. Behaviour variables follow the behaviour which uses them.
- the profiling of the behaviour is disabled.
- the slip systems of single crystals (`@CrystalStructure`,
  `@SlidingSystem`) are built at compile time.
- initialize functions and post-processings are called through function
  objects generated by `MFront`, never through pointers to members, which
  `nvc++` ignores in device code.
- behaviour variables (`@BehaviourVariable`, `@BehaviourVariableFactory`,
  external models declared by `@Model`) can be used in device code, with
  the values of their parameters given on the host, as the ones of the
  behaviour (see the `Parameters` section).
- the parameters of the material properties called by the behaviour are
  constants, in host and device code.
- the linear system solvers of the implicit DSLs can be used in device
  code, including the `TDLS` solver (`@LinearSystemSolver TDLS`) when
  `TFEL` is built with `TDLS` support.

The configurations have been tested with `nvcc` 13.0, `hipcc` 5.7 on top of
`nvcc` (NVIDIA platform), `g++` 14, `nvc++` 25.11, Kokkos 5.0.2 and
AdaptiveCpp 25.10. Some compiler defects found during these tests are
worked around in the generated code and the headers (see the comments of
`MFront/GenericParallelBehaviour/Integrate.hxx`).

# Current limitations

- the comparison of the jacobian to a numerical jacobian
  (`@CompareToNumericalJacobian`) prints its results on the standard
  output: it is only performed on the host.
- the `HIP` backend has not been tested on AMD GPUs.
- the SYCL backend has been tested with AdaptiveCpp (CPU and NVIDIA GPU)
  and with Intel's `icpx` (CPU).

# Tests

The tests are installed in
`share/tfel/test-suite/behaviours/generic-parallel`. For each configuration,
the `build-libraries.sh` script builds the test behaviours twice: with the
`generic` interface and the default compiler of `MFront` (reference), and
with the `generic` and `generic-parallel` interfaces and the tested
configuration (which checks that both interfaces can be used together). The
reference then does not depend on the tested compiler. The results of the
batch integration are compared to the results of the reference on two time
steps of a random loading, the second one being computed asynchronously,
for three layouts of the fields (point by point, component by component,
and component by component with the material properties and the external
state variables given variable by variable) and three types of computation, including
the energies, the speed of sound and the statuses of batches where the
integration fails at some points. The initialize functions, the
post-processings, the rotation functions and the standalone models are
compared on random states.
The list of the comparisons, shared by all the configurations, is given by
the `compare-all.sh` script; `compare.cxx` documents its options. The sizes
of the variables are read in the symbols of the reference library. The
behaviours using the `TDLS` linear system solver are tested in the `tdls`
subdirectory of each configuration (`compare-tdls.sh` script) if `TFEL` is
built with `TDLS` support.
