# Kernels of 3D finite strain behaviours that never end at -O2 on gfx1036

ROCm 10.1 (HIP 7.16, Python packages of TheRock, AMD clang 24.0.0git
d6f6cb69), integrated GPU gfx1036 (Ryzen 7 9800X3D), Ubuntu 24.04 with
Linux 7.0.

The kernels generated by MFront (`generic-parallel` interface, `hip`
backend) for two finite strain behaviours in 3D, those of the examples rve
and ssna303_3d, never end when compiled at -O2 or -O3: the GPU stays busy
at 100 %, the host waits for the completion signal of the kernel
(`BusyWaitSignal::WaitAcquire` under `hipLaunchKernel`, the kernels being
serialised). The same libraries compiled at -O0 or -O1 give the right
stresses. Plane strain passes at every level; the small strain behaviours
in 3D of the other examples pass at -O2.

    reproducers/hip-finite-strain-3d-hang/run.sh

(through `sg render` if the session does not have the group render yet).

`run.sh` generates with MFront, for each optimisation level of `LEVELS`
(`O1 O2` by default), the libraries of the behaviours of the examples
rve (ex6, `SaintVenantKirchhoffElasticity`) and ssna303_3d (ex4,
`IsotropicLinearHardeningPlasticity` with the logarithmic strain), compiled
as `mfem_mgis_add_behaviours_library` does, then integrates them by MGIS on
one point (`integrate.cpp`, data in managed memory, kernels and copies
serialised as for the tests of `scripts/build-hip-amd.sh`). It uses the
TFEL and the MGIS installed by the prototype (`install/tfel-mmm-gpu`,
`install/mgis`). Results of 20/10 (times left out):

## What was ruled out

- MFEM and mfem-mgis: `integrate.cpp` only uses MGIS, and one point is
  enough.
- The size of the private memory: the blocked kernels use 4840 bytes
  (ex6) and 7024 bytes (ex4) per thread, while passing builds of the same
  kernel use 7120 bytes (see below) and 19568 bytes (-O1); kernels writing
  up to 16400 bytes of private memory per thread pass.
- A loop without exit in the optimised IR: every loop of the kernel has an
  exit.
- The tangent operator conversion alone, and the push forward of a fourth
  order tensor alone, in a kernel of one thread: right at -O2 and -O3.

## Bisection of the optimisation passes

With `-Xarch_device -mllvm=-opt-bisect-limit=N` on the source generated
for `SaintVenantKirchhoffElasticity`, the first limit giving a blocked
kernel is the pass 151206 of the compile pipeline (178321 passes, then
2192 in the LTO stage): `inline` on
`FiniteStrainBehaviourTangentOperatorConverter<DTAU_DF, ABAQUS>::exe<3, double>`
of TFEL, which inlines into this function all the tensor operations of the
conversion (`det`, `unsyme`, `computeRateOfDeformationDerivative`,
`computeSpinRateDerivative`, `t2tot2::tpld`, `t2tot2::tprd` and the
products). At the limit 151205, the kernel passes, with 7120 bytes of
private memory. This inlining only gives a larger function: the defect is
in the code generation.

## The defect is in the code generation of the AMDGPU backend

The optimised IR of the library (`--save-temps`, before the code
generation) was compiled again into a code object with the code
generation at -O0, -O1 and -O2 (`clang -Xclang -disable-llvm-optzns`), and
its 3D kernel launched in place of the one of the library, with the same
arguments (a library loaded by `LD_PRELOAD` replacing the kernel given to
`hipLaunchKernel`): at -O0 the stress is right, at -O1 and -O2 the kernel
never ends. The same IR, the same runtime and the same GPU: the defect is
in the code generation. `llc` of the same revision of the LLVM of AMD
(d6f6cb69), built with the assertions, gives no assertion and no error of
`-verify-machineinstrs`. Its `-opt-bisect-limit` gives as first blocking
pass `amdgpu-isel` on the function
`mfront::gb::integrate<SaintVenantKirchhoffElasticity<Tridimensional>>`:
the selection of the instructions of this function at -O2 instead of -O0
is enough.

## Workaround

`scripts/build-hip-amd.sh` compiles the libraries of behaviours at -O1 for
gfx1036 only (`HIPCC_COMPILE_FLAGS_APPEND`), the other architectures keep
-O2. The examples rve and ssna303_3d_hypre then pass on this GPU.
