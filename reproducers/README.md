# Reproducers

Small standalone programs that check a precise point, outside the large
test suites. Each directory has a script `run.sh` that works in
`scratch/reproducers` and uses the MFront of the development tree
(`scratch/build-dev2`, sources of `tfel-dev`).

| Directory | What is checked | Expected result |
|---|---|---|
| `rotations` | Rotation of the blocks of the tangent operator of an orthotropic behaviour (`generic` library), independently of the code that rotates them: for any operator `K` and any gradients `x`, `rotateTangentOperatorBlocks(K) x = rotateThermodynamicForces(K rotateGradients(x))`, and identical in place rotation. The behaviour used by default, `OrthotropicTangentOperatorBlocksTest` (`generic-parallel` tests of `tfel-dev`), has blocks of all types (arrays, vectors, symmetric tensors, tensors). Another behaviour can be given as argument. | `OK` for each modelling hypothesis (gap of the order of 1e-15) |
| `device-strings` | String constant used in GPU code (comparisons, size), with six compilers. `std::string_view` goes through `std::char_traits` (`strlen`, `memcmp`): wrong results without message with nvcc and hipcc, errors with nvc++. A small type without `char_traits` (`constant-string.hxx`) works everywhere. | variants A and B wrong or refused, C and D right (`1 7 13 19`) |
| `hypre-ilu-gpu` | Incomplete factorisation of hypre (ILU) preconditioning its flexible GMRES, on CPU and on GPU (hypre 3.2.0 built with CUDA), three solves, the operator being given again before each one. `mfem::HypreILU` recreates the preconditioner of hypre with the default options of MFEM (fill level 1) at each new operator: a level given once (mode 2) is lost after the first solve. A preconditioner kept from one operator to the next (mode 1) keeps its level. Standalone program (MFEM and hypre only), `run.sh` without MFront. | CPU, 2 processes: 17 iterations with level 1, level 0 given once 18 then 17, 17 (level lost). GPU: ILU(0) kept 18 iterations at each solve; level 1 kept or by default: segmentation fault in `hypre_ILUSolveLUDevice` from the first solve; level 0 given once: 18 then segmentation fault at the second |
| `hypre-parasails-operator` | ParaSails preconditioner of hypre (`mfem::HypreParaSails`) of the GMRES of hypre, two solves with two operators, the first one destroyed before the second one is given, as the non linear solvers do. `mfem::HypreParaSails::SetOperator` (MFEM 4.10 and main branch) creates the new preconditioner of hypre with the communicator of the previous operator, already freed. Three modes: `mfem`, `kept` (first operator kept alive) and `fixed` (the preconditioner points to the new operator before the call, fix of mfem-mgis). Argument `cuda`: ParaSails computes only on the host. Standalone program (MFEM and hypre only), `run.sh` without MFront. | CPU, 2 processes: `mfem` 16 iterations then `MPI_ERR_COMM: invalid communicator`; `kept` and `fixed` 16 then 16. GPU (mode `fixed`, 2 processes): segmentation fault in `MatrixSetRow` from the first setup |
| `mfront-static-quantity-cuda` | Static constexpr member of a TFEL quantity (class type) used in GPU code, as the code generated by MFront for a static variable (`@StaticVariable`) of a behaviour that uses quantities (`@UseQt true`). nvcc refuses a reference to such a member in GPU code: an operator that takes its arguments by reference, in an expression evaluated at runtime, binds one. A copy initialised by a constant expression (`decltype(v){v}`, which is what the macro `TFEL_STATIC_VARIABLE`, written by MFront since the fix, gives in GPU code) passes. Compilation only, without GPU. | mode 1 (the member itself): `identifier "Behaviour<0>::Tref" is undefined in device code`; modes 2 (copy), 3 (expression evaluated at compile time) and 4 (macro `TFEL_STATIC_VARIABLE`): `OK` |
| `amgx-classical-cuda13` | Example `amgx_capi` of AmgX (conjugate gradient preconditioned by its multigrid, configurations shipped with AmgX) on a 20³ Laplacian, for each installation of AmgX given as argument (by default, the one of the environment). With CUDA 13 (commit 91a8413e of the main branch, sm_120), the device code of `src/amg.cu` does not contain the kernel of `thrust::sequence` on integers, although the inline functions of the matrices instantiate its host code: the copy of `cub::DeviceFor::Bulk` of this file launches a null kernel, and the linker keeps it. This defect does not depend on the option `-static-global-template-stub` of nvcc (checked with `=false`). The patch of the spack recipe (`amgx-cuda13-sequence-kernel.patch`) uses `thrust::sequence` in a function of this file. | Without the patch: classical "invalid device function" in `parallel_for`, aggregation 22 iterations. With the patch: classical 14 iterations, aggregation 22 |
| `cudss-distributed` | Distributed factorisation by cuDSS 0.7.1 (`mfem::CuDSSSolver` of MFEM 4.10) on 1, 2 and 3 processes (one GPU): `diagonal-rows`, tridiagonal matrix whose second half of the rows of the last process have only their diagonal coefficient, with or without coupling between the processes, symmetric pattern (isolated rows) or not, 4 and 400 rows per process; `structures`, tridiagonal matrix coupling the processes, and matrices whose each row is coupled to a row of the next process, evenly distributed or not. Standalone programs (MFEM only, compiled with the configuration of MFEM), `run.sh` without MFront. | 1 process: all cases right. 2 processes, diagonal rows: analysis fails (`CUDSS call ended unsuccessfully [code: 5]`) for the coupled matrices from 4 rows on and without coupling at 400 rows. Coupled tridiagonal: failure from 4 rows per process on. Coupling to the next process: right for 4 4, 4 6, 4 4 4, 4 4 6, 4 3 5 and 5 2 5, failure for 4 2 6 |
| `sync-call-overhead` | Duration of a synchronous call of the CUDA backend on a batch of an elastic behaviour, data in managed memory, with the headers of `tfel-dev` at a reference commit (before R8 by default) and those of the working tree. | 08/10, RTX 5080: 1000 points 135 → 29 µs, 100000 points 546 → 442 µs |

The comparisons between the `generic` and `generic-parallel` interfaces of
the affected behaviours run on their own, without building all the test
behaviours, with `scratch/targeted-test.sh configuration pattern behaviour...`.
