# Reproducteurs

Petits programmes autonomes qui vérifient un point précis, en dehors des
grandes suites de tests. Chaque dossier a un script `run.sh` qui travaille
dans `scratch/reproducers` et utilise MFront de l'arbre de développement
(`scratch/build-dev2`, sources de `tfel-dev`).

| Dossier | Ce qui est vérifié | Résultat attendu |
|---|---|---|
| `rotations` | Rotation des blocs de l'opérateur tangent d'une loi orthotrope (bibliothèque `generic`), indépendamment du code qui les tourne : pour tout opérateur `K` et tous gradients `x`, `rotateTangentOperatorBlocks(K) x = rotateThermodynamicForces(K rotateGradients(x))`, et rotation sur place identique. La loi utilisée par défaut, `OrthotropicTangentOperatorBlocksTest` (tests `generic-parallel` de `tfel-dev`), a des blocs de tous les types (tableaux, vecteurs, tenseurs symétriques, tenseurs). Une autre loi peut être donnée en argument. | `OK` pour chaque hypothèse (écart de l'ordre de 1e-15) |
| `device-strings` | Constante chaîne utilisée dans du code GPU (comparaisons, taille), avec six compilateurs. `std::string_view` passe par `std::char_traits` (`strlen`, `memcmp`) : résultats faux sans message avec nvcc et hipcc, erreurs avec nvc++. Un petit type sans `char_traits` (`constant-string.hxx`) fonctionne partout. | variantes A et B fausses ou refusées, C et D justes (`1 7 13 19`) |
| `hypre-ilu-gpu` | Factorisation incomplète de hypre (ILU) préconditionnant son GMRES flexible, sur CPU et sur GPU (hypre 3.2.0 construit avec CUDA), trois résolutions, l'opérateur étant redonné avant chacune. `mfem::HypreILU` recrée le préconditionneur de hypre avec les options par défaut de MFEM (niveau de remplissage 1) à chaque nouvel opérateur : un niveau donné une fois (mode 2) est perdu après la première résolution. Un préconditionneur gardé d'un opérateur à l'autre (mode 1) garde son niveau. Programme autonome (MFEM et hypre seuls), `run.sh` sans MFront. | CPU, 2 processus : 17 itérations avec le niveau 1, niveau 0 donné une fois 18 puis 17, 17 (niveau perdu). GPU : ILU(0) gardé 18 itérations à chaque résolution ; niveau 1 gardé ou par défaut : erreur de segmentation dans `hypre_ILUSolveLUDevice` dès la première résolution ; niveau 0 donné une fois : 18 puis erreur de segmentation à la deuxième |
| `hypre-parasails-operator` | Préconditionneur ParaSails de hypre (`mfem::HypreParaSails`) du GMRES de hypre, deux résolutions avec deux opérateurs, le premier détruit avant que le second soit donné, comme le font les solveurs non linéaires. `mfem::HypreParaSails::SetOperator` (MFEM 4.10 et branche principale) crée le nouveau préconditionneur de hypre avec le communicateur de l'opérateur précédent, déjà libéré. Trois modes : `mfem`, `kept` (premier opérateur gardé en vie) et `fixed` (le préconditionneur pointe sur le nouvel opérateur avant l'appel, correction de mfem-mgis). Argument `cuda` : ParaSails ne calcule que sur l'hôte. Programme autonome (MFEM et hypre seuls), `run.sh` sans MFront. | CPU, 2 processus : `mfem` 16 itérations puis `MPI_ERR_COMM: invalid communicator` ; `kept` et `fixed` 16 puis 16. GPU (mode `fixed`, 2 processus) : erreur de segmentation dans `MatrixSetRow` dès la première préparation |
| `mfront-static-quantity-cuda` | Membre statique constexpr d'une quantité de TFEL (type classe) utilisé dans du code GPU, comme le code généré par MFront pour une variable statique (`@StaticVariable`) d'une loi qui utilise les quantités (`@UseQt true`). nvcc refuse une référence à un tel membre dans le code GPU : un opérateur qui prend ses arguments par référence, dans une expression évaluée à l'exécution, en lie une. Une copie initialisée par une expression constante (`decltype(v){v}`, ce que donne dans le code GPU la macro `TFEL_STATIC_VARIABLE` écrite par MFront depuis la correction) passe. Compilation seule, sans GPU. | mode 1 (membre lui-même) : `identifier "Behaviour<0>::Tref" is undefined in device code` ; modes 2 (copie), 3 (expression évaluée à la compilation) et 4 (macro `TFEL_STATIC_VARIABLE`) : `OK` |
| `amgx-classical-cuda13` | Exemple `amgx_capi` d'AmgX (gradient conjugué préconditionné par son multigrille, configurations livrées avec AmgX) sur un Laplacien 20³, pour chaque installation d'AmgX donnée en argument (par défaut, celle de l'environnement). Avec CUDA 13 (commit 91a8413e de la branche principale, sm_120), le code device de `src/amg.cu` ne contient pas le noyau de `thrust::sequence` sur des entiers, dont les fonctions inline des matrices instancient pourtant le code hôte : la copie de `cub::DeviceFor::Bulk` de ce fichier lance un noyau nul, et l'éditeur de liens la garde. Ce défaut ne dépend pas de l'option `-static-global-template-stub` de nvcc (vérifié avec `=false`). Le patch de la recette spack (`amgx-cuda13-sequence-kernel.patch`) utilise `thrust::sequence` dans une fonction de ce fichier. | Sans le patch : classique « invalid device function » dans `parallel_for`, agrégation 22 itérations. Avec le patch : classique 14 itérations, agrégation 22 |
| `cudss-distributed` | Factorisation distribuée par cuDSS 0.7.1 (`mfem::CuDSSSolver` de MFEM 4.10) sur 1, 2 et 3 processus (un GPU) : `diagonal-rows`, matrice tridiagonale dont la seconde moitié des lignes du dernier processus n'ont que leur coefficient diagonal, avec ou sans couplage entre les processus, motif symétrique (lignes isolées) ou non, 4 et 400 lignes par processus ; `structures`, matrice tridiagonale couplant les processus, et matrices dont chaque ligne est couplée à une ligne du processus suivant, réparties également ou non. Programmes autonomes (MFEM seul, compilés avec la configuration de MFEM), `run.sh` sans MFront. | 1 processus : tous les cas justes. 2 processus, lignes diagonales : analyse en échec (`CUDSS call ended unsuccessfully [code: 5]`) pour les matrices couplées dès 4 lignes et sans couplage à 400 lignes. Tridiagonale couplée : échec dès 4 lignes par processus. Couplage au processus suivant : justes pour 4 4, 4 6, 4 4 4, 4 4 6, 4 3 5 et 5 2 5, échec pour 4 2 6 |
| `sync-call-overhead` | Durée d'un appel synchrone du backend CUDA sur un lot d'une loi élastique, données en mémoire managée, avec les en-têtes de `tfel-dev` à un commit de référence (avant R8 par défaut) et ceux de l'arbre de travail. | 08/10, RTX 5080 : 1000 points 135 → 29 µs, 100000 points 546 → 442 µs |

Les comparaisons entre les interfaces `generic` et `generic-parallel` des
lois touchées se lancent seules, sans construire toutes les lois de test,
avec `scratch/targeted-test.sh configuration motif loi...`.
